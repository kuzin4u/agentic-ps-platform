# ТЗ: агентная платформа платёжной системы

Редакция 1 · 08.10.2026 · основание: пул «Агентная коммерция» (файлы 07–14, 20–23, 29–31, 35–37), драфты A1–A9, решения РП1–РП17.

## 1. Назначение

Агентная платформа платёжной системы (далее — **Платформа**) — сервисный слой оператора платёжной системы, который делает агентную операцию **видимой, ограниченной и разбираемой** на действующих рельсах: карты «Мир», СБП, универсальный платёжный код.

Платформа не торгует, не выбирает товар и не заменяет банк. Её предмет:
- кто такой агент (реестр, ключи);
- что ему поручено (мандаты, журнал согласий);
- в каких пределах он действует (состояние бюджета);
- как это проверяется в момент авторизации (точка решения в процессинге);
- как это разбирается при споре (вычисление `in_scope`).

У Платформы две внешние границы:
1. **Интерфейс с процессингом (ОПКЦ)** и смежными системами оператора: СБП, токен-сервис, УПК, антифрод, отчётность. Описан в `PROCESSING-INTERFACE.md`.
2. **Протокол агентских операций (ПАО)** — интерфейс для агентов покупателя, в первую очередь BuyerAgent. Описан в `AGENT-PROTOCOL.md` и `agent-protocol.yaml`.

Плюс интерфейс для банков-участников (эмитент, эквайрер) — в `PROCESSING-INTERFACE.md`, раздел «Участники».

## 2. Главный архитектурный принцип

**Агент не инициирует авторизацию в платёжной системе.** Платёж, как и сегодня, инициирует продавец через эквайрера, а процессинг доводит его до эмитента.

Платформа встраивается в этот путь в двух местах:
- **до операции** агент получает от Платформы *агентский платёжный реквизит*: агентский токен с одноразовой криптограммой для карт или привязку счёта для СБП. Реквизит привязан к коду агента, мандату и области продавцов. Агент передаёт его продавцу вместе с признаком операции, номера карты он не видит;
- **в момент авторизации** процессинг синхронно обращается к *точке решения* Платформы (ADP — agentic decision point). Она проверяет признак, агента, мандат и бюджет, резервирует позицию бюджета и возвращает решение.

Метод `/v1/pay/authorize`, которым агент в испытательном контуре пула вызывал шлюз напрямую, — упрощение для испытаний. В Платформе он сохраняется только в песочнице как эмуляция цепочки «продавец → эквайрер → процессинг» (РП2).

### Реестр (П1): код, допуск, статус, ключи (РП21, РП23, РП27, РП28)

- **Код агента** — части через `:`, каждая `[a-z0-9-]+`: последняя — версия `v<N>` (N ≥ 1), предпоследняя — идентификатор, остальные — выдавшая сторона. `nspk:agent:buyref-01:v3` — сторона `nspk:agent`, идентификатор `buyref-01`, версия 3. Выдавшая сторона — только `nspk:agent`: код присваивается при допуске, операторы агентов коды не выдают; другая сторона — `CODE_INVALID` (РП23). Код неизменен; существенное изменение — новая версия, новая запись (A2 п. 4.1–4.2).
- **Основания отказа в допуске** (закрытый перечень): `APPLICATION_INCOMPLETE`, `CLASS_UNKNOWN`, `CODE_INVALID`, `CODE_TAKEN`, `PRINCIPAL_DATA`, `CONFORMANCE_MISSING`, `AGENT_CARD_MISMATCH`, `KEY_INVALID` (РП23). Заявление, не попадающее ни под одно, допускается (A6 п. 2.1). Учитываются только поля `agent_code`, `class`, `model`, `runtime`, `conformance_run_ref`, `agent_card`, `alg`, `public_key`; оператор — из контекста вызова, не из заявления: контекст создаёт только аутентификация оператора по его сертификату mTLS (РП28; код — PS-31).
- **Уровень** — целое ≥ 1, при допуске — 1; изменяет П8 по оценке исполнения.
- **Статус:** ACTIVE → SUSPENDED — с основанием A2 п. 7.1 (`KEY_COMPROMISE`, `OUT_OF_MANDATE`, `FALSE_INFORMATION`, `INCIDENT_EVASION`); SUSPENDED → ACTIVE — без основания; EXCLUDED — из любого статуса, с тем же основанием или `WITHDRAWN`; из EXCLUDED выхода нет.
- **Приостановление и снятие (РП54):** одно действие оператора Системы — `suspend` / `reinstate` службы статуса (HTTP — PS-32; на стенде — `stand.suspendAgent`, `stand.reinstateAgent`). Сначала статус, затем событие `agent.suspended` / `agent.reinstated`; событие не записалось — статус остаётся, инцидент, ошибка вызова; повтор действия в достигнутом статусе дописывает событие. `suspended_at` — время последнего приостановления, при снятии сохраняется: реквизиты и `confirmation_ref` с `created_at < suspended_at` ADP не принимает и после снятия (§6 п. 4, 10). Мандаты, реквизиты, запросы подтверждения и удержания не меняются; авторизованное до приостановления исполняется (A3 п. 6.2). Распространение до ADP и шлюза — ≤ `revocation_propagation_max_ms` (инвариант 8): статус читается из реестра на каждом решении и обращении, кэша нет; будущий кэш — со сроком меньше `revocation_propagation_max_ms` или со сбросом по смене статуса. **Реестр — в памяти процесса: до развёртывания больше чем в одном экземпляре — переезд в PostgreSQL** (РП54 п. 3). Исключение: снятие мандатов Платформой — PS-32 (РП54 п. 12).
- **Ключи (РП23):** первый ключ — в заявлении (`alg`, `public_key` — DER SPKI, каноническая запись base64 по RFC 4648 §3.5; иная запись — `KEY_INVALID`, РП23 доп. 6), пару генерирует оператор агента; запись и ключ сохраняются вместе или не сохраняются. `kid` присваивает Платформа — отпечаток JWK по RFC 7638, глобально уникален; повтор ключа у другого агента, свой отозванный или истёкший — `KEY_INVALID`; свой действующий повторно — тот же ключ без изменений (РП23 доп. 7). `valid_to = valid_from + key_ttl_days`; новый ключ сокращает срок остальных действующих до `now + key_overlap_days`; наступил `valid_to` — `EXPIRED`. Отзыв любого ключа, включая последний, необратим и действует со следующей проверки подписи; повторный отзыв возвращает тот же ключ. Слабый ключ Ed25519 (неканоническая запись точки, точка малого порядка) — `KEY_INVALID`. Исключённому агенту новый ключ не регистрируется; приостановленному — только через оператора (PS-31), не по ПАО (РП23 доп. 8, #33); проверка статуса неделима с добавлением ключа (РП23, дополнения). Смена ключа приостановленным агентом — только через оператора (PS-31), не через ПАО: `POST /pao/v1/agent/keys` от приостановленного — `AGENT_SUSPENDED` (РП23 п. 6.3). Отказ от полномочий (`relinquish`) приостановленному доступен, исключённому — нет (РП38 доп. п. 8). По ПАО — `POST /pao/v1/agent/keys` под ключом идемпотентности: 201 `Key`; недопустимый ключ — 422 `KEY_INVALID` без причины (РП31 п. 2); класс, уровень и прочие поля тела сверх схемы игнорируются. **Отзыв по ПАО (РП60 п. 1–8):** `POST /pao/v1/agent/keys/{kid}/revoke` — пустое тело под ключом идемпотентности, 200 `Key` `REVOKED`; любой свой ключ, в том числе последний и тот, которым подписан запрос; повторный — тот же `Key`. Чужой, неизвестный и не по форме `kid` — один ответ 422 `KEY_INVALID`, в журнал процесса — признак (`FOREIGN`, `UNKNOWN` — с `kid`; `MALFORMED` — только длина, РП60 доп. 3); в пределах транспортного предела и корректного процентного кодирования: `kid` длиннее 256 знаков — 414, испорченное кодирование (`%zz`) — 400, оба — ответы Fastify до проверки обращения, не ПАО §6 (№ 43, заделы № 8–9 → PS-05б ч. 2). Приостановленному — доступен, исключённому — 403 `AGENT_SUSPENDED` (исключение из РП23 п. 6.3, как `relinquish`). Событие `agent.key_revoked` не выпускается до отзыва оператором (PS-31). Распространение: на этом экземпляре — со следующей проверки подписи; между экземплярами — после переезда реестра (PS-05в); каталог JWKS у продавца — до `merchant_jwks_max_age_sec`, авторизацию это не открывает (ADP решает по реквизиту, а не по ключу подписи пакета); выданные до отзыва реквизиты действуют. **Остаточный нюанс (РП60 доп. 5):** статус агента читается на проверке обращения, а `revoke` его не перепроверяет (у `register` проверка неделима со вставкой): агент, исключённый между проверкой и отзывом, свой ключ отзовёт — полномочия только сужаются; к пересмотру при переезде реестра (PS-05в). **Нюанс (РП60 доп. 2):** держатель украденного ключа может им же отозвать все остальные ключи агента — агент блокируется до оператора; свойство A2 п. 5.4, к пересмотру при PS-31 или ПАО 1.5.0.
- **Сертификат mTLS агента (РП27):** ключ генерирует оператор агента, Платформа получает CSR; сертификат УЦ песочницы выдаётся в решении о допуске, код агента — в SAN URI `urn:nspk:agent:<id>:v<N>`; отзывается только при компрометации ключа сертификата (приостановление и исключение режет статус). Стенд dev — без mTLS.
- **Обнаружение ПАО (РП60 п. 9–14):** `GET /.well-known/pao-configuration` — в рабочем сервере и на стенде одной функцией `buildServer`, своей областью без проверки обращения; строго по схеме `Configuration` 1.4.0 (`versions` — `PAO_SPEC_VERSION`, `sunset: {}`, `platform_keys: []` до SEC-1, `algorithms` — по контуру реестра, без `endpoints`); грубый лимит по адресу — свой счётчик (РП32); `Cache-Control: no-cache`; режим «только BYPASS» — 503 `UPSTREAM_UNAVAILABLE` по ПАО §6 с `Retry-After`. Стендовые параметры для агента — ПАО 1.5.0. **Нюанс к SEC-1 (п. 14):** с 1.5.0 конфигурация — источник доверия к ключам Платформы; её подлинность — только TLS шлюза (РП27), подписи у самой конфигурации нет.
- **Проверка обращения ПАО (РП23, РП27):** сертификата нет, он не УЦ песочницы или его код агента не равен `x-agent-code` — `AGENT_UNKNOWN`, истёк или отозван — `AGENT_KEY_REVOKED` (ступень 0, РП27; код — PS-05) → агента нет — `AGENT_UNKNOWN` → подпись ключами только агента из `x-agent-code` (`SIGNATURE_INVALID`; отозванный или истёкший ключ — `AGENT_KEY_REVOKED`; nonce проверяется и запоминается одной операцией после успешной проверки подписи, РП30) → статус (`SUSPENDED`, `EXCLUDED` — `AGENT_SUSPENDED`, кроме `GET /pao/v1/agent`; при `SUSPENDED` открыты ещё `POST /pao/v1/mandates/{id}/relinquish` — РП38 доп. п. 8 — и `POST /pao/v1/agent/keys/{kid}/revoke` — РП60 п. 3; путь — точным выражением, только `POST`). Сбой реестра, ключей или хранилища nonce на любой ступени — `UPSTREAM_UNAVAILABLE` (503, `Retry-After` по РП24), обращение не принимается (РП23, дополнения; РП30). После проверки обращения, до обработчика изменяющего метода: нет `Idempotency-Key` — `IDEMPOTENCY_REQUIRED`; тело не по схеме метода (не JSON, нет обязательного поля, неверный тип, значение вне перечня) — `REQUEST_INVALID` (400, `after_fix`, ПАО 1.3.0), до захвата ключа идемпотентности: неполный запрос ключ не занимает; недопустимый реквизит мандата по смыслу (форма `principal_ref`, срок в прошлом, корзина, родитель-CART) — тоже `REQUEST_INVALID`, но после захвата: ответ сохраняется под ключом (РП33 п. 1); в `message` нет фрагментов присланного тела (РП31). Тело ошибки — ПАО §6 как есть.
- **Хранилища шлюза ПАО (РП30):** nonce и идемпотентность — хранилища agentic-core на PostgreSQL. Nonce — одна область `pao`, значение `<agent_code> <x-nonce>` (разбор по первому пробелу), срок — 2 × `signature_skew_sec`, очистка раз в `signature_skew_sec`. Идемпотентность изменяющих методов — область `pao:<agent_code>`, ключ — SHA-256 от `Idempotency-Key` (длина ключа агента на хранилище не влияет, РП30 п. 3, дополнение), хэш тела от метода, пути, запроса и тела; сохраняется ответ обработчика (2xx, 4xx), сбой (5xx) — нет; срок — `idempotency_ttl_sec`, аренда захвата — 60 с. Без ключа — `IDEMPOTENCY_REQUIRED`, другое тело или путь — `IDEMPOTENCY_CONFLICT`, тот же ключ ещё выполняется или сбой хранилища — `UPSTREAM_UNAVAILABLE` до обработчика. Без базы: `sandbox` не запускается; `dev` и стенд для агента — хранилища ядра в памяти (один процесс).
- **Лимит частоты шлюза ПАО (РП32):** первый слой — по адресу на всех маршрутах `/pao`, хук `onRequest` до проверки обращения и до чтения тела (`@fastify/rate-limit`); `pao_rate_limit_per_30s` обращений за окно 30 с; превышение — 429 `RATE_LIMITED` по ПАО §6 с `Retry-After` ≤ 30 (РП24). Ключ — адрес соединения, IPv6 — его подсеть /64; `X-Forwarded-For` читается только от доверенных прокси (`PAO_TRUSTED_PROXIES`, адреса и CIDR не шире IPv4 /16 и IPv6 /32; «доверять всем» — отказ запуска). `Retry-After` обрезается до 30 и при переводе часов назад (РП32, дополнение). Счётчик — в памяти процесса (один экземпляр). `/health` не ограничен. Второй слой — по уровню агента после проверки подписи — отдельным решением.

### Журнал согласий (П2): запись мандата (РП14, РП33)

- **Записи** — журнал ядра (`core_journal`), одна цепочка на корневой мандат, CART под INTENT — в цепочку родителя; только вставка (инвариант 6). Статус — свёртка записей при чтении (`PENDING_SIGNATURE` → `ACTIVE` / `REJECTED` → `REVOKED`; `EXPIRED` — по `valid_to`; `ACTIVE` → `EXHAUSTED` — запись `MANDATE_EXHAUSTED`, которую П3 пишет, когда закреплён весь предел, РП41 п. 11; конечный, срок на него не действует; дубль записи пропускается, отзыв после неё — гонка двух экземпляров — `REVOKED`).
- **Предмет** (`subject`, `cart`) — в записи только хэш-обязательство `sha256(canonicalJson({salt, subject, cart}))`, соль 32 байта и предмет — в `consent_subjects` (A7 п. 9.2). Открыты реквизиты, нужные ADP и verify; `principal_ref` — только непрозрачный идентификатор.
- **Запрос мандата** (`POST /pao/v1/mandates`): в запись — только поля перечня; CART под INTENT — только под `ACTIVE` родителем этого агента и только сужением (A7 п. 5). Отказы — коды ПАО по РП33 п. 1.
- **Идемпотентность мандата** (РП33 доп. п. 5–9): id вычисляется — `mnd_` + UUID v8 из SHA-256(`pao:mandate-id:v1\n` + `agent_code` + `\n` + хэш `Idempotency-Key`); прежние v4 действительны. Пока ключ хранится в ядре (24 ч), повтор получает сохранённый ответ (статус — на момент первого ответа). Позже, или после 5xx, мандат ищется по id до проверки срока и родителя:
  - запись журнала есть и запрос совпадает по смыслу — тот же мандат в любой срок, статус на момент повтора (после `valid_to` — `EXPIRED`);
  - запрос другой или не проходит проверку реквизитов — `IDEMPOTENCY_CONFLICT`, в любой срок;
  - запись прервалась (индекс или индекс и предмет) — сохранённая часть сверяется с запросом (реквизиты по `terms_hash` индекса, цепочка, предмет), затем запись доделывается со свежей проверкой срока и родителя; расхождение — `IDEMPOTENCY_CONFLICT`.

  Обработчик под ключом не пишет после `PAO_HANDLER_BUDGET_MS` = 30 с от захвата: предел проверяется перед каждой командой записи, в том числе перед каждой попыткой вставки в журнал; команда к базе — до 2 с на соединение и 2 с на исполнение, исполнение — и на сервере (`statement_timeout`). Последняя запись — не позже 34 с, второй обработчик того же ключа (аренда 60 с) не начнёт запись, пока первый может писать. Остаточный риск — процесс, вставший дольше аренды между проверкой предела и записью: две головные записи одного id, мандат не читается (503, fail-closed), ключ занят навсегда (агент сообщает клиенту об ошибке; новый ключ — только после нового подтверждения поручения клиентом) до условной вставки в журнал ядра (STATUS «Открыто»).

- **Порядок отзыва** (РП37, A7 п. 2.1–2.2): реквизит `revocation_order` — ссылка на соглашение банка с клиентом (`bank:<participant_code>:revocation:v1`); задаёт Платформа из записи участника (до PS-20 — `PARTICIPANT_KEYS_PATH`), поле от агента игнорируется; входит в `payload` записи и в `Mandate.hash` — банк подписывает мандат вместе с ним. Не задан — мандат не пишется, 503 `STATE_UNAVAILABLE`. CART наследует порядок родителя; со вторым банком корневой — по банку клиента (Б2). Повтор записанного мандата тем же ключом — записанный порядок (сверяются только реквизиты агента); запись без порядка отзыва не читается как действующая (503).
- **Статус CART** (РП35): при чтении — вместе со статусом родителя по одному снимку цепочки. Собственные `REVOKED` и `REJECTED` сохраняются; родитель `REVOKED`/`REJECTED` → CART `REVOKED`; родитель `EXHAUSTED` → CART `EXHAUSTED` (РП41 п. 11); родитель `EXPIRED` → CART `EXPIRED`; иначе — собственный статус. Записей потомкам нет. Одно вычисление — для `GET`, `verify`, подписи принципала и ADP. Родитель не `ACTIVE` на момент проверки — `409` (РП33 п. 1). Если отзыв записан между проверкой родителя и записью CART (гонка), CART оказывается в цепочке после отзыва, а `POST` отвечает `201` со статусом `REVOKED` (тот же ответ на повтор тем же ключом). На повтор после 24 ч памяти ключей `201` несёт статус на момент повтора — `REVOKED`/`EXPIRED` и без гонки. В пределах 24 ч повтор отдаёт сохранённый ответ со статусом первого ответа. Агент обязан проверять `status` после `201`; актуальный статус — только из `GET`.
- **Чтение мандата** (`GET /pao/v1/mandates/{id}`, РП34): статус — свёртка записей на момент чтения, а не сохранённый ответ `POST`. Чужой id, неизвестный id, id не по маске `MANDATE_ID` и прерванная запись (индекс без записи журнала) — один и тот же ответ `MANDATE_NOT_FOUND` 404 с одинаковым телом: существование чужого мандата не проверить (A7 п. 8). Id не по маске отсекается до обращения к базе. Нарушенная цепочка или неопределённое состояние — `STATE_UNAVAILABLE` 503 (инцидент в журнал процесса), сбой хранилища — `UPSTREAM_UNAVAILABLE` 503; `Retry-After` по РП24, подробностей сбоя в ответе нет. Приостановленный агент мандаты не читает (403, РП23 п. 6).
- **Отзыв и отказ агента** (РП38, A7 п. 6): клиент — через банк, `POST /participants/v1/mandates/{id}/revoke` (ПИ-8) с подписью банка над записью отзыва (`mandate_hash`, метка `pao:participant-mandate-revocation:v1`), запись `MANDATE_REVOKED` с записью участника и подписью; агент — `POST /pao/v1/mandates/{id}/relinquish`, запись `MANDATE_RELINQUISHED` с `{agent_code, kid}` из обращения. Пишется только при `PENDING_SIGNATURE`/`ACTIVE` (у CART — вместе с родителем); `REVOKED`, `REJECTED`, `EXPIRED`, `EXHAUSTED` — 200 с текущим статусом без записи. Отзыв родителя действует на CART свёрткой (РП35). Отзыв, отказ и решение банка по одному мандату внутри процесса — под одним локом записи. Свёртка: после `REVOKED` записи отзыва, отказа и решения пропускаются, после `REJECTED` — записи отзыва и отказа (гонки на двух экземплярах не дают 503). ADP и `/credentials` берут статус свёрткой при каждом решении (инвариант 8); событие `mandate.revoked` — PS-08. **`revoke-all`** (РП45 п. 4, РП46 (а); PS-20 ч. 2): метка пары `(participant_code, principal_ref)` в таблице порядка пары `principal_order` (`sql/106`); подпись мандата (`SIGN`) и метка берут один `pg_advisory_xact_lock` пары, номер в паре выдаётся под ним — порядок номеров = порядок фиксации. Мандат отозван меткой, если номер последней метки больше номера `SIGN` корня (у CART — корня); правило применяет свёртка `load` (одно вычисление для `GET`, `verify`, подписи, П3 и ADP), подписанный мандат без строки `SIGN` — `ConsentStateUnknown` (503 / `STATE_UNAVAILABLE`). Затем — `MANDATE_REVOKED` с записью банка (`{mandate_id, revoke_all}`) и событием каждому `ACTIVE`-мандату с номером `SIGN` меньше метки, сначала CART; подпись CART под корнем, отозванным меткой, — 409 `MANDATE_NOT_PENDING`. Тот же `revocation_ref` с другой записью — прежняя метка (действие то же, запись банка — первая), в журнал процесса. Время отзыва — `at` записи журнала (момент, когда Платформа узнала), `revoked_at` банка — сведения (РП38 доп. п. 4). Остаточный риск: при неопределимом статусе (две разные подписи на двух экземплярах) отзыв — 503 и не записывается (РП38 доп. п. 5). `relinquish` пишет без предела обработчика: лишняя запись при повторе после аренды пропускается свёрткой (РП38 доп. п. 6).
- **Проверка** (`GET …/verify`, РП38 п. 6, A7 п. 9.2): ровно `{outcome, amount_left, valid_to, as_of}`, предмета нет. `CONFIRMED` — `ACTIVE`; `OUT_OF_SCOPE` — остальные статусы; `STATE_UNKNOWN` — с П3; нарушенная цепочка, предмет не сходится с обязательством или неопределимый статус — 503 `STATE_UNAVAILABLE` (в выписке те же нарушения целостности — 200 `BROKEN`, неопределимый статус — 503). `amount_left` (РП41 п. 10): у `ACTIVE` — остаток счёта мандата в П3, не ниже 0 (счёта ещё нет — `amount_limit`); бюджет не прочитан при целом журнале — 200 `STATE_UNKNOWN` с `amount_left` = 0; у `EXHAUSTED` и прочих — `OUT_OF_SCOPE`, 0; у CART — по счёту CART. Чтение не пишет и счёт не открывает. ~~До PS-09: `amount_left` = `amount_limit`~~ — отменено РП41.
- **Выписка** (`GET …/evidence`, РП38 п. 7, A7 п. 9.3): `mandate_chain` (как `GET`; у CART — родитель и CART), `records` — вся цепочка журнала `{seq, kind, ref, parent_ref, at, payload, prev_hash, hash}`: хэши, `Mandate.hash` и подписи банка проверяются без Платформы и без банка (ключ банка — из реестра участников; начало цепочки — `chainGenesis("consent:<корень>")` ядра, хэш записи — `entryHash`). `operations` — `[]` до PS-16/PS-22. Выписка — из одного снимка цепочки: хэши, статусы и `records` по одному чтению (РП38 доп. п. 1). Нарушенная цепочка — 200 `integrity: BROKEN` с пустыми массивами. `signature_ref` и `revocation_ref` банка — непрозрачные ссылки без ПДн по маске `principal_ref` (РП38 доп. п. 2). **Ограничение:** раскрытие предмета (соль к `subject_commitment`) — только по запросу клиента через банк (ПИ-8, PS-20/PS-22), в PS-06 не делается; агенту соль не отдаётся.

### Порт «банк» (П10): протокол участника, подпись принципала (РП36)

- **Уровень интеграции пилота — А:** решение ADP — до выпуска реквизита; банк выпускает одноразовую виртуальную карту с лимитом ровно на заказ, авторизация — обычным путём (РП2). От банка: выпуск карты по API, лимит, вебхуки. Уровень Б (ADP в авторизации, ПИ-1) — позже.
- **Протокол участника и адаптеры:** Платформа говорит с банком на своём каноническом протоколе (ПИ-8); адаптер банка, адаптер песочницы (эмуляторы) и пустой слот НСПК — в `src/adapters/`; у каждого адаптера — набор тестов соответствия. API конкретного банка ядро не знает.
- **Подпись принципала:** клиент подписывает мандат простой ЭП в приложении банка по договору с банком (63-ФЗ, A7 п. 3); банк присылает подтверждение подписи — подпись Ed25519 ключом банка над записью о решении с хэшем мандата `Mandate.hash` (хэш записи журнала: реквизиты и обязательство предмета с солью) и меткой контекста `pao:participant-mandate-signature:v1` (РП36 доп. п. 1–2). Платформа проверяет подпись банка по реестру участников; ключей и данных входа клиента у Платформы нет. Подпись банка — подтверждение для Платформы, не ЭП клиента.
- **Точка входа:** `POST /participants/v1/mandates/{id}/sign` (ПИ-8) — только запрос участника с подписью участника; неаутентифицированной точки нет, в том числе на стенде (эмулятор эмитента подписывает тестовым ключом). До шлюза участников (PS-20) — список доверенных ключей в файле `PARTICIPANT_KEYS_PATH`; нет — подпись отклоняется всем; не больше одного боевого участника до привязки мандата к банку; ключ эмулятора — только на стенде (РП36 доп. п. 7–9).
- **Запись решения** (РП36 доп. п. 3–6): только при `PENDING_SIGNATURE` (у CART — вместе с родителем); повтор той же подписи — 200 без второй записи; другая после записанной — 409; `simple` выше порогов `qualified_signature_above_*` или не в рублях — 422, мандат не активируется. Остаточный риск: разные решения на двух экземплярах одновременно — 503 до условной вставки ядра (гонка «подпись против отзыва» — не 503: отзыв поглощает решение, РП38 п. 5).

### Шлюз ПАО (П9): лента событий агенту (РП39), подписка и доставка (РП40)

- **Очередь — Outbox в транзакции записи:** событие вставляется в `pao_events` в той же транзакции PostgreSQL, что и запись журнала; внешний ключ на `core_journal (chain, seq)` — событие без записи невозможно, откат — без записи и без события. В памяти (dev, стенд) — в том же вызове `append`.
- **Порядок:** номер `seq` у агента выдаётся под `pg_advisory_xact_lock` по коду агента до фиксации — номера без пропусков, порядок номеров = порядок фиксации, курсор не проскакивает незафиксированное событие; блокировка на агента, не общая (РП39 п. 2).
- **События мандата:** `MANDATE_SIGNED` → `mandate.signed`, `MANDATE_REJECTED` → `mandate.rejected`, `MANDATE_REVOKED` и `MANDATE_RELINQUISHED` → `mandate.revoked`, `MANDATE_EXHAUSTED` → `mandate.exhausted` (РП41 п. 11: по закреплению всего предела, не по резерву; возможен дубль); одна запись — одно событие, `event_id` вычисляется от записи (`evt_` + UUID v8), `data` — только `{mandate_id}` (A7 п. 8.3). У CART, которые теряют силу вместе с родителем, своих событий нет (РП35).
- **`GET /pao/v1/events?after=`** — только свои события, по возрастанию `seq`, не больше `event_page_max`; чужой или неизвестный `after` — 400 `REQUEST_INVALID`. Ответы 400/401/403/503 в YAML — с ПАО 1.5.0 (№ 20).
- **Ограничение до ПАО 1.5.0:** события не подписаны — для агента только сигнал; действие — по `GET /pao/v1/mandates/{id}`. Дубли и события без смены статуса (запись, поглощённая свёрткой, РП38 п. 5) — норма. ПС03 до 1.5.0 — без части «событие подписано».
- **Подписка** (`PUT /pao/v1/subscription`, РП40 п. 1–3): в записи агента, заменяется целиком; адрес — `https://`, порт 443, имя хоста (не IP) из `event_subscription_allow_hosts` (пустой — отказ всем); при `PUT` имя разрешается, хоть один не глобальный адрес — 400 `REQUEST_INVALID`, причина — в журнал процесса.
- **Доставка с повтором** (РП40 п. 4–5): перед каждой отправкой имя разрешается заново, соединение — с проверенным IP; без перенаправлений, успех — только 2xx, тайм-аут `event_delivery_timeout_ms`, тело ответа не читается. Попытки — `pao_event_deliveries` (`sql/102_event_deliveries.sql`; изменяемая, строка — в транзакции события, если агент `ACTIVE` и подписан на тип; у `agent.suspended` — и при `SUSPENDED`, РП54 п. 9); строки берутся по одной с арендой (`FOR UPDATE SKIP LOCKED`, `claims` — номер взятия, итог — только последнему взявшему); разрешение имени и отправка — в одном пределе `event_delivery_timeout_ms`; задержка — `nextAttemptDelayMs` ядра; `event_retry_max` попыток всего, затем `EXHAUSTED` — событие только в ленте; попытка без отправки (агент не `ACTIVE`, статус не прочитан) не тратится (дополнение РП40 п. 6–14).
- **`SUSPENDED` / `EXCLUDED`** (РП40 п. 6–7): лента и подписка — 403 `AGENT_SUSPENDED` (как `GET` мандата, исключение — только `GET /pao/v1/agent`); push не выполняется, статус читается перед каждой отправкой (`SKIPPED` без попытки); события копятся в `pao_events` и доступны через ленту после снятия приостановки, push по накопленным не догоняет. Исключение — `agent.suspended`: push-ем уходит и при `SUSPENDED` (РП54 п. 9).
- **События статуса агента** (РП54 п. 8): `agent.suspended` / `agent.reinstated` — четвёртый источник `pao_events` без записи журнала, `agent_status_version` = `row_version` записи реестра (`sql/116`), `UNIQUE (agent_code, agent_status_version)`; `data` — только `{agent_code}`, без основания. `EXCLUDED` события не даёт до ПАО 1.5.0 (PS-32).
- **Стенд** (РП40 п. 8): проверка адреса не отключается; подменяются только разрешение имени и транспорт (эмулятор агента `agent-emulator.stand` в процессе); в рабочем сервере стендовые порты — отказ запуска.

### Продавцы и площадки (П10): каталог ключей агентов, пакет оплаты (РП22)

- **Каталог ключей агентов** — JWKS (RFC 7517). Ключ — JWK по RFC 8037: `kty: OKP`, `crv: Ed25519`, `x`, `alg: EdDSA`, `use: sig`; `kid` — тот же отпечаток RFC 7638, что `Key.kid` ПАО. Частные члены: `agent_code`, `nbf`, `exp` (секунды Unix, `nbf` = `valid_from`, `exp` = `valid_to`). В каталоге только действующие ключи агентов в статусе `ACTIVE`; отозванный, истёкший ключ и ключи приостановленного или исключённого агента удаляются (РП22 п. 1–2). Каталог строит одна функция реестра (П1): её используют эмулятор продавцов (PS-12) и HTTP-адрес каталога (PS-30).
- **Адрес каталога** (РП56 п. 1–3): `GET /.well-known/agent-keys`, без подписи; `Content-Type: application/jwk-set+json`, `Cache-Control: public, max-age=<merchant_jwks_max_age_sec>`; сбой реестра — 503 `UPSTREAM_UNAVAILABLE` с `Retry-After`, не пустой каталог (инвариант 3); в режиме «только BYPASS» (РП43 п. 8) каталог и статус агента — 503 `UPSTREAM_UNAVAILABLE` с `Retry-After: 30` без `Cache-Control`, а не 404 (РП56 п. 8). Каталог — только своего контура ключей (`jwks(contour)`): среды `dev` и `sandbox` — контур `sandbox`; ключи не Ed25519 в каталог не попадают.
- **Статус агента** (РП56 п. 4): `GET /merchants/v1/agents/{code}`, без подписи — `{agent_code, status, class}`; неизвестный, не по форме или из другого контура — 404 `AGENT_UNKNOWN`; сбой реестра — 503. Сведений об операторе сверх кода и о принципалах нет (A2 п. 1.2). Путь ПИ-8 для эквайрера — `GET /participants/v1/agents/{code}/status` с подписью запроса участника роли `ACQUIRER`, тело и коды те же (РП57 п. 6). Перебор кодов без подписи — остаточный риск, ограничение частоты на входе — SEC-2.
- **Роль участника `ACQUIRER`** (РП57 п. 1): запись доверенного участника с обязательным перечнем `merchants`; подписывает только маршруты эквайрера ПИ-8 и только для своих продавцов; маршруты эмитента с его подписью — 401, `ISSUER` и `UPK` на маршрутах эквайрера — 401. Один `merchant_id` у двух участников — отказ запуска. Стенд — `stand:acquirer-emulator`.
- **Знак готовности** (РП57 п. 2–3; A5 п. 5): записи только вставкой (`sql/118`), порядок — номер записи в базе. Эквайрер подаёт `ACTIVE` и снимает `WITHDRAWN` подписанной записью (`POST /participants/v1/merchants/{id}/readiness`, `readiness_ref` уникален навсегда, повтор — без изменения статуса, `issued_at` не в будущем сверх `signature_skew_sec`); оператор приостанавливает (`SUSPENDED` с причиной) и снимает (`REINSTATED`) — на стенде `stand.suspendReadiness` / `reinstateReadiness`, автоматического приостановления нет. Статус: последняя запись оператора `SUSPENDED` → `SUSPENDED`; иначе по последней записи эквайрера — `ACTIVE` или `NONE`. При `SUSPENDED` эквайреру — 409 `READINESS_SUSPENDED`. Чтение — `{merchant_id, status, since}`: продавцу без подписи (`Cache-Control: max-age=<merchant_readiness_max_age_sec>`), эквайреру с подписью и причиной (чужой продавец — 404, у `POST` — 403 `MERCHANT_NOT_SERVED`), агенту через ПАО `GET /pao/v1/merchants/{id}/readiness` (`no-store`; в YAML — с ПАО 1.5.0). Неизвестный продавец — `NONE`. Знак не влияет на выдачу и не читается ADP (A5 п. 5.2, A6 п. 2.1).
- **Метаданные пакета и сверка** (РП57 п. 5; РП22 п. 6): эквайрер присылает подписанную запись `{merchant_id, metadata_ref, credential_ref, order_ref, aoi?, submitted_at}` (`POST /participants/v1/merchants/{id}/payments`, `sql/119`, только вставка); ответ и `GET …/payments/{credential_ref}` — сверка по записи реквизита: `MATCHED` с `op_ref`, `MISMATCH` с `fields`, `PENDING`, `NOT_USED` с `reason` (`EXPIRED`, `MANDATE_REVOKED`, `AGENT_SUSPENDED`); `aoi_checked: false` — без `aoi`. После реверсала и возврата — `MATCHED` с тем же `op_ref`. Чужой или неизвестный реквизит — 404 `CREDENTIAL_NOT_FOUND`. Решение ADP от метаданных не зависит; `MISMATCH` — в журнал процесса для решения оператора.
- **Проверка у продавца:** подпись RFC 9421 по ключу из каталога; `agent_code` ключа ≠ `x-agent-code` или истёкший `exp` — отказ; неизвестный `kid` — одно перечитывание не чаще раза в `merchant_jwks_refetch_min_sec`, затем отказ (РП22 п. 2–3). Отзыв доходит до продавца не дольше чем за `merchant_jwks_max_age_sec`; отказ в авторизации всё равно даёт ADP.
- **Пакет агентской оплаты** — `PaymentPackage` (ПАО §4): `credential_ref`, `kind`, `payload`, `aoi`, `cart_mandate_id`, `order_ref`, подпись агента. Суммы в пакете нет: сумма — только из сообщения процессинга (инвариант 5, РП22 п. 5).
- **Эквайрер без поддержки `aoi`** (РП22 п. 6): операция с инструментом `AGENT_TOKEN` или `ACCOUNT_LINK` остаётся агентской, ADP определяет агента и мандат по домену токена (ФП4); метаданные пакета (присылает эквайрер за продавца по ПИ-8, РП57 п. 5) — только для сверки по `credential_ref` и отчётности, решение ADP от них не зависит.

### Диагностика (РП42): реестр кодов и самопроверка при старте

- **Формат — `/diag` agentic-core (К17):** у каждого кода — компонент, источник (агент / Платформа / банк / продавец / клиент / среда), действие получателя, тексты для человека и оператора (`ru` обязателен, без бренда и подстановок), норма, «с версии». Код не из реестра — действие `stop`.
- **Три реестра:** `PAO_DIAG` ядра (коды ПАО, свой реестр не пишется), `PI_DIAG` (13 кодов причин ПИ, номера ОПКЦ — `[альбом]`), `PLATFORM_DIAG` (коды вне протоколов: `RESERVATION_RELEASED`, `COMMIT_CONFLICT` П3, коды самопроверки `STARTUP_*`). Коды ПИ и ПАО с одинаковым именем — разные записи: разный получатель. Полнота — тестом («код без записи — красный»).
- **Самопроверка при старте:** отчёт «готов / не готов» с кодами (`params`, `proxies`, `db.storage`, `db.migrations`, `participants`, `pao.spec`, `diag.registry`) — в журнал процесса до приёма трафика. `ready: false` — процесс не слушает порт и завершается (fail-closed); `warn` (`dev` без базы) готовность не снимает. С PS-10 `ready: false` останавливает только агентские операции (инвариант 2): режим «только `BYPASS`» — `POST /adp/v1/decide` отвечает `BYPASS` неагентским и HTTP 503 агентским (у процессинга — `ADP_UNAVAILABLE`), ПАО и П10 не регистрируются; `/health` — 200 с `mode: "bypass_only"` и кодами непрошедших проверок; при входе в режим — запись «тревога» в журнал процесса. Не разобраны среда или адрес — код выхода 1 (РП43 п. 8). Код — `buildServer({ bypassOnly })`; в `main.ts` — вместе с маршрутом ADP (SEC-1), до того `ready: false` — код выхода 1 (доп. РП43 п. 21–22). Стенд для агента самопроверку не выполняет.
- Коды витрин эмулятора продавцов — не коды Платформы, в реестры не входят.

## 4. Режимы участия эмитента

Минимум доработок банка — главный риск программы (MVP пула). Поэтому Платформа поддерживает два режима:

- **«За эмитента» (on-behalf, по умолчанию).** Процессинг вызывает ADP до передачи авторизации эмитенту. Решение Платформы по агентским условиям обязательно; финансовое решение остаётся за эмитентом. Доработка эмитента: принять и сохранить признак, показать клиенту уведомления, дать отзыв одним действием в приложении (через API П10).
- **«Сам эмитент».** Эмитент проверяет ограничения у себя, используя П3 как сервис состояния через API П10. ADP проверяет только признак, агента и мандат.

Режим задаётся на уровне эмитента в конфигурации Платформы.

## 5. Жизненный цикл бюджета (двухфазное расходование)

| Событие процессинга | Действие П3 | Норма |
|---|---|---|
| Авторизация одобрена ADP | Резерв позиции: сумма уменьшает доступный остаток, позиция помечена `RESERVED` с `auth_ref` | A3 п. 4.4 |
| Отказ эмитента после одобрения ADP | Освобождение резерва | — |
| Реверсал (отмена авторизации) | Освобождение резерва: ПИ-3 `REVERSAL` при `APPROVE` ADP без клиринга — `release` каждого удержания записи операции, запись `operation_reversals`, `REVERSED` в `GET`; частичного реверсала нет; после клиринга — инцидент без изменения (РП55 п. 1) | — |
| Истечение срока авторизации без клиринга | Освобождение по `reservation_ttl` (проход `expire`) или по ПИ-3 `AUTH_EXPIRED` — как реверсал (РП55 п. 1) | — |
| Клиринговое представление | Закрепление: `COMMITTED` по каждому удержанию записи операции (CART, родитель, клиент), запись об исполнении, `operation.settled` (РП53 п. 2–9); сумма больше одобренной — закрепляется одобренная, `EXCEEDS_AUTHORIZATION`; удержание уже освобождено — запись `NOT_RESERVED` без изменения бюджета | A1 п. 6 |
| Частичное представление | Закрепление на сумму представления, остаток резерва освобождается; одно представление на авторизацию (РП53 п. 7) | A1 п. 6.3 |
| Возврат продавцом / по спору | Возврат средств; восстановление бюджета — по `restore_budget_on_refund` (по умолчанию нет, РП9). С PS-16 ч. 3: ПИ-3 `REFUND` после клиринга — запись `operation_refunds`, `operation.refunded`, П3 не меняется; сумма больше суммы клиринга — запись и инцидент; `true` до PS-23 — отказ запуска (РП55 п. 3–4) | A4 п. 4.1; В8 |
| Отзыв мандата | Новые авторизации отклоняются; авторизованное до отзыва исполняется | A3 п. 6.3 |

Расходование неделимо: одновременные авторизации по одному мандату не могут зарезервировать одну и ту же позицию. Реализация (РП41) — удержания agentic-core: `PgHoldLedger` (`sandbox`, `dev` с базой), `AsyncMemoryHoldLedger` (`dev` без базы, стенд); условие по остатку и изменение — один оператор, своих реализаций нет. Счёт = мандат (`mandate:<id>`, предел — из записи мандата, открывается после `MANDATE_SIGNED`, при отказе — заново при первом резерве); `ref` = мандат + ключ операции. Перед резервом — статус мандата по свёртке и валюта; лимит клиента — вторым счётом после счетов мандата (РП45 п. 1). Срок резерва — `expires_at` = сейчас + `reservation_ttl_sec`; освобождает проход `expire` раз в 60 с на каждом экземпляре. Закрепление — одно на удержание, всегда с освобождением остатка; повтор распознаётся по чтению удержания; после освобождения — отказ `RESERVATION_RELEASED`, без нового резерва в обход. После отзыва новых резервов нет, закрепление и освобождение прежних — есть (A3 п. 6.3). Коды П3 — РП41 п. 5; бюджет не прочитан — `STATE_UNAVAILABLE`, резерв не создаётся (A3 п. 4.5).

**Меньшее из пределов** (A3 п. 7.2): ядро держит один предел на счёт — предел мандата; лимит клиента — **второй счёт удержаний ядра** (РП45 п. 1): клиент мандата — `(participant_code, principal_ref)` из журнала (банк — из `MANDATE_SIGNED`, у CART — корневого INTENT); счёт `client:<participant_code>:<principal_ref>:<period>:<period_start>` с пределом `{per_period, currency}` действующей записи лимитов, `ref` — `client:<participant_code>:<principal_ref>:op:<op_key>`. Порядок резервов: мандат → (у CART — родитель INTENT) → клиент; отказ любого — освобождение предыдущих. `per_operation` (→ `LIMIT_EXCEEDED`) и `merchant_categories` (→ `MANDATE_SCOPE`) — до резерва. Период — календарный `DAY`/`MONTH` в `client_limit_period_tz`; снятие `per_period` или смена вида — расширение, со следующего периода прежнего вида (лимит за период — по истории версий, РП45 доп. п. 7). Порт лимитов клиента обязателен (доп. п. 8). Записи лимитов нет — только предел мандата; не прочитана, не по форме, валюта ≠ операции — `STATE_UNAVAILABLE`. Изменение суммы `per_period` в периоде — **сразу**, `setLimit` ядра (РП46 (г)): перед резервом `account` счёта, `setLimit` — только при расхождении предела счёта с записью (обычный путь — `account` и `reserve`); расширение — сразу; сужение не ниже `committed + reserved` — сразу; ниже — предел `committed + reserved` (остаток 0 до конца периода, резерв — `LIMIT_EXCEEDED`; прошлое не отменяется, A3 п. 6.3), уже суженный до использованного счёт `setLimit` не вызывает; после освобождения удержаний предел снова приводится к записи. `LIMIT_BELOW_USED` или `ACCOUNT_CONFLICT` открытия в гонке — перечитать, не больше трёх раз, затем `STATE_UNAVAILABLE`. Остаток без резерва (`clientLeft`, путь подтверждения) — `max(0, предел записи − committed − reserved)`. Лимит инструмента по `funding_ref` — PS-14. **Остаточные риски (РП45, РП46):** ложный `LIMIT_EXCEEDED` в гонке при отказе следующего резерва (безопасная сторона); граница периода — по часам экземпляра; **устаревший `setLimit` (РП46 (г) п. 5, асимметричный):** экземпляр, прочитавший версию лимитов до фиксации следующей, может вернуть счёту прежний предел на одно решение — после расширения предел временно ниже (безопасная сторона), после **сужения одно решение может пройти сверх суженного лимита клиента**; следующее решение снова приводит предел к записи. Принят в части 2 PS-20, к пересмотру до пилота (Р-68) или подключения реального банка (Р-81) — монотонный `setLimit` с версией источника (передача ядру, `agentic-core` #38). **Уведомления клиента через банк по решениям ADP** (РП46 доп. п. 7; код — PS-20 ч. 3): формируются по сохранённым записям операций вне пути авторизации, задержка — не больше `participant_notify_max_delay_sec`; **остаточный риск:** запись решения ADP не сохранилась (РП43 доп. п. 16) — уведомления по этому решению нет; к пересмотру при подключении реального банка (Р-81). **Резерв после таймаута процессинга** (остаточный риск, РП43 п. 5): ADP ответила позже `adp_timeout_ms` — процессинг уже отклонил, а удержание создано (в том числе удержание клиента; оно же остаётся без записи в `holds`, если резерв ядра применён, а ответ потерян, или освобождение после отказа не прошло — `/audit` PS-20 № 6); оно держит бюджет и лимит клиента до `REVERSAL`/`AUTH_EXPIRED` (PS-16) или прохода `expire` — безопасная сторона. **Дописывание `MANDATE_EXHAUSTED`** при `INSUFFICIENT` на пути ADP — без ожидания (РП43 п. 9). **Стенд:** проход `expire` без таймера и без журнала процесса — его вызывает тест (как доставку событий, РП40 п. 14).

**Уведомления клиента через банк** (A3 п. 5.3; РП46 (б), доп. п. 7, 9, 10): по решениям ADP — уведомителем по сохранённым записям операций `adp_operations` **вне пути авторизации** (признаки — тем же `UPDATE` решения, новых обращений к базе в пути ADP нет); номер в ленте участника — под локом участника. Типы: `client.mandate_first_use` — первое одобрение по мандату (одно на мандат); `client.limit_declined` — отказ `LIMIT_EXCEEDED` с признаком чьего предела (`MANDATE` / `CLIENT` / `INSTRUMENT` — `amount_max` реквизита, РП49 (е); при подтверждении — `MANDATE`, если не хватает остатка мандата), одно на операцию; `client.limit_exhausted` — остаток счёта клиента стал 0 после резерва, одно на счёт периода, **не отменяется** после освобождения удержания (реверсал, отказ эмитента, срок): «лимит был исчерпан в момент X», после отмены операции у клиента снова может быть остаток, уведомления «лимит снова доступен» нет (к пересмотру при пилоте, Р-68); `client.mandate_exhausted` — в транзакции `MANDATE_EXHAUSTED`; `client.revoked_all` — после записей `revoke-all`. Задержка — не больше `participant_notify_max_delay_sec`. **Остаточные риски:** запись решения ADP не сохранилась (РП43 доп. п. 16) — уведомления по этому решению нет (Р-111; пересмотр — реальный банк, Р-81); уведомитель не работал дольше `participant_notify_horizon_sec` — уведомлений по старым решениям нет; дольше половины горизонта — признак `PARTICIPANT_NOTIFY_LAGGING` в самопроверке, журнале прохода и `/health`.

## 6. Порядок проверок ADP

Выполняется только для агентских операций (есть признак **или** использован агентский токен). Неагентские операции проходят мимо ADP без изменения времени ответа (РП4). Порядок, причины и сопоставление кодов — РП43.

0. **`BYPASS`** — `instrument.kind = CARD_TOKEN` **и** признака нет: `aoi` нет, `aoi: null` или `aoi.indicator: false` без `agent_code` и `mandate_id` (РП49 (в)): первая проверка, чистая функция над двумя полями — до реестра, журнала, П3, лимитов клиента (РП45), записи операции, идемпотентности по `op_ref`, разбора остального тела и независимо от `ready` (РП43 п. 1). Неизвестный `kind` без `aoi` — не `BYPASS`: `AOI_MISSING` и инцидент.

1. Признак: есть, полный (`indicator = true`, код агента по форме) → `AOI_MISSING`; исключение — `CARD_TOKEN` с противоречивым признаком (`indicator: false` с кодом агента или мандатом): на п. 2, `CREDENTIAL_INVALID` и счётчик (РП49 (в)). Агентский инструмент без признака — по очереди внедрения `aoi_rollout_phase` (A1 п. 8.3): 3 (песочница) → `AOI_MISSING` (ПС07); 1–2 → агент и мандат по домену токена на п. 2 (РП22 п. 6, РП48 (г)), `ACCOUNT_LINK` без признака — `CREDENTIAL_INVALID` до PS-21 (РП43 п. 2, 10).
2. Код агента в признаке совпадает с доменом токена → `AOI_MISMATCH` (инцидент). Только `AGENT_TOKEN`, до реестра: домен — из записи токена Платформы по `token_ref` (токен на CART: код агента, мандат CART, его область и срок); токена нет — `CREDENTIAL_INVALID`; `aoi.agent_code` или `aoi.mandate_id` ≠ домену — `AOI_MISMATCH`; хранилище не прочитано — `STATE_UNAVAILABLE` (РП47 п. 2, 6); `aoi` без `mandate_id` — тоже `AOI_MISMATCH` (доп. п. 5). Без признака (очередь 1–2) код агента и мандат — из домена токена, сверять не с чем; дальше п. 3–12, как с признаком (РП48 (г)). `CARD_TOKEN` с признаком — не реквизит П5 (нет домена и криптограммы): `CREDENTIAL_INVALID` и инцидент со счётчиком по паре «эквайрер + продавец» (в памяти процесса; РП48 (а)); без признака — `BYPASS` на п. 0. Противоречивый признак (`indicator: false` с кодом агента или мандатом) у `CARD_TOKEN` п. 1 не отсекает — та же ветка со счётчиком; код агента в журнал — только по форме (РП49 (в) п. 3, «Нюансы РП49» п. 3).
3. Агент в реестре, статус ACTIVE → `AGENT_UNKNOWN` (нет в реестре, `EXCLUDED`), `AGENT_SUSPENDED`.
4. Криптограмма агентского токена валидна и одноразова → `CREDENTIAL_INVALID`. Запись реквизита — по `token_ref` и SHA-256 криптограммы; нет, истёк `valid_to` (момент проверки срока — здесь), не `ISSUED`, продавец ≠ продавцу реквизита, выдан раньше последнего приостановления агента (`created_at < suspended_at`; время не разбирается — как «раньше», РП54 п. 5 и «Дополнения К1.4») — `CREDENTIAL_INVALID`. Сумма против `amount_max` — на п. 7 (РП47 доп. п. 1). Погашение `ISSUED → USED` — только у `APPROVE`, после п. 11–12 (РП47 п. 7–8).
5. Мандат: найден и принадлежит агенту (чужой = неизвестный; нет `mandate_id` → `MANDATE_NOT_FOUND`), не истёк, не отозван — по свёртке журнала → `MANDATE_NOT_FOUND` (в том числе неподписанный), `MANDATE_EXPIRED`, `MANDATE_REVOKED` (в том числе отклонённый). У `AGENT_TOKEN` мандат домена — только CART: другой тип — `STATE_UNAVAILABLE` и инцидент, сразу после чтения мандата и до статуса (нарушение целостности записей Платформы, РП49 (б)).
6. Продавец и категория (MCC) в области мандата и токена → `MANDATE_SCOPE`. Для `AGENT_TOKEN` `merchant.mcc` сообщения должен входить в набор продавца `merchant.id` из домена токена (`merchant_mcc`, записан при выпуске из справочника продавцов оператора — РП49 (д)); MCC нет, не строка или не в наборе — `MANDATE_SCOPE`; набора у токена нет (выпущен до `sql/110`), в нём нет записи продавца области или запись не по форме (набор не объект, запись не массив, набор пуст, есть не строки) — `STATE_UNAVAILABLE` и инцидент без резерва (порча записей Платформы, «Нюансы РП49» п. 7). Поверх — `merchant_categories` клиента (РП45).
7. Разовая сумма → `LIMIT_EXCEEDED`. Отдельного поля в мандате нет: условие — в резерве п. 11 (у CART — `amount_limit` CART, у клиента — `per_operation` до резерва и `per_period` вторым счётом, РП45 п. 1; у инструмента — `amount_max` реквизита после `per_operation` клиента: сумма > `amount_max` — `LIMIT_EXCEEDED`, уведомление клиенту с `reason: INSTRUMENT` (РП49 (е)); валюта реквизита = валюте CART, другую валюту отсекает п. 6 — РП47 п. 7, доп. п. 1).
8. Состояние: доступный остаток, частота; при невозможности получить состояние → отказ (A3 п. 4.5) → `STATE_UNAVAILABLE`.
9. Дробление по мандату в окне → `CONFIRMATION_REQUIRED` с `split_detected: true` (РП44 п. 1): операция не выше порога `T`, при которой в окне `split_window_sec` по ключу окна (корневой INTENT; у CART — родитель) вместе с ней не меньше `split_min_ops` операций и их сумма выше `T`. Резерва нет, остаток — чтением, как у п. 10 (меньше суммы — `LIMIT_EXCEEDED`, не прочитан — `STATE_UNAVAILABLE`). В окно входят одобрения (`APPROVE` и записи «в работе», вошедшие в окно); доля, отказы, `CONFIRMATION_REQUIRED` и одобренные по действующему `confirmation_ref` (РП50 п. 7) — нет. Сбой окна — `STATE_UNAVAILABLE` до резерва.
10. Порог подтверждения `T` = меньшее из рыночного `confirm_above_kop` и клиентского `Limits.confirm_above` (A3 п. 7.2; РП44 п. 5) → сумма > `T` — `CONFIRMATION_REQUIRED` с `split_detected: false`, если нет действующего `confirmation_ref` на эти итоговые значения; в окно п. 9 такая операция не входит. Клиентский порог — из записи лимитов клиента тем же чтением, что лимит (РП45 п. 2): не задан — рыночный; сбой, запись не по форме, валюта ≠ операции — `STATE_UNAVAILABLE` до окна дробления. Порог — в рублях: операция не в RUB — `STATE_UNAVAILABLE`. **`confirmation_ref` (РП50 п. 7–10):** проверяется до порога и окна; действует, если запись П6 `APPROVED`, в сроке и совпадает по агенту, мандату, продавцу, сумме, валюте и `order_ref` — тогда п. 9 и 10 для этой операции не применяются (окно не читается и не пополняется), остальные проверки и резервы — как без подтверждения. Не действует (неизвестна, другие значения — инцидент, истекла, отклонена, использована, запрос создан раньше последнего приостановления агента — `created_at < suspended_at`, без инцидента, РП54 п. 6) — не учитывается, выше порога — `CONFIRMATION_REQUIRED`; сбой чтения П6 — `STATE_UNAVAILABLE`. На `CONFIRMATION_REQUIRED` ADP создаёт запрос подтверждения (SPEC §3 П6; без `order_ref` — без запроса); сбой записи — `STATE_UNAVAILABLE`. Погашение — после резерва и сверки статуса, до погашения реквизита, условной записью `APPROVED → USED` с `op_ref`: не прошло — освобождение и `CONFIRMATION_REQUIRED` с `split_detected: false`, сбой — освобождение и `STATE_UNAVAILABLE`. Ссылка без `order_ref` в сообщении не учитывается (без инцидента); повтор со ссылкой — с новым `op_ref` (Дополнения РП50 п. 2, 5, 7).
11. Резерв позиции (`op_key` = `op_ref`): мандат, у CART — родитель, затем счёт лимита клиента (РП45 п. 1) → `APPROVE` с `reservation_id` = `hold.id` мандата; удержание клиента — в записи операции. Коды П3 → ПИ — РП43 п. 3. Затем у `AGENT_TOKEN` — погашение криптограммы условной записью `ISSUED → USED` с `op_ref` после п. 12: не прошло (погашена другой авторизацией) — освобождение удержаний и `CREDENTIAL_INVALID`, сбой записи — освобождение и `STATE_UNAVAILABLE` (РП47 п. 8).
12. Сверка статуса мандата после резерва: не `ACTIVE` — освобождение и отказ по статусу; сбой чтения — освобождение и `STATE_UNAVAILABLE`. Момент авторизации для A3 п. 6.3 — это второе чтение (РП43 п. 5).

**CART** — два резерва с одним `op_ref`: счёт CART, затем счёт родителя INTENT; отказ второго — освобождение первого, причина второго (РП43 п. 6). CART без родителя в журнале или родитель не прочитан — `STATE_UNAVAILABLE`; `reservation_id` — удержание CART, `mandate_left_after` и `verify.amount_left` у CART — меньшее из остатков CART и родителя (родитель не прочитан — `STATE_UNKNOWN`).

**Состояние не подтверждено** (журнал, реестр или П3 не прочитаны, нарушенная цепочка, `ACCOUNT_CONFLICT`, неизвестная ошибка ядра) → `DECLINE` / `STATE_UNAVAILABLE`, резерв не создаётся; `BYPASS` по состоянию хранилищ запрещён (РП43 п. 4, решение владельца). Проверка, чей сервис ещё не подключён, — тоже «не подтверждено»: `ACCOUNT_LINK` до PS-21 → `CREDENTIAL_INVALID` (`AGENT_TOKEN` — с PS-14, РП47); `confirmation_ref` — с PS-19 (РП50); сбой П6 — `STATE_UNAVAILABLE`.

**Идемпотентность по `op_ref`:** до резерва атомарно создаётся запись операции «в работе» — к резерву проходит только первый запрос; чужая запись «в работе» — `STATE_UNAVAILABLE` без резерва. Повтор с тем же сообщением (канонический JSON без `ts` и `seq`) — прежнее решение; у `APPROVE` — чтением удержания, не повторным резервом (освобождённое без закрепления — `STATE_UNAVAILABLE`); с другим — `STATE_UNAVAILABLE` и инцидент. Хранятся все решения, кроме `BYPASS` (РП43 п. 5, доп. п. 16–18).

**Уточнения порядка (доп. РП43 п. 12–15, 19–20):** `aoi: null` — отсутствие признака; неизвестный `kind` при `aoi` — `CREDENTIAL_INVALID` и инцидент; до PS-14 `AGENT_TOKEN`/`ACCOUNT_LINK` с `aoi` — `CREDENTIAL_INVALID` на месте п. 2, до реестра (с PS-14 — только `ACCOUNT_LINK`, до PS-21; `AGENT_TOKEN` — п. 2 и 4 на своих местах, РП47); сумма > `confirm_above_kop` — без резерва: остаток чтением (меньше суммы — `LIMIT_EXCEEDED`, не прочитан — `STATE_UNAVAILABLE`, иначе `CONFIRMATION_REQUIRED`); статус и тип мандата вне перечня — `STATE_UNAVAILABLE`; некорректное агентское сообщение — 400 (у процессинга `ADP_UNAVAILABLE`), неагентское — `BYPASS`.

При расхождении ограничений инструмента и пределов мандата применяется меньшее значение (A3 п. 7.2).

**Окно дробления (РП44 п. 4):** столбцы окна в записи операции `adp_operations` (`window_key`, `amount`, `currency`, `window_at_ms`); вход — на PostgreSQL транзакцией под `pg_advisory_xact_lock` ключа окна (чтение числа и суммы после блокировки, запись своей строки, `COMMIT`), резерв ядра — после `COMMIT`; ожидание блокировки — не дольше `adp_timeout_ms` (`lock_timeout`), превышение — `STATE_UNAVAILABLE` без входа в окно и без резерва; в памяти — без `await` между проверкой и записью, входы старше окна удаляются. Часы — Платформы. **Порядок вычисления:** порог `T` (п. 10) вычисляется до правила доли (п. 9) — правилу нужен `T`; исход тот же (доп. РП44 п. 2). **Остаточные риски (РП44):** дробление по разным INTENT одного клиента не выявляется (сумму ограничивает лимит клиента `per_period`, РП45; антифрод — PS-25); возврат и `REVERSAL` окно не уменьшают; расхождение часов экземпляров сдвигает окно; запись «в работе» после сбоя считается до конца окна; при `split_min_ops = 2` возможны ложные подтверждения честных покупок — параметры уточнит пилот (O19); до PS-19 долю нельзя подтвердить — вторая покупка в окне не пройдёт до истечения окна.

**Отказ в пользу безопасности.** Если ADP не ответила за `adp_timeout_ms`, процессинг отклоняет **агентскую** операцию с кодом «агентская проверка недоступна». Неагентские операции работают как обычно.

## 8. Нефункциональные требования

- **Доступность** пути ADP — не ниже нормативов процессинга; цель песочницы — `adp_availability_target`. Отказ ADP не влияет на неагентские операции.
- **Задержка** ADP p99 ≤ `adp_p99_ms`, таймаут процессинга `adp_timeout_ms`.
- **Идемпотентность** по идентификаторам процессинга (уникальная ссылка операции, повтор сообщения) и по `Idempotency-Key` в ПАО.
- **Криптография.** В песочнице — ed25519; в контуре оператора — ГОСТ Р 34.10-2012 / 34.11-2012 через сертифицированное СКЗИ, ключи в HSM. Протокол не привязан к алгоритму: `alg` указан у ключа (РП5). Модель угроз, ключи Платформы, mTLS и аутентификация операторов — [`SECURITY.md`](SECURITY.md) (РП26–РП28).
- **Защита информации:** ГОСТ Р 57580.1-2017, положение 719-П; персональные данные — 152-ФЗ, локализация. В реестре нет сведений о принципалах; в журнале согласий принципал — ссылкой.
- **Неизменяемость журнала** — хэш-цепочка, проверка целостности по расписанию и по запросу.
- **Готовность при старте** — отчёт самопроверки по РП42; не готов — трафик не принимается.
- **Записи Fastify о запросе — без значений параметров пути (РП61):** на всех маршрутах сервера — `method` и шаблон маршрута `route` (`/pao/v1/mandates/:id`), без `url`, значений параметров пути и строки запроса; маршрут не найден — без шаблона. Собственные записи маршрутов — по своим решениям: `kid` — только при `FOREIGN` и `UNKNOWN` (РП60 доп. 3); `mandate_id`, `confirmation_id`, `merchant_id` — только после маски идентификатора, никогда сырое из пути (РП61 нюанс 3). Уровень журнала рабочего сервера — не ниже `info` (РП61 нюанс 1). Отказы 414 и 400 bad url до маршрутизации в журнал пока не пишутся — запись без пути, с кодом и размером запроса — PS-05б ч. 3. Предупреждения Fastify об ошибках кода с сырым адресом — риск до пилота с банком (РП61 нюанс 1).
- **Наблюдаемость** — метрики ADP по кодам решений, доля ложных отказов агентских операций, время распространения отзыва, нагрузка на П2 и П3.
- **Среды:** dev (всё в памяти; с `DATABASE_URL` — хранилища шлюза ПАО на PostgreSQL) → sandbox (PostgreSQL, эмуляторы процессинга и банков; без `DATABASE_URL` не запускается, РП30) → интеграционная (форматы ОПКЦ) → пилот (два банка). Коды и мандаты сред не пересекаются. До песочницы агент проверяет подпись против стенда Платформы в своём тесте (`agentic-ps-platform/stand`, РП25): среда dev, контур ключей sandbox; стенд — тестовый интерфейс, не контракт, и приёмку не заменяет (§11 п. 6). Сочетание среды dev с контуром ключей sandbox в стенде — исключение из правила «коды и мандаты сред не пересекаются»: стенд живёт в памяти процесса теста и вне приёмки.

## 9. Что эмулируется в репозитории

Реального доступа к процессингу нет, поэтому в репозитории есть эмуляторы окружения (`src/env/`):
- **ОПКЦ:** маршрутизация авторизации, вызов ADP, ответ эмитента, реверсал, клиринговое представление;
- **эмитент** (два банка, режимы «за эмитента» и «сам»), включая приложение клиента для подписи мандата и подтверждения;
- **эквайрер и продавцы** (витрины из пула, включая недобросовестные; PS-12). Адреса витрин — К6 пула с префиксом версии `/v1`: `GET /v1/shops`, `GET /v1/shops/{id}/catalog`, `POST /v1/shops/{id}/orders`; сверх К6 — `POST /v1/shops/{id}/orders/{order_id}/payment`: приём пакета агентской оплаты `PaymentPackage` (РП22 п. 5), которого в К6 нет. Подпись агента витрина проверяет по каталогу ключей агентов (РП22 п. 8) на всех адресах, включая список `GET /v1/shops` (#49, РП56 п. 6: без подписи — человек, список отдаётся; подпись не прошла — код `MERCHANT_ERROR_CODES`; каталог ключей недоступен — 503); отказ списка задаётся из теста (`failShopList`: 503 `UPSTREAM_UNAVAILABLE` или 429 `RATE_LIMITED` с `Retry-After`). Сверх К6 по РП58 (#62): чтение заказа подписанным агентом — `GET /v1/shops/{id}/orders?cart_mandate_id=…` (`{orders}` — только свои заказы, пусто — 200) и `GET /v1/shops/{id}/orders/{order_id}` (чужой или нет — 404 `ORDER_NOT_FOUND`), без `cart_mandate_id` — 422 `QUERY_INVALID`; обрыв ответа на `POST …/orders` после записи заказа — из теста (`failOrderReply`: `RESET` или `GARBLED`). Состояние при чтении — текущее: `PAYING` — оплата идёт (`payment: null`), читать снова; `CREATED` после `PAYING` — авторизация не ушла (сбой эквайрера), заказ можно оплатить. `POST …/orders` неидемпотентен: после обрыва — сначала чтение по `cart_mandate_id`; повтор `POST` создаёт новый заказ и только с новой подписью и новым nonce (nonce оборванного запроса израсходован — повтор с ним 401 `SIGNATURE_INVALID`). Факты модели каталога (РП58, #45): у магазина — `inn`, `mcc`, `payment_methods`, `delivery_regions`, `returns {days, text}`; у товара — `delivery_options` (стоимость парой с валютой), `updated_at` (часы стенда минус возраст карточки), `gtin`, `brand`, `model`, `attributes`; в ответе каталога — `responded_at` по часам стенда; SHOP-5501 неполна и по ним (A5 п. 1.1). Эквайрер переносит `aoi` или работает без его поддержки (РП22 п. 6); порт ОПКЦ — заглушка до PS-11. Эмулятор — не контракт Платформы (инвариант 10);
- **СБП** (C2B по привязке счёта, возврат);
- **УПК** (платёжная страница с выбором инструмента);
- **токен-сервис**.

Эмуляторы живут в репозитории Платформы и поднимаются в песочнице. BuyerAgent работает против песочницы через ПАО.

## 10. Вне задания

Условное исполнение (эскроу) как механизм Платформы — платформа его не исполняет; интерфейс для внешних поставщиков — `CONDITIONAL-EXECUTION.md` (РП13). Трансграничные сценарии и признание внешних реестров (A9) — модель данных готовится, исполнение позже. Оценка исполнения как основание изменения уровня — после накопления данных.

## 11. Критерии приёмки

1. Все сценарии ПС01–ПС28 проходят в песочнице; отрицательные — с ожидаемыми кодами.
2. Ни один сценарий не пройден обходом нормы.
3. Неагентские операции в нагрузочном прогоне не изменили время ответа сверх `bypass_overhead_ms`.
4. ADP укладывается в `adp_p99_ms` на профиле нагрузки из `PARAMS.md`.
5. Конкурентный тест: N одновременных авторизаций по одному мандату не превышают бюджет ни на копейку.
6. BuyerAgent проходит свои 30 сценариев против песочницы Платформы по ПАО той же версии.
7. Сканер не находит реквизитов и ключей в журналах.
