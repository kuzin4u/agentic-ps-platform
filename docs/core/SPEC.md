# ТЗ: агентная платформа платёжной системы

Редакция 1 · 08.10.2026 · основание: пул «Агентная коммерция» (файлы 07–14, 20–23, 29–31, 35–37), драфты A1–A9, решения РП1–РП17.

## 1. Назначение

Агентная платформа платёжной системы (далее — **Платформа**) — сервисный слой оператора платёжной системы, который делает агентную операцию **видимой, ограниченной и разбираемой** на действующих рельсах: карты «Мир», СБП, универсальный платёжный код.

Платформа не торгует, не выбирает товар и не заменяет банк. Её предмет:
- кто такой агент (реестр, ключи);
- что ему поручено (мандаты, журнал согласий);
- в каких пределах он действует (состояние бюджета);
- как это проверяется в момент авторизации (точка решения в процессинге);
- как это разбирается при споре (вычисление `in_scope`).

У Платформы две внешние границы:
1. **Интерфейс с процессингом (ОПКЦ)** и смежными системами оператора: СБП, токен-сервис, УПК, антифрод, отчётность. Описан в `PROCESSING-INTERFACE.md`.
2. **Протокол агентских операций (ПАО)** — интерфейс для агентов покупателя, в первую очередь BuyerAgent. Описан в `AGENT-PROTOCOL.md` и `agent-protocol.yaml`.

Плюс интерфейс для банков-участников (эмитент, эквайрер) — в `PROCESSING-INTERFACE.md`, раздел «Участники».

## 2. Главный архитектурный принцип

**Агент не инициирует авторизацию в платёжной системе.** Платёж, как и сегодня, инициирует продавец через эквайрера, а процессинг доводит его до эмитента.

Платформа встраивается в этот путь в двух местах:
- **до операции** агент получает от Платформы *агентский платёжный реквизит*: агентский токен с одноразовой криптограммой для карт или привязку счёта для СБП. Реквизит привязан к коду агента, мандату и области продавцов. Агент передаёт его продавцу вместе с признаком операции, номера карты он не видит;
- **в момент авторизации** процессинг синхронно обращается к *точке решения* Платформы (ADP — agentic decision point). Она проверяет признак, агента, мандат и бюджет, резервирует позицию бюджета и возвращает решение.

Метод `/v1/pay/authorize`, которым агент в испытательном контуре пула вызывал шлюз напрямую, — упрощение для испытаний. В Платформе он сохраняется только в песочнице как эмуляция цепочки «продавец → эквайрер → процессинг» (РП2).

### Реестр (П1): код, допуск, статус, ключи (РП21, РП23, РП27, РП28)

- **Код агента** — части через `:`, каждая `[a-z0-9-]+`: последняя — версия `v<N>` (N ≥ 1), предпоследняя — идентификатор, остальные — выдавшая сторона. `nspk:agent:buyref-01:v3` — сторона `nspk:agent`, идентификатор `buyref-01`, версия 3. Выдавшая сторона — только `nspk:agent`: код присваивается при допуске, операторы агентов коды не выдают; другая сторона — `CODE_INVALID` (РП23). Код неизменен; существенное изменение — новая версия, новая запись (A2 п. 4.1–4.2).
- **Основания отказа в допуске** (закрытый перечень): `APPLICATION_INCOMPLETE`, `CLASS_UNKNOWN`, `CODE_INVALID`, `CODE_TAKEN`, `PRINCIPAL_DATA`, `CONFORMANCE_MISSING`, `AGENT_CARD_MISMATCH`, `KEY_INVALID` (РП23). Заявление, не попадающее ни под одно, допускается (A6 п. 2.1). Учитываются только поля `agent_code`, `class`, `model`, `runtime`, `conformance_run_ref`, `agent_card`, `alg`, `public_key`; оператор — из контекста вызова, не из заявления: контекст создаёт только аутентификация оператора по его сертификату mTLS (РП28; код — PS-31).
- **Уровень** — целое ≥ 1, при допуске — 1; изменяет П8 по оценке исполнения.
- **Статус:** ACTIVE → SUSPENDED — с основанием A2 п. 7.1 (`KEY_COMPROMISE`, `OUT_OF_MANDATE`, `FALSE_INFORMATION`, `INCIDENT_EVASION`); SUSPENDED → ACTIVE — без основания; EXCLUDED — из любого статуса, с тем же основанием или `WITHDRAWN`; из EXCLUDED выхода нет.
- **Ключи (РП23):** первый ключ — в заявлении (`alg`, `public_key` — DER SPKI, каноническая запись base64 по RFC 4648 §3.5; иная запись — `KEY_INVALID`, РП23 доп. 6), пару генерирует оператор агента; запись и ключ сохраняются вместе или не сохраняются. `kid` присваивает Платформа — отпечаток JWK по RFC 7638, глобально уникален; повтор ключа — `KEY_INVALID`. `valid_to = valid_from + key_ttl_days`; новый ключ сокращает срок остальных действующих до `now + key_overlap_days`; наступил `valid_to` — `EXPIRED`. Отзыв любого ключа, включая последний, необратим и действует со следующей проверки подписи; повторный отзыв возвращает тот же ключ. Слабый ключ Ed25519 (неканоническая запись точки, точка малого порядка) — `KEY_INVALID`. Исключённому агенту новый ключ не регистрируется, приостановленному — можно; проверка статуса неделима с добавлением ключа (РП23, дополнения).
- **Сертификат mTLS агента (РП27):** ключ генерирует оператор агента, Платформа получает CSR; сертификат УЦ песочницы выдаётся в решении о допуске, код агента — в SAN URI `urn:nspk:agent:<id>:v<N>`; отзывается только при компрометации ключа сертификата (приостановление и исключение режет статус). Стенд dev — без mTLS.
- **Проверка обращения ПАО (РП23, РП27):** сертификата нет, он не УЦ песочницы или его код агента не равен `x-agent-code` — `AGENT_UNKNOWN`, истёк или отозван — `AGENT_KEY_REVOKED` (ступень 0, РП27; код — PS-05) → агента нет — `AGENT_UNKNOWN` → подпись ключами только агента из `x-agent-code` (`SIGNATURE_INVALID`; отозванный или истёкший ключ — `AGENT_KEY_REVOKED`; nonce проверяется и запоминается одной операцией после успешной проверки подписи, РП30) → статус (`SUSPENDED`, `EXCLUDED` — `AGENT_SUSPENDED`, кроме `GET /pao/v1/agent`). Сбой реестра, ключей или хранилища nonce на любой ступени — `UPSTREAM_UNAVAILABLE` (503, `Retry-After` по РП24), обращение не принимается (РП23, дополнения; РП30). После проверки обращения, до обработчика изменяющего метода: нет `Idempotency-Key` — `IDEMPOTENCY_REQUIRED`; тело не по схеме метода (не JSON, нет обязательного поля, неверный тип, значение вне перечня) — `REQUEST_INVALID` (400, `after_fix`, ПАО 1.3.0), до захвата ключа идемпотентности: неполный запрос ключ не занимает; в `message` нет фрагментов присланного тела (РП31). Тело ошибки — ПАО §6 как есть.
- **Хранилища шлюза ПАО (РП30):** nonce и идемпотентность — хранилища agentic-core на PostgreSQL. Nonce — одна область `pao`, значение `<agent_code> <x-nonce>` (разбор по первому пробелу), срок — 2 × `signature_skew_sec`, очистка раз в `signature_skew_sec`. Идемпотентность изменяющих методов — область `pao:<agent_code>`, ключ `Idempotency-Key`, хэш от метода, пути, запроса и тела; сохраняется ответ обработчика (2xx, 4xx), сбой (5xx) — нет; срок — `idempotency_ttl_sec`, аренда захвата — 60 с. Без ключа — `IDEMPOTENCY_REQUIRED`, другое тело или путь — `IDEMPOTENCY_CONFLICT`, тот же ключ ещё выполняется или сбой хранилища — `UPSTREAM_UNAVAILABLE` до обработчика. Без базы: `sandbox` не запускается; `dev` и стенд для агента — хранилища ядра в памяти (один процесс).

### Продавцы и площадки (П10): каталог ключей агентов, пакет оплаты (РП22)

- **Каталог ключей агентов** — JWKS (RFC 7517). Ключ — JWK по RFC 8037: `kty: OKP`, `crv: Ed25519`, `x`, `alg: EdDSA`, `use: sig`; `kid` — тот же отпечаток RFC 7638, что `Key.kid` ПАО. Частные члены: `agent_code`, `nbf`, `exp` (секунды Unix, `nbf` = `valid_from`, `exp` = `valid_to`). В каталоге только действующие ключи агентов в статусе `ACTIVE`; отозванный, истёкший ключ и ключи приостановленного или исключённого агента удаляются (РП22 п. 1–2). Каталог строит одна функция реестра (П1): её используют эмулятор продавцов (PS-12) и HTTP-адрес каталога (PS-30).
- **Проверка у продавца:** подпись RFC 9421 по ключу из каталога; `agent_code` ключа ≠ `x-agent-code` или истёкший `exp` — отказ; неизвестный `kid` — одно перечитывание не чаще раза в `merchant_jwks_refetch_min_sec`, затем отказ (РП22 п. 2–3). Отзыв доходит до продавца не дольше чем за `merchant_jwks_max_age_sec`; отказ в авторизации всё равно даёт ADP.
- **Пакет агентской оплаты** — `PaymentPackage` (ПАО §4): `credential_ref`, `kind`, `payload`, `aoi`, `cart_mandate_id`, `order_ref`, подпись агента. Суммы в пакете нет: сумма — только из сообщения процессинга (инвариант 5, РП22 п. 5).
- **Эквайрер без поддержки `aoi`** (РП22 п. 6): операция с инструментом `AGENT_TOKEN` или `ACCOUNT_LINK` остаётся агентской, ADP определяет агента и мандат по домену токена (ФП4); метаданные пакета от продавца — только для сверки по `credential_ref` и отчётности, решение ADP от них не зависит.

## 4. Режимы участия эмитента

Минимум доработок банка — главный риск программы (MVP пула). Поэтому Платформа поддерживает два режима:

- **«За эмитента» (on-behalf, по умолчанию).** Процессинг вызывает ADP до передачи авторизации эмитенту. Решение Платформы по агентским условиям обязательно; финансовое решение остаётся за эмитентом. Доработка эмитента: принять и сохранить признак, показать клиенту уведомления, дать отзыв одним действием в приложении (через API П10).
- **«Сам эмитент».** Эмитент проверяет ограничения у себя, используя П3 как сервис состояния через API П10. ADP проверяет только признак, агента и мандат.

Режим задаётся на уровне эмитента в конфигурации Платформы.

## 5. Жизненный цикл бюджета (двухфазное расходование)

| Событие процессинга | Действие П3 | Норма |
|---|---|---|
| Авторизация одобрена ADP | Резерв позиции: сумма уменьшает доступный остаток, позиция помечена `RESERVED` с `auth_ref` | A3 п. 4.4 |
| Отказ эмитента после одобрения ADP | Освобождение резерва | — |
| Реверсал (отмена авторизации) | Освобождение резерва | — |
| Истечение срока авторизации без клиринга | Освобождение по `reservation_ttl` | — |
| Клиринговое представление | Закрепление: `COMMITTED`, запись об исполнении | A1 п. 6 |
| Частичное представление | Закрепление на сумму представления, остаток резерва освобождается | A1 п. 6.3 |
| Возврат продавцом / по спору | Возврат средств; восстановление бюджета — по `restore_budget_on_refund` (по умолчанию нет, РП9) | A4 п. 4.1; В8 |
| Отзыв мандата | Новые авторизации отклоняются; авторизованное до отзыва исполняется | A3 п. 6.3 |

Расходование неделимо: одновременные авторизации по одному мандату не могут зарезервировать одну и ту же позицию. Реализация — атомарная операция над записью состояния мандата (блокировка строки или условное обновление с версией).

## 6. Порядок проверок ADP

Выполняется только для агентских операций (есть признак **или** использован агентский токен). Неагентские операции проходят мимо ADP без изменения времени ответа (РП4).

1. Признак: есть, полный → `AOI_MISSING`. Агентский токен без признака → `AOI_MISSING`.
2. Код агента в признаке совпадает с доменом токена → `AOI_MISMATCH` (инцидент).
3. Агент в реестре, статус ACTIVE → `AGENT_UNKNOWN`, `AGENT_SUSPENDED`.
4. Криптограмма агентского токена валидна и одноразова → `CREDENTIAL_INVALID`.
5. Мандат: найден, не истёк, не отозван → `MANDATE_NOT_FOUND`, `MANDATE_EXPIRED`, `MANDATE_REVOKED`.
6. Продавец и категория (MCC) в области мандата и токена → `MANDATE_SCOPE`.
7. Разовая сумма → `LIMIT_EXCEEDED`.
8. Состояние: доступный остаток, частота; при невозможности получить состояние → отказ (A3 п. 4.5) → `STATE_UNAVAILABLE`.
9. Дробление по мандату в окне → `CONFIRMATION_REQUIRED` с отметкой «дробление».
10. Порог подтверждения (меньшее из рыночного порога и клиентского) → `CONFIRMATION_REQUIRED`, если нет действующего `confirmation_ref` на эти итоговые значения.
11. Резерв позиции → `APPROVE` с `reservation_id`.

При расхождении ограничений инструмента и пределов мандата применяется меньшее значение (A3 п. 7.2).

**Отказ в пользу безопасности.** Если ADP не ответила за `adp_timeout_ms`, процессинг отклоняет **агентскую** операцию с кодом «агентская проверка недоступна». Неагентские операции работают как обычно.

| ФП13 | События агенту (отзыв, приостановление, результат подтверждения, статус операции) подписаны Платформой; доставка с повтором, идемпотентна | П9 | ПС23 |

## 8. Нефункциональные требования

- **Доступность** пути ADP — не ниже нормативов процессинга; цель песочницы — `adp_availability_target`. Отказ ADP не влияет на неагентские операции.
- **Задержка** ADP p99 ≤ `adp_p99_ms`, таймаут процессинга `adp_timeout_ms`.
- **Идемпотентность** по идентификаторам процессинга (уникальная ссылка операции, повтор сообщения) и по `Idempotency-Key` в ПАО.
- **Криптография.** В песочнице — ed25519; в контуре оператора — ГОСТ Р 34.10-2012 / 34.11-2012 через сертифицированное СКЗИ, ключи в HSM. Протокол не привязан к алгоритму: `alg` указан у ключа (РП5). Модель угроз, ключи Платформы, mTLS и аутентификация операторов — [`SECURITY.md`](SECURITY.md) (РП26–РП28).
- **Защита информации:** ГОСТ Р 57580.1-2017, положение 719-П; персональные данные — 152-ФЗ, локализация. В реестре нет сведений о принципалах; в журнале согласий принципал — ссылкой.
- **Неизменяемость журнала** — хэш-цепочка, проверка целостности по расписанию и по запросу.
- **Наблюдаемость** — метрики ADP по кодам решений, доля ложных отказов агентских операций, время распространения отзыва, нагрузка на П2 и П3.
- **Среды:** dev (всё в памяти; с `DATABASE_URL` — хранилища шлюза ПАО на PostgreSQL) → sandbox (PostgreSQL, эмуляторы процессинга и банков; без `DATABASE_URL` не запускается, РП30) → интеграционная (форматы ОПКЦ) → пилот (два банка). Коды и мандаты сред не пересекаются. До песочницы агент проверяет подпись против стенда Платформы в своём тесте (`agentic-ps-platform/stand`, РП25): среда dev, контур ключей sandbox; стенд — тестовый интерфейс, не контракт, и приёмку не заменяет (§11 п. 6). Сочетание среды dev с контуром ключей sandbox в стенде — исключение из правила «коды и мандаты сред не пересекаются»: стенд живёт в памяти процесса теста и вне приёмки.

## 9. Что эмулируется в репозитории

Реального доступа к процессингу нет, поэтому в репозитории есть эмуляторы окружения (`src/env/`):
- **ОПКЦ:** маршрутизация авторизации, вызов ADP, ответ эмитента, реверсал, клиринговое представление;
- **эмитент** (два банка, режимы «за эмитента» и «сам»), включая приложение клиента для подписи мандата и подтверждения;
- **эквайрер и продавцы** (витрины из пула, включая недобросовестные; PS-12). Адреса витрин — К6 пула с префиксом версии `/v1`: `GET /v1/shops`, `GET /v1/shops/{id}/catalog`, `POST /v1/shops/{id}/orders`; сверх К6 — `POST /v1/shops/{id}/orders/{order_id}/payment`: приём пакета агентской оплаты `PaymentPackage` (РП22 п. 5), которого в К6 нет. Подпись агента витрина проверяет по каталогу ключей агентов (РП22 п. 8). Эквайрер переносит `aoi` или работает без его поддержки (РП22 п. 6); порт ОПКЦ — заглушка до PS-11. Эмулятор — не контракт Платформы (инвариант 10);
- **СБП** (C2B по привязке счёта, возврат);
- **УПК** (платёжная страница с выбором инструмента);
- **токен-сервис**.

Эмуляторы живут в репозитории Платформы и поднимаются в песочнице. BuyerAgent работает против песочницы через ПАО.

## 10. Вне задания

Условное исполнение (эскроу) как механизм Платформы — платформа его не исполняет; интерфейс для внешних поставщиков — `CONDITIONAL-EXECUTION.md` (РП13). Трансграничные сценарии и признание внешних реестров (A9) — модель данных готовится, исполнение позже. Оценка исполнения как основание изменения уровня — после накопления данных.

## 11. Критерии приёмки

1. Все сценарии ПС01–ПС28 проходят в песочнице; отрицательные — с ожидаемыми кодами.
2. Ни один сценарий не пройден обходом нормы.
3. Неагентские операции в нагрузочном прогоне не изменили время ответа сверх `bypass_overhead_ms`.
4. ADP укладывается в `adp_p99_ms` на профиле нагрузки из `PARAMS.md`.
5. Конкурентный тест: N одновременных авторизаций по одному мандату не превышают бюджет ни на копейку.
6. BuyerAgent проходит свои 30 сценариев против песочницы Платформы по ПАО той же версии.
7. Сканер не находит реквизитов и ключей в журналах.
