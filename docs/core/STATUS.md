## Передача агенту (AG-03 Подписант)

Строки для первой сессии агента (AG-01…AG-03): переносятся в `../agentic-buyer-ref` там, а не из платформы; источник — РП23, РП24.
- Код агента — только `nspk:agent:<id>:v<N>`: оператор указывает его в заявлении, реестр выдаёт решением о допуске.
- `kid` — отпечаток JWK открытого ключа по RFC 7638 (`{"crv","kty","x"}`, SHA-256, base64url без дополнения); агент вычисляет сам, не выдумывает. Эталон — RFC 8037 прил. A.3.
- `public_key` — DER SubjectPublicKeyInfo в канонической записи base64 (RFC 4648 §3.5; как `newEd25519Signer` из agentic-core); лишние биты перед «=», без дополнения, пробелы, base64url — `KEY_INVALID` (РП23 доп. 6; расхождение № 8 агента). Пару генерирует оператор агента.
- Слабые ключи Ed25519 (точки малого порядка, неканоническая запись) — `KEY_INVALID` при допуске и регистрации.
- **Тег `v0.1.1`** (после слияния задачи PS-key-b64, ставит владелец) — `v0.1.0` + каноническая запись `public_key`; в 3d подключать его: `git+https://github.com/kuzin4u/agentic-ps-platform.git#v0.1.1`. Интерфейс стенда не менялся.
- `Retry-After` у ответов 503 — не больше 30 с (= `maxRetryAfterSec` клиента core, РП24).
- `GET /pao/v1/agent` подписывается с `content-digest` пустого тела (РП16); отвечает и приостановленному агенту.
- **SEC-1 (РП26, РП27; код — PS-05, PS-08, ПАО 1.3.0):** ключ сертификата mTLS генерирует оператор агента и передаёт CSR; сертификат — в решении о допуске, код агента в SAN URI `urn:nspk:agent:<id>:v<N>`; код из сертификата ≠ `x-agent-code` — `AGENT_UNKNOWN`, истёкший или отозванный сертификат — `AGENT_KEY_REVOKED`. Ответы и события Платформы подписаны по RFC 9421 (метка `platform`, `created`, ответ привязан к запросу через `;req`); ключи — в `platform_keys` `/.well-known/pao-configuration`, проверять `use`; неизвестный `kid` — одно перечитывание, затем отказ. Проверка — `verifyResponse` agentic-core (задача к CO). В копии ПАО 1.2 агента `Platform-Signature` остаётся до 1.3.0. До переезда хранилища перезапуск песочницы = повторный допуск агента (SECURITY.md §6).

**Стенд для С0 (AG-03 3d, РП25)** — задача PS-stand, готово в PR #23 (CI зелёный), ждёт слияния и тега `v0.1.0`:
- зависимость: `"agentic-ps-platform": "git+https://github.com/kuzin4u/agentic-ps-platform.git#v0.1.0"` в devDependencies; `dist` собирается при установке (`prepare`);
- `import { createStand } from "agentic-ps-platform/stand"`; `createStand()` → `admit(application, operator)` (контур sandbox, РП21/РП23), `listen()` → базовый адрес, `close()`, `setClock(d)`; поля `params`, `registry`, `keys`, `app`;
- среда dev в процессе теста агента, контур ключей sandbox (ed25519); песочницей не является, приёмку не заменяет; параметры — `config/params.stand.json` Платформы, `config/` агента не читается;
- стенд — тестовый интерфейс, не контракт: сигнатура может меняться между тегами, изменения — здесь.


## Заделы к задачам

По аудитам PS-04 (решение владельца 11.10.2026).

**К PS-05 (шлюз ПАО: основа):**
- первый аудит №5 — повторённые подписываемые заголовки по HTTP (Node склеивает их через «, »): `headersDistinct`, отказ при повторе;
- №6 — GET с непустым телом проверяется по digest пустого тела: `content-length > 0` или `transfer-encoding` у запроса без тела — `SIGNATURE_INVALID`;
- №7 — digest от байтов, а не от строки UTF-8: `parseAs: "buffer"`;
- №8 — ответы Fastify (404, 413, 415, 500) не по ПАО §6: обработчики ошибок и «не найдено» в области `/pao`, вместе с решением о RFC 9457;
- №9 — неканонический путь (`/pao/v1/%61gent`) и автоматический `HEAD`: отказ при сыром пути ≠ нормализованному, `exposeHeadRoutes: false`;
- №12 — проверка агента и заголовков в `onRequest`, меньший `bodyLimit` в `/pao`;
- ограничение частоты в два слоя (CodeQL `js/missing-rate-limiting`, `src/pao/routes.ts:35`, PR #21 — в GitHub не отклонять, закрывается в PS-05):
  - грубый лимит по адресу **до** проверки подписи — для неподписанного потока; вместе с №12 (проверка до чтения тела);
  - лимит по уровню агента **после** проверки — `RATE_LIMITED` (429, `Retry-After`, ПАО §2); значения по уровням — `/decision`.
- повторный аудит №5 — `isWeakEd25519` на BigInt ≈ 2,7 мс на ключ: до открытия `POST /pao/v1/agent/keys` — сравнение с 8 каноническими кодировками малого порядка;
- повторный аудит №7 — `/decision`: общие ответы 401/429/503 у путей `agent-protocol.yaml` (совместимо, в составе ПАО 1.3.0 — РП26 п. 8).
- аудит PS-key-b64 №4 — `/decision`: каноническая запись base64 `public_key` (РП23 доп. 6) — описательно в AGENT-PROTOCOL §2 и `description` у `Key.public_key` вместе с `POST /pao/v1/agent/keys` (совместимо, в составе ПАО 1.3.0 — РП26 п. 8).

- SEC-1, РП27 — TLS шлюза ПАО, УЦ песочницы (ECDSA P-256), выпуск сертификата агента по CSR при допуске, ступень 0 проверки (сертификат ↔ `x-agent-code` → `AGENT_UNKNOWN`, истёкший или отозванный → `AGENT_KEY_REVOKED`, сбой списка отзыва → 503), `requestCert` без обрыва рукопожатия, грубый лимит до ступени 0, `/.well-known` и `/health` без сертификата; список отзыва; ключ УЦ и ключи Платформы — в хранилище реестра; ПС01 `it.todo` «сертификат mTLS»;
- SEC-1, РП26 — ключи Платформы (ответы, события), `platform_keys` в `/.well-known/pao-configuration`, подпись ответов по RFC 9421 с меткой `platform`; параметры `platform_key_ttl_days`, `platform_key_overlap_days` — в PARAMS и `params.stand.json`;
- SEC-1, РП26 п. 8 — одно изменение ПАО 1.3.0 (совместимо): заголовки подписи у ответов, `use` у ключа Платформы, вместе с общими 401/429/503 и описанием `public_key`; затем копия спецификации и типы в agentic-core.

**К PS-08 (доставка событий):**
- SEC-1, РП26 п. 3–4 — подпись события ключом событий при каждой отправке; компоненты `content-digest`, `x-event-id`, `x-agent-code`, `date`; ПС23.

**К PS-31 (API допуска и кабинет оператора):**
- SEC-1, РП28 — учётная запись и сертификат оператора (`urn:nspk:operator:<id>`); `AgentRegistry.admit` — оператор только из контекста аутентификации; закрывает расхождение №9 кодом.

**К agentic-core (передаёт владелец):**
- SEC-1, РП26 — проверка подписи ответа и события Платформы (`verifyResponse` на общей `signatureBase`) для агента (AG-06).

**После CO-1, CO-2 (постоянное хранилище):**
- ключ УЦ песочницы и ключи Платформы переходят в постоянное хранилище **вместе с реестром** — в PS-05 (зависит от CO-2); иначе после перезапуска выданные сертификаты агентов не проверяются (РП27 п. 1, РП26 п. 7); до переезда — ограничение «перезапуск песочницы = повторный допуск агентов» (SECURITY.md §6);
- реестр, ключи агентов, список отзыва сертификатов — на PostgreSQL; затем измерение «отзыв → отказ» между экземплярами (ПС02, ФП2; угроза Ш7);
- хранилище nonce — атомарное «запомнить, если ещё нет» (угроза Ш3а; см. «Открыто»);
- журнал согласий — запрет UPDATE/DELETE, `verify()` находит подмену в обход триггера (угроза Ж1; PS-06);
- хранилище идемпотентности в паре «агент + ключ» (угроза Ш16; CO-2, PS-05); очередь событий с повтором — PS-08 на Outbox agentic-core (угроза С4);
- учётные записи операторов и выданные сертификаты (PS-31);
- до этого песочница работает одним экземпляром (SECURITY.md §6).

**К PS-10 (ADP):**
- повторный аудит №6 — `Retry-After` у любого 503 в одном месте (`onSend`), тест на `STATE_UNAVAILABLE` из обработчика.

**К CO-2:** хранилище nonce — см. «Открыто».
