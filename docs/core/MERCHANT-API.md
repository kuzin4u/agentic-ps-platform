# API для продавцов и площадок

Документ для продавцов и площадок, которые принимают обращения агентов покупателя. Основание — РП22 и РП56 (PS-30 ч. 1). Знак готовности, приём метаданных пакета оплаты и сверка по `op_ref` появятся в ч. 2 (РП57). Пока их нет, раздел «Будет в ч. 2» описывает только план.

Агент не инициирует авторизацию (РП2). Он передаёт продавцу подписанное обращение и пакет агентской оплаты. Продавец проверяет подпись агента по каталогу ключей Платформы и проводит оплату через своего эквайрера.

## 1. Адреса

Оба адреса — без подписи и без входа. Тело ошибки — `{code}`.

| Метод и путь | Ответ | Ошибки |
|---|---|---|
| `GET /.well-known/agent-keys` | Каталог ключей агентов — JWKS (RFC 7517); `Content-Type: application/jwk-set+json`; `Cache-Control: public, max-age=<merchant_jwks_max_age_sec>` | 503 `UPSTREAM_UNAVAILABLE` с `Retry-After`, без `Cache-Control` |
| `GET /merchants/v1/agents/{code}` | `{agent_code, status, class}`; `status` — `ACTIVE`, `SUSPENDED` или `EXCLUDED` | 404 `AGENT_UNKNOWN` — код неизвестен, не по форме или из другого контура; 503 `UPSTREAM_UNAVAILABLE` с `Retry-After` |

Эквайрер пользуется теми же адресами. Путь ПИ-8 `GET /participants/v1/agents/{code}/status` с подписью эквайрера появится в ч. 2 вместе с ролью участника `ACQUIRER` (РП56 п. 4).

## 2. Каталог ключей агентов

Ключ агента — JWK по RFC 8037:

```json
{
  "kty": "OKP", "crv": "Ed25519", "x": "<32 байта, base64url>",
  "alg": "EdDSA", "use": "sig",
  "kid": "<отпечаток RFC 7638>",
  "agent_code": "nspk:agent:<id>:v<N>",
  "nbf": 1792000000, "exp": 1799776000
}
```

- `kid` — отпечаток RFC 7638 из `{crv, kty, x}`. Это то же значение, что `keyid` в подписи агента и `Key.kid` в ПАО.
- `agent_code`, `nbf`, `exp` — частные члены (RFC 7517 §4): код агента и срок ключа в секундах Unix. Стандартные библиотеки JOSE их игнорируют, поэтому продавец проверяет их сам (п. 3).
- В каталоге только действующие ключи агентов в статусе `ACTIVE`. Отозванный или истёкший ключ, а также ключи приостановленного или исключённого агента из каталога удаляются. Статуса `REVOKED` в каталоге нет: «ключа нет» значит «не принимать».
- Во время ротации в каталоге одновременно два ключа агента, пока длится перекрытие.
- Каталог — только своего контура ключей. Песочница отдаёт ключи агентов песочницы, контур оператора — свои. Ключ из песочницы у боевого продавца не проходит.
- Сейчас в каталоге только ключи Ed25519. Ключи других алгоритмов (ГОСТ, РП5) RFC 8037 не описывает, и в каталог они не попадают; для продавца такой агент выглядит как «неизвестный `kid`».

## 3. Проверка обращения агента у продавца

Подпись — HTTP Message Signatures (RFC 9421), Ed25519. Набор компонентов — как у обращений ПАО (AGENT-PROTOCOL §2): `@method`, `@path`, `@query`, `content-digest`, `x-agent-code`, `x-timestamp`, `x-nonce`. У запроса без тела `content-digest` считается от пустого тела.

Порядок проверки:
1. Нет заголовков подписи — это обращение человека, а не агента: продавец обслуживает его своими правилами. Если подпись есть, но заголовки неполны (`signature-input` без `keyid`, нет `x-agent-code`), — отказ.
2. Найти ключ по `keyid` в кэше каталога. Если его нет — одно перечитывание каталога, но не чаще раза в `merchant_jwks_refetch_min_sec`. Не нашёлся после перечитывания или перечитывание в этом окне уже было — отказ.
3. `agent_code` ключа ≠ `x-agent-code` обращения — отказ: агент A подписал за агента B.
4. Сейчас раньше `nbf` или не раньше `exp` — отказ.
5. Проверить подпись, окно `x-timestamp` (`signature_skew_sec`) и однократность `x-nonce` у этого агента.

Каталог недоступен — отказ, а не догадка. Устаревшие ключи после неудачного чтения не используются.

Эмулятор продавцов в репозитории (`src/env/merchants/verify.ts`, `MerchantAgentVerifier`) работает в этом порядке и отвечает кодами `KEY_UNKNOWN`, `AGENT_MISMATCH`, `KEY_EXPIRED`, `SIGNATURE_INVALID`, при сбое каталога — 503. Набор продавца `agentic-core/merchant` (CO-4) повторит ту же проверку одной реализацией.

## 4. Кэш и отзыв

- Каталог кешируется на `max-age` из ответа (`merchant_jwks_max_age_sec`): рабочее значение — 300 с, на стенде — 1 с.
- Окно перечитывания по неизвестному `kid` — `merchant_jwks_refetch_min_sec`: рабочее — 30 с, на стенде — 1 с. Окно не даёт обращениям со случайными `kid` заставлять продавца перечитывать каталог на каждый запрос.
- Отзыв ключа или приостановление агента доходит до продавца не дольше чем за срок кэша. Оплату такого агента всё равно не пропустит точка решения ADP: до неё отзыв доходит за `revocation_propagation_max_ms`. Продавцу, которому нужно быстрее, — статус агента (п. 1) перед заказом.
- Ответ 503 не кешируется: в нём нет `Cache-Control`. Повтор — не раньше `Retry-After`.

## 5. Отличия от Visa Trusted Agent Protocol

Совпадает формат: подпись RFC 9421 с Ed25519 и каталог ключей в JWKS. Продавцу, который уже проверяет агентов Visa, нужно добавить адрес нашего каталога и проверки п. 3. Отличия:
- частные члены JWK `agent_code`, `nbf`, `exp` и проверка `agent_code` ↔ `x-agent-code`;
- заголовок `x-agent-code` и компоненты подписи ПАО (п. 3);
- путь каталога — `/.well-known/agent-keys`. В открытых материалах Visa путь каталога не опубликован, поэтому совпадение путей и меток подписи с TAP не утверждается (РП22 п. 4, РП56 п. 5).

## 6. Будет в ч. 2 (РП57)

- **Знак готовности** (A5 п. 5, РП22 п. 7): продавец инициирует заявку, эквайрер подаёт и подтверждает её по ПИ-8. Статус знака доступен продавцу по API, агенту — через ПАО. Знак не влияет на порядок выдачи (A5 п. 5.2).
- **Метаданные пакета и сверка** (РП22 п. 6): продавец передаёт `credential_ref`, `order_ref`, `aoi` пакета, а Платформа сверяет их с записью реквизита и операции. `op_ref` — результат сверки, а не её вход. Метаданные служат для сверки и отчётности, решение ADP от них не зависит.
- Путь ПИ-8 статуса агента для эквайрера с подписью.

## 7. Ограничения

- Ограничения частоты на входе у адресов п. 1 пока нет: перебор кодов по статусу возможен. В ответе только код, статус и класс из реестра, сведений о принципалах нет (A2 п. 1.2). Ограничение — SEC-2 (SECURITY.md С3б).
- В режиме «только BYPASS» (РП43 п. 8: самопроверка Платформы при старте не прошла) оба адреса п. 1 отвечают 503 `UPSTREAM_UNAVAILABLE` с `Retry-After: 30`, без `Cache-Control` (РП56 п. 8). Ключи, закешированные раньше, действуют до своего срока; новых продавец не получит до перезапуска Платформы.
