# API для продавцов и площадок

Документ для продавцов и площадок, которые принимают обращения агентов покупателя. Основание — РП22, РП56 (PS-30 ч. 1) и РП57 (PS-30 ч. 2): каталог ключей и статус агента, знак готовности, метаданные пакета оплаты и сверка `credential_ref` → `op_ref` через эквайрера.

Агент не инициирует авторизацию (РП2). Он передаёт продавцу подписанное обращение и пакет агентской оплаты. Продавец проверяет подпись агента по каталогу ключей Платформы и проводит оплату через своего эквайрера.

## 1. Адреса

Все три адреса — без подписи и без входа. Тело ошибки — `{code}`.

| Метод и путь | Ответ | Ошибки |
|---|---|---|
| `GET /.well-known/agent-keys` | Каталог ключей агентов — JWKS (RFC 7517); `Content-Type: application/jwk-set+json`; `Cache-Control: public, max-age=<merchant_jwks_max_age_sec>` | 503 `UPSTREAM_UNAVAILABLE` с `Retry-After`, без `Cache-Control` |
| `GET /merchants/v1/agents/{code}` | `{agent_code, status, class}`; `status` — `ACTIVE`, `SUSPENDED` или `EXCLUDED` | 404 `AGENT_UNKNOWN` — код неизвестен, не по форме или из другого контура; 503 `UPSTREAM_UNAVAILABLE` с `Retry-After` |
| `GET /merchants/v1/merchants/{merchant_id}/readiness` | Знак готовности продавца (п. 6): `{merchant_id, status, since}`; `status` — `ACTIVE`, `SUSPENDED` или `NONE`; `Cache-Control: public, max-age=<merchant_readiness_max_age_sec>` | 400 `REQUEST_INVALID` — `merchant_id` пустой или длиннее 128 знаков; 503 `UPSTREAM_UNAVAILABLE` с `Retry-After` |

Эквайрер пользуется теми же адресами или путями ПИ-8 со своей подписью (участник с ролью `ACQUIRER`, РП57 п. 1): `GET /participants/v1/agents/{code}/status` — тот же статус агента; знак своего продавца с причиной приостановления — п. 6; метаданные пакета и сверка — п. 7.

**Длина параметра пути.** До 256 знаков параметр доходит до проверки и ответа по таблице; длиннее — HTTP 414 до проверки, тело не `{code}` (`FST_ERR_MAX_PARAM_LENGTH`), повторять не нужно (РП57 доп. 1). По схеме параметров длиннее 128 знаков нет.

## 2. Каталог ключей агентов

Ключ агента — JWK по RFC 8037:

```json
{
  "kty": "OKP", "crv": "Ed25519", "x": "<32 байта, base64url>",
  "alg": "EdDSA", "use": "sig",
  "kid": "<отпечаток RFC 7638>",
  "agent_code": "nspk:agent:<id>:v<N>",
  "nbf": 1792000000, "exp": 1799776000
}
```

- `kid` — отпечаток RFC 7638 из `{crv, kty, x}`. Это то же значение, что `keyid` в подписи агента и `Key.kid` в ПАО.
- `agent_code`, `nbf`, `exp` — частные члены (RFC 7517 §4): код агента и срок ключа в секундах Unix. Стандартные библиотеки JOSE их игнорируют, поэтому продавец проверяет их сам (п. 3).
- В каталоге только действующие ключи агентов в статусе `ACTIVE`. Отозванный или истёкший ключ, а также ключи приостановленного или исключённого агента из каталога удаляются. Статуса `REVOKED` в каталоге нет: «ключа нет» значит «не принимать».
- Во время ротации в каталоге одновременно два ключа агента, пока длится перекрытие.
- Каталог — только своего контура ключей. Песочница отдаёт ключи агентов песочницы, контур оператора — свои. Ключ из песочницы у боевого продавца не проходит.
- Сейчас в каталоге только ключи Ed25519. Ключи других алгоритмов (ГОСТ, РП5) RFC 8037 не описывает, и в каталог они не попадают; для продавца такой агент выглядит как «неизвестный `kid`».

## 3. Проверка обращения агента у продавца

Подпись — HTTP Message Signatures (RFC 9421), Ed25519. Набор компонентов — как у обращений ПАО (AGENT-PROTOCOL §2): `@method`, `@path`, `@query`, `content-digest`, `x-agent-code`, `x-timestamp`, `x-nonce`. У запроса без тела `content-digest` считается от пустого тела.

Порядок проверки:
1. Нет заголовков подписи — это обращение человека, а не агента: продавец обслуживает его своими правилами. Если подпись есть, но заголовки неполны (`signature-input` без `keyid`, нет `x-agent-code`), — отказ.
2. Найти ключ по `keyid` в кэше каталога. Если его нет — одно перечитывание каталога, но не чаще раза в `merchant_jwks_refetch_min_sec`. Не нашёлся после перечитывания или перечитывание в этом окне уже было — отказ.
3. `agent_code` ключа ≠ `x-agent-code` обращения — отказ: агент A подписал за агента B.
4. Сейчас раньше `nbf` или не раньше `exp` — отказ.
5. Проверить подпись, окно `x-timestamp` (`signature_skew_sec`) и однократность `x-nonce` у этого агента.

Каталог недоступен — отказ, а не догадка. Устаревшие ключи после неудачного чтения не используются.

Эмулятор продавцов в репозитории (`src/env/merchants/verify.ts`, `MerchantAgentVerifier`) работает в этом порядке и отвечает кодами `KEY_UNKNOWN`, `AGENT_MISMATCH`, `KEY_EXPIRED`, `SIGNATURE_INVALID`, при сбое каталога — 503. Набор продавца `agentic-core/merchant` (CO-4) повторит ту же проверку одной реализацией.

## 4. Кэш и отзыв

- Каталог кешируется на `max-age` из ответа (`merchant_jwks_max_age_sec`): рабочее значение — 300 с, на стенде — 1 с.
- Окно перечитывания по неизвестному `kid` — `merchant_jwks_refetch_min_sec`: рабочее — 30 с, на стенде — 1 с. Окно не даёт обращениям со случайными `kid` заставлять продавца перечитывать каталог на каждый запрос.
- Отзыв ключа или приостановление агента доходит до продавца не дольше чем за срок кэша. Оплату такого агента всё равно не пропустит точка решения ADP: до неё отзыв доходит за `revocation_propagation_max_ms`. Продавцу, которому нужно быстрее, — статус агента (п. 1) перед заказом.
- Ответ 503 не кешируется: в нём нет `Cache-Control`. Повтор — не раньше `Retry-After`.

## 5. Отличия от Visa Trusted Agent Protocol

Совпадает формат: подпись RFC 9421 с Ed25519 и каталог ключей в JWKS. Продавцу, который уже проверяет агентов Visa, нужно добавить адрес нашего каталога и проверки п. 3. Отличия:
- частные члены JWK `agent_code`, `nbf`, `exp` и проверка `agent_code` ↔ `x-agent-code`;
- заголовок `x-agent-code` и компоненты подписи ПАО (п. 3);
- путь каталога — `/.well-known/agent-keys`. В открытых материалах Visa путь каталога не опубликован, поэтому совпадение путей и меток подписи с TAP не утверждается (РП22 п. 4, РП56 п. 5).

## 6. Знак готовности (A5 п. 5; РП22 п. 7, РП57 п. 1–3)

- **Как получить.** Продавец подаёт заявку своему эквайреру. Эквайрер подаёт и подтверждает знак записью ПИ-8 со своей подписью: `POST /participants/v1/merchants/{merchant_id}/readiness`, `status` — `ACTIVE`; снять знак — та же запись с `WITHDRAWN`. Канала «заявка от продавца напрямую» у Платформы нет: подписи продавца у неё нет, а эквайрер отвечает за своего продавца. У продавца один эквайрер (РП57 п. 1).
- **Приостановление.** Приостанавливает и снимает приостановление только оператор Платформы (A5 п. 5.3): расхождения сведений, отказы опознанным агентам (A5 п. 2.2), систематическая отмена. Пока знак приостановлен, эквайрер его не меняет (409 `READINESS_SUSPENDED`). Автоматического приостановления по расхождениям сверки нет — их рассматривает оператор.
- **Статус.** `ACTIVE` — знак действует, витрина в зоне `CONTOUR`. `SUSPENDED` — приостановлен оператором. `NONE` — знака нет, он снят или продавец Платформе неизвестен. `since` — время последней записи знака. Причина приостановления видна только эквайреру (`GET /participants/v1/merchants/{merchant_id}/readiness` с подписью).
- **Кэш.** Адрес п. 1 отдаёт `Cache-Control: public, max-age=<merchant_readiness_max_age_sec>`; рабочее значение — 60 с (на стенде 1 с). Приостановление доходит до продавца и площадки не дольше этого срока. Агент читает знак через ПАО без кэша (`no-store`).
- **Выдача.** Знак не влияет на порядок выдачи (A5 п. 5.2, A6 п. 2.1): Платформа витрины не сортирует и не фильтрует, а точка решения ADP знак не читает.

## 7. Метаданные пакета и сверка `credential_ref` → `op_ref` (РП22 п. 6, РП57 п. 5)

- **Зачем.** Если эквайрер не переносит признак `aoi` в авторизацию, операция всё равно агентская по инструменту, и ADP определяет агента по домену токена. Метаданные пакета нужны только для сверки и отчётности: решение ADP от них не зависит.
- **Как передать.** Продавец отдаёт `credential_ref`, `order_ref` и, если есть, `aoi` пакета своему эквайреру. Эквайрер присылает их Платформе подписанной записью ПИ-8: `POST /participants/v1/merchants/{merchant_id}/payments`. Без поддержки `aoi` запись — без него. Канала «метаданные от продавца напрямую» нет.
- **Ответ — сверка по записи реквизита Платформы:**
  - `MATCHED` с `op_ref` — реквизит погашен этой операцией; `op_ref` остаётся и после реверсала и возврата;
  - `MISMATCH` с `fields` — `order_ref` или `aoi` расходятся с записью реквизита;
  - `PENDING` — реквизит действует, авторизации ещё не было;
  - `NOT_USED` с `reason` — реквизит не погашен и погашен не будет: `MANDATE_REVOKED`, `AGENT_SUSPENDED` или `EXPIRED`;
  - `aoi_checked: false` — `aoi` не прислан, сверка только по продавцу и `order_ref`.
- `op_ref` — результат сверки, а не её вход: у продавца в момент авторизации его нет. Неизвестный реквизит и реквизит другого продавца — 404 `CREDENTIAL_NOT_FOUND`. Повторить сверку позже — `GET /participants/v1/merchants/{merchant_id}/payments/{credential_ref}`.

## 8. Ограничения

- Метаданные пакета и сверка (п. 7) пока работают только на стенде Платформы: в рабочем сервере нет записей реквизитов до подключения токен-сервиса оператора (РП57 доп. 5).
- Ограничения частоты на входе у адресов п. 1 пока нет: перебор кодов по статусу и продавцов по знаку возможен. В ответе только код, статус и класс из реестра, сведений о принципалах нет (A2 п. 1.2). Ограничение — SEC-2 (SECURITY.md С3б).
- В режиме «только BYPASS» (РП43 п. 8: самопроверка Платформы при старте не прошла) все адреса п. 1 отвечают 503 `UPSTREAM_UNAVAILABLE` с `Retry-After: 30`, без `Cache-Control` (РП56 п. 8). Ключи, закешированные раньше, действуют до своего срока; новых продавец не получит до перезапуска Платформы.
