### РП1. Место Платформы — у оператора, рядом с процессингом
- **Решение:** Платформа — сервисный слой оператора платёжной системы. Процессинг вызывает её синхронно в пути авторизации (точка решения ADP), а не банк-участник по своей инициативе.
- **Почему:** так банку остаются две доработки — принять признак и показать клиенту уведомления, отзыв и подтверждение. Без этого прогон остаётся лабораторным (главный риск MVP пула). Модель повторяет путь сетей: функция ставится на действующий актив (процессинг, токенизация, мониторинг).
- **Что меняет:** ПИ-1, режим эмитента «за эмитента» по умолчанию.
- **Отменяет:** —

### РП2. Агент не инициирует авторизацию
- **Решение:** агент получает агентский платёжный реквизит (одноразовая криптограмма агентского токена или списание по привязке СБП) и передаёт продавцу пакет агентской оплаты. Авторизацию инициирует продавец через эквайрера. О результате агент узнаёт событием Платформы. `POST /v1/pay/authorize` испытательного контура пула сохраняется только как эмуляция в песочнице.
- **Почему:** так устроены карточные и быстрые платежи — инициатор списания на стороне получателя. Это не требует для агента статуса участника. Источник истины об операции — Платформа, а не продавец.
- **Что меняет:** ПАО, ресурс `/credentials`; в репозитории агента — переход с `/v1/pay/*` на ПАО (Р14 там).
- **Отменяет:** в части архитектуры — прямой вызов шлюза агентом из файла 23 пула.

### РП3. Два режима эмитента
- **Решение:** «за эмитента» (ADP проверяет всё и резервирует бюджет) — по умолчанию; «сам эмитент» (ADP проверяет признак, агента и мандат, эмитент ведёт ограничения через API состояния).
- **Почему:** A3 п. 2.1 относит проверку ограничений к банку плательщика; банк вправе её делегировать, как делегирует токенизацию и 3-D Secure.
- **Что меняет:** `issuer_mode_default`, ПИ-8 `state/*`.
- **Отменяет:** —

### РП4. Fail-closed только для агентских операций
- **Решение:** операция без признака и с неагентским инструментом получает `BYPASS` первой же проверкой. Недоступность ADP отклоняет только агентские операции.
- **Почему:** Платформа не должна стать точкой отказа для всего процессинга; агентские операции при неопределённости отклоняются (A3 п. 4.5).
- **Что меняет:** порядок проверок ADP, ПС08, ПС17.
- **Отменяет:** —

### РП5. Криптография независима от алгоритма
- **Решение:** в песочнице — ed25519; в контуре оператора — ГОСТ Р 34.10-2012 / 34.11-2012 через сертифицированное СКЗИ, ключи в HSM. Алгоритм — атрибут ключа.
- **Почему:** песочница не должна зависеть от СКЗИ, а боевой контур обязан его использовать (719-П, 57580.1).
- **Что меняет:** `Key.alg`, `Signature-Input` с `alg`.
- **Отменяет:** —
- **Изменено:** PKI для TLS песочницы — ECDSA P-256 (РП27 п. 1); подписи — по-прежнему ed25519.

### РП6. Каноническая модель вместо внешних форматов
- **Решение:** Платформа работает с канонической моделью сообщения; адаптеры к форматам ОПКЦ, СБП и токен-сервиса пишутся по таблицам соответствия с пометкой `[альбом]`. В песочнице эмуляторы говорят на канонической модели.
- **Почему:** альбомы форматов оператора недоступны; ядро не должно зависеть от номеров полей.
- **Что меняет:** `src/adapters/*` пустые до получения альбомов.
- **Отменяет:** —

### РП11. Резерв, а не списание, в момент авторизации
- **Решение:** двухфазное расходование: резерв → закрепление при клиринге → освобождение при реверсале, отказе или истечении.
- **Почему:** авторизация не равна списанию; без резерва реверсалы съедают бюджет, без закрепления частичные представления дают расхождения.
- **Что меняет:** SPEC §5, ПИ-3.
- **Отменяет:** однофазное «лимит уменьшается при авторизации» из испытательного контура пула.

### РП13. Точка расширения «условное исполнение»
- **Решение:** платформа не держит деньги и не решает о наступлении условия, а даёт точку расширения для поставщиков условного исполнения (ПУИ): допуск по публичным условиям, `deal_ref` в мандате, реквизите, признаке и событиях, приём итога сделки для записи об исполнении и маршрутизации споров. Интерфейс — `CONDITIONAL-EXECUTION.md`, `/cx/v1/*`. Первый ПУИ — НСВР.
- **Почему:** условное исполнение — свободная роль, которую сети не взяли из-за ответственности за качество; платформа должна остаться нейтральной, но не мешать эскроу-модели.
- **Что меняет:** ПАО v1.1.0 (совместимо), ПИ-2 субполе 6, П10 — новый тип участника, П7 — маршрут `PROVIDER`, параметр `cx_outcome_timeout_days`.
- **Отменяет:** «условное исполнение — только точка расширения без интерфейса» из SPEC §10.

### РП14. Общие механизмы — из agentic-core
- **Решение:** журнал согласий (П2), удержания бюджета (П3), идемпотентность, подпись ПАО и доставка событий реализуются на `@kuzin4u/agentic-core` (журнал, holds, idempotency, signing, events). Своих реализаций этих механизмов в платформе нет.
- **Почему:** те же механизмы нужны агенту, НСВР и marketplace-api; одна реализация и одни тестовые векторы.
- **Что меняет:** `package.json` — зависимость `git+https://github.com/kuzin4u/agentic-core.git#v0.1.0`; ROADMAP этапа 1 короче на реализацию механизмов, длиннее на хранилища PostgreSQL (их делает agentic-core 0.2).
- **Отменяет:** —

### РП16. ПАО v1.2.0: смысл `retry`, digest пустого тела, таблица ошибок в YAML
- **Решение:**
  1. Значения `retry` не переименовываются. `same_key` — повторить запрос с тем же `Idempotency-Key`, с новыми `x-nonce`, `x-timestamp` и подписью. `new_key` — нужен новый ключ подписи агента (не ключ идемпотентности); повтор — после выпуска ключа. `RATE_LIMITED` (429), `STATE_UNAVAILABLE` и `UPSTREAM_UNAVAILABLE` (503) — `same_key`; Платформа передаёт `Retry-After`, клиент ждёт не меньше указанного. Число повторов ограничивает клиент; после исчерпания — ошибка вызывающему (у BuyerAgent — Т14).
  2. У запросов без тела подписывается `content-digest` пустого тела.
  3. Таблица ошибок — в `agent-protocol.yaml`, расширение `x-pao-errors` (код, HTTP, `retry`, описание). YAML — источник; AGENT-PROTOCOL.md §6 ссылается на него.
- **Почему:** расхождения 2–4 agentic-core: клиент CO-3 и заглушка держали свою трактовку `retry` и ручную копию таблицы, у GET не было правила для digest. Временные отказы с `after_fix` не повторялись даже там, где повтор безопасен благодаря идемпотентности.
- **Что меняет:** AGENT-PROTOCOL.md §2, §6, шапка; `agent-protocol.yaml` → 1.2.0 (`x-pao-errors`, заголовок `Retry-After` у ответа-ошибки, описание `Content-Digest`). ПАО v1.2.0 — совместимое изменение по §7. Копия у агента остаётся v1.0.0 до перехода своим `/decision`; agentic-core обновляет копию спецификации, типы и заглушку.
- **Отменяет:** `retry: after_fix` у `RATE_LIMITED`, `STATE_UNAVAILABLE`, `UPSTREAM_UNAVAILABLE` в таблице §6 ПАО v1.1.0.

### РП17. Допуск стороннего агента — через набор соответствия
- **Решение:** агент любого оператора, включая эталонный BuyerAgent, включается в реестр (П1) контура оператора только после прохождения набора соответствия — исполняемого прогона сценариев против песочницы Платформы. В песочнице агент вносится в реестр по заявлению для прохождения набора (ПС01). Факт прохождения — ссылка на прогон в записи реестра (`conformance_run_ref`), в ПАО не передаётся. Набор и инструкция для операторов агентов публикуются (PS-29, совместный план ред. 5). Платформа обслуживает сторонних агентов на тех же публичных условиях, что и эталонного (A6 п. 2.1; 135-ФЗ ст. 10–11).
- **Почему:** нейтральность Платформы должна быть проверяемой; одна мера для своего и чужих агентов.
- **Что меняет:** SPEC §3 (П1), ФП1; ROADMAP — PS-29 в этапе 6 (+1 сессия, после PS-26), SEC-1 в этапе 1 — выдача ключей и сертификатов mTLS сторонним операторам агентов, а не только песочнице. ПАО не меняется.
- **Отменяет:** —

### РП18. Ослабление `retry` — совместимое изменение ПАО
- **Решение:** в ПАО v1 совместимым считается изменение `retry` у существующего кода, которое разрешает повтор там, где раньше его не было: `never` или `after_fix` → `same_key`. Обратный переход (`same_key` → `never` или `after_fix`) несовместим и делается только новой версией пути. Совместимость не отменяет обоснования: перевести код из `never` в `same_key` можно только отдельным решением РП с оценкой безопасности повтора. Версия ПАО остаётся 1.2.0.
- **Почему:** расхождение №10 agentic-core. В РП16 значение `retry` у `RATE_LIMITED`, `STATE_UNAVAILABLE`, `UPSTREAM_UNAVAILABLE` сменилось с `after_fix` на `same_key`, и изменение названо совместимым по §7. Но §7 называл совместимыми только новые необязательные поля и новые типы событий. По YAML ничего не удалено и типы не сузились. Агент на прежней версии просто не повторит запрос там, где теперь повтор разрешён: возможностью не воспользуется, но и не сломается. Повтор с `same_key` безопасен благодаря идемпотентности. Для `never` безопасность повтора нужно оценивать по каждому коду отдельно.
- **Что меняет:** AGENT-PROTOCOL.md §7. Спецификация `agent-protocol.yaml` не меняется, версия ПАО остаётся 1.2.0. Задним числом обосновывает совместимость РП16.
- **Отменяет:** —

### РП19. Пары «решение — причина» в ответе ADP
- **Решение:**
  1. В ответе ADP (ПИ-1) допустимы только такие пары:
     - `APPROVE`, `BYPASS` — `reason: null`;
     - `DECLINE` — причина обязательна: любой код ПИ §6, кроме `CONFIRMATION_REQUIRED` и `ADP_UNAVAILABLE`;
     - `CONFIRMATION_REQUIRED` — `reason: CONFIRMATION_REQUIRED`.
  2. `ADP_UNAVAILABLE` ставит процессинг, когда ADP не ответила за `adp_timeout_ms` (ПИ §3), а не сама ADP. Этот код допустим только в решении, которое процессинг формирует от своего имени: `DECLINE` / `ADP_UNAVAILABLE`.
  3. Несогласованная пара — отказ, как и неизвестный код (A3 п. 4.5).
  4. Строки ПИ §6, где в колонке ОПКЦ стоит только `[альбом]` (`AOI_MISMATCH`, `AGENT_SUSPENDED`, `CREDENTIAL_INVALID`), остаются без группы смысла до получения альбомов. Это расхождение №8.
- **Почему:** находка 1 аудита PS-02. ПИ §3 говорил только «`reason` — код из раздела 6», а в YAML у `reason` есть `null`. Поэтому ответ `APPROVE` с кодом отказа или `DECLINE` без причины проходил проверку типов. На такой ответ опрётся ADP (PS-10) и эмулятор ОПКЦ. Группу смысла для строк с одним `[альбом]` не выдумываем (РП6).
- **Что меняет:** ПИ §3 и §6; описание `Decision` в `processing-interface.yaml`; `src/shared/codes.ts` — функция `parseDecision(raw, source)`, где `source` равен `adp` или `processing`; STATUS — расхождение №8. ПАО не меняется.
- **Отменяет:** —

### РП20. Границы стендовых параметров и перекрёстные правила
- **Решение:** загрузчик стендовых параметров отказывает в запуске, если нарушена граница или перекрёстное правило из PARAMS.md, раздел «Границы». Новые правила:
  1. `protocol_overlap_days` ≥ 1;
  2. `event_retry_max` ≥ 1;
  3. `bypass_overhead_ms` < `adp_p99_ms`;
  4. `adp_timeout_ms` > `adp_p99_ms` (строго; раньше равенство допускалось).
  Путь к файлу параметров задаётся переменной окружения `PARAMS_PATH`, по умолчанию `config/params.stand.json`; это записывается в PARAMS.md.
- **Почему:** находка 4 аудита PS-02. При нынешних нижних границах загрузчик принимал вырожденные конфигурации:
  - `protocol_overlap_days = 0` — вывод старой версии ПАО без периода параллельной работы, вопреки §7;
  - `event_retry_max = 0` — нет повторов, то есть нет доставки «не менее одного раза» (инвариант 9);
  - добавка к неагентским операциям не меньше всей задержки ADP — нарушение РП4;
  - таймаут, равный p99, — процессинг отклоняет хвост нормальных ответов как `ADP_UNAVAILABLE`.

  Ошибка в конфигурации должна останавливать запуск, а не проявляться на прогоне. `PARAMS_PATH` уже читается кодом, но в документах не описан.
- **Что меняет:** PARAMS.md — новый раздел «Границы» и строка о `PARAMS_PATH`; `src/shared/config.ts` — четыре правила; тесты загрузчика. Стендовые значения не меняются: 180, 8, 1 < 50, 150 > 50 укладываются в правила. ПАО не меняется.
- **Отменяет:** —

### РП21. Реестр агентов: код, основания отказа в допуске, уровень и статус
- **Решение:**
  1. **Код агента** — части через `:`, каждая `[a-z0-9-]+`. Последняя часть — версия `v<N>` (N ≥ 1), предпоследняя — идентификатор, всё перед ними — выдавшая сторона (одна или больше частей). `nspk:agent:buyref-01:v3`: сторона `nspk:agent`, идентификатор `buyref-01`, версия 3. Код неизменен; существенное изменение агента — новая версия, новая запись (A2 п. 4.1–4.2).
  2. **Закрытый перечень оснований отказа в допуске:**
     - `APPLICATION_INCOMPLETE` — нет кода агента (версия — в нём), модели или среды исполнения (A2 п. 4.4);
     - `CLASS_UNKNOWN` — класс вне A2 п. 2;
     - `CODE_INVALID` — код нарушает грамматику п. 1;
     - `CODE_TAKEN` — код уже выдан другому агенту (A2 п. 4.1);
     - `PRINCIPAL_DATA` — сведения о принципалах в сохраняемых полях заявления или в `x-system` Agent Card (A2 п. 1.2): телефон, e-mail или 13–19 цифр подряд в `model`, `runtime` и значениях `x-system`; в `x-system` — поля принципала, кроме `principal` / `principal_type` с кодом типа `[A-Z_]{1,32}` (ПАО §8);
     - `CONFORMANCE_MISSING` — контур оператора без `conformance_run_ref` (РП17);
     - `AGENT_CARD_MISMATCH` — Agent Card расходится с заявлением (ПАО §8, A9 п. 5).
     Других оснований нет; заявление, не попадающее ни под одно, допускается (A6 п. 2.1). Учитываются только поля `agent_code`, `class`, `model`, `runtime`, `conformance_run_ref` (только в контуре оператора), `agent_card`; прочие не учитываются и в запись не попадают. Оператор агента — из контекста вызова (аутентифицированный оператор), а не из заявления; до аутентификации операторов (PS-04, SEC-1) его передаёт вызывающий — расхождение №9.
  3. **Уровень** — целое ≥ 1; при допуске — 1. Изменение уровня — П8 по оценке исполнения (позже).
  4. **Статус:** ACTIVE → SUSPENDED — только с основанием A2 п. 7.1: `KEY_COMPROMISE`, `OUT_OF_MANDATE`, `FALSE_INFORMATION`, `INCIDENT_EVASION`; SUSPENDED → ACTIVE — без основания. Переход в EXCLUDED — из любого статуса, с тем же основанием или `WITHDRAWN` (отказ оператора агента от допуска); из EXCLUDED выхода нет. Неизвестный статус или основание — отказ (инвариант 3).
- **Почему:** ФП1 требует закрытого перечня оснований отказа, но перечня не было; без него допуск дискреционный, а нейтральность (A6 п. 2.1, РП17) не проверить. Пример кода в ПАО из четырёх частей при норме «сторона : идентификатор : версия» допускал два прочтения. `CODE_INVALID` и `CODE_TAKEN` — разные ошибки заявителя: первая исправляется форматом, вторая — выбором другого идентификатора. Белый список полей и проверка значений вместо поиска слов в именах ключей: поиск по словам и обходился (`cardholder_name`, `fio`), и ложно срабатывал на поля оператора (`operator_inn`, `clientCredentials` в A2A Agent Card) — неравные условия для операторов (A6 п. 2.1). Оператор из тела заявления позволял выпустить новую версию чужого агента (инвариант 5).
- **Что меняет:** SPEC §3 — подраздел «Реестр (П1)» с п. 1–4; ФП1 — ссылка на РП21; `src/registry`; STATUS — расхождение №9 и в «Открыто» — кто может быть выдавшей стороной кода. ПАО не меняется: `AgentSelf.class`, `level`, `status` уже совместимы.

- **Изменено:** п. 1 — выдавшая сторона только `nspk:agent`; п. 2 — основание `KEY_INVALID`, поля `alg`, `public_key` — РП23. П. 2, оператор из контекста — аутентификация операторов: РП28.

### РП22. Интерфейс для продавцов и площадок: каталог ключей агентов (JWKS), пакет оплаты, признак без поддержки эквайрера, знак готовности

- **Решение:**
  1. **Каталог ключей агентов — JWKS (RFC 7517) по известному адресу** API для продавцов и площадок (PS-30). Ключ агента — JWK по RFC 8037: `kty: OKP`, `crv: Ed25519`, `x` (base64url, 32 байта), `alg: EdDSA`, `use: sig`. `kid` — тот же отпечаток RFC 7638, что в реестре и в `Key.kid` ПАО (РП23 п. 3): он вычисляется из `{crv, kty, x}`, поэтому у одного ключа один `kid` и в ПАО (DER SPKI в `public_key`), и в JWKS (`x`). Частные члены JWK (RFC 7517 §4): `agent_code` (код агента `nspk:agent:<id>:v<N>`) и `nbf`, `exp` (срок ключа, секунды Unix). Это не стандартные параметры JWK, и сторонние библиотеки их игнорируют. Поэтому привязку `kid` к агенту и срок ключа продавец проверяет сам — так делает набор продавца agentic-core (CO-4).
  2. **В каталоге только действующие ключи** допущенных агентов в статусе `ACTIVE`. Отозванный или истёкший ключ, а также ключ приостановленного или исключённого агента из каталога удаляется; статуса `REVOKED` в JWKS нет. Продавец действует так же, как агент с ключами Платформы (РП26 п. 6): неизвестный `kid` — одно перечитывание каталога, затем отказ. Ключ с истёкшим `exp` или с `agent_code` ≠ `x-agent-code` обращения — отказ (как в РП23: ключ привязан к агенту, инвариант 5). Срок кэша каталога у продавца задаёт стендовый параметр `merchant_jwks_max_age_sec` (`Cache-Control: max-age`). Отзыв доходит до продавца не дольше чем за этот срок. Инвариант 8 (≤ `revocation_propagation_max_ms` до ADP и шлюза) на продавцов не распространяется; отказ в авторизации всё равно даёт ADP.
  3. **Ограничение перечитывания.** Каталог перечитывается из-за неизвестного `kid` не чаще одного раза в `merchant_jwks_refetch_min_sec`. Если перечитывание в этом окне уже было, неизвестный `kid` — сразу отказ, без перечитывания. Иначе обращения со случайными `kid` заставляли бы продавца перечитывать каталог на каждый запрос. Агент с ключами Платформы действует так же (дополнение к РП26 п. 6): `platform_keys` перечитываются не чаще одного раза в `platform_keys_refetch_min_sec`. Значения параметров — `/decision` в PS-30 и PS-05, когда появится код, который их читает.
  4. **Совместимость с Visa TAP — по формату**: подпись RFC 9421 с Ed25519 и каталог ключей в JWKS. Продавцу, который проверяет агентов Visa, нужно добавить только адрес нашего каталога. Соответствие остальных параметров TAP (метки подписи, путь каталога) этим решением не утверждается: их сверяют по документации TAP в PS-30, отличия описываются в документации для продавцов.
  5. **Пакет агентской оплаты** (AGENT-PROTOCOL §4) — `PaymentPackage`: `credential_ref`, `kind`, `payload`, `aoi`, `cart_mandate_id`, `order_ref` (ссылка продавца на заказ), подпись агента по RFC 9421 тем же ключом, что и обращения ПАО (`kid` из каталога п. 1). Разбор и проверка — одна реализация в agentic-core (`merchant`, CO-4) для продавцов и площадок. Продавец проверяет подпись пакета и переносит `aoi` в авторизацию через эквайрера (ПИ-2). Суммы в пакете нет: сумма операции берётся только из сообщения процессинга (инвариант 5).
  6. **Признак без поддержки эквайрера.** Если эквайрер не переносит `aoi` в сообщения процессинга, операция всё равно агентская: инструмент `AGENT_TOKEN` или `ACCOUNT_LINK` (ПИ-1), и ADP определяет агента и мандат по домену токена (ФП4), а не по `aoi`. `BYPASS` для неё невозможен (ПИ-1: только при отсутствии `aoi` **и** неагентском инструменте). Продавец дополнительно передаёт метаданные пакета (`credential_ref`, `order_ref`, `aoi`) в API для продавцов (PS-30).
     - **Ключ сверки — `credential_ref`.** Продавец знает его из пакета. Платформа связывает реквизит с операцией сама, когда авторизация с этим реквизитом проходит ADP: криптограмма одноразовая и выпущена на один заказ (ФП4); для `ACCOUNT_LINK` — идентификатор списания из `payload`. `order_ref` и время проверяются как совпадение с записью, а не как ключ.
     - **`op_ref` — результат сверки, а не её вход**: у продавца в момент авторизации его нет. Ссылка эквайрера на авторизацию (RRN/ARN, ПИ-2) — дополнительный ключ после получения альбомов (`[альбом]`, РП6).
     - Метаданные служат только для сверки и отчётности (П11), решение ADP от них не зависит. Расхождение «метаданные ↔ операция» записывается и учитывается в п. 7. `CARD_TOKEN` без `aoi` остаётся неагентской операцией (инвариант 2), поэтому агенту для оплаты выдаются только агентские инструменты (ФП4).
  7. **Знак готовности (A5 п. 5).** Продавец инициирует заявку через API для продавцов (PS-30). Подаёт и подтверждает её эквайрер продавца по ПИ-8 (`POST /participants/v1/merchants/{id}/readiness`): он отвечает за продавца. Продавцу в API доступен статус знака. Знак приостанавливается по A5 п. 5.3: расхождения сведений (в том числе по п. 6), отказы опознанным агентам (A5 п. 2.2), систематическая отмена. Знак определяет зону `CONTOUR` и не влияет на порядок выдачи (A5 п. 5.2, A6 п. 2.1).
  8. **Эмуляторы (PS-12) — до PS-30.** Эмулятор продавцов проверяет подпись агента по каталогу ключей в формате п. 1. Каталог строит та же функция реестра, что потом отдаст HTTP-адрес PS-30. Эмулятор эквайрера поддерживает оба режима п. 6: с переносом `aoi` и без него.
- **Почему:** продавцу нужно проверить, что обращение и пакет действительно от допущенного агента. Формат JWKS + RFC 9421 + Ed25519 совпадает с Visa TAP, поэтому продавцы TAP подключаются без доработки (совместный план ред. 6, «Что дала синхронизация»). Один `kid` по RFC 7638 во всех представлениях ключа исключает расхождение между ПАО и каталогом. Удаление ключа вместо статуса — обычное поведение JWKS: продавцу не нужно знать модель статусов реестра, а fail-closed даёт «неизвестный `kid` → отказ». Ограничение перечитывания не даёт превратить fail-closed в нагрузку на продавца и Платформу. Признак без поддержки эквайрера закрывает разрыв, который иначе пришлось бы ждать до альбомов форматов (расхождение № 3): агентский инструмент уже делает операцию видимой для ADP, а метаданные дают сверку по ключу, известному продавцу, но не становятся источником истины (инвариант 5). Заявка через эквайрера сохраняет ответственность участника за продавца (ПИ-8). `cart_mandate_id` по смыслу совпадает с CartMandate AP2 — это пригодится в документе соответствия.
- **Что меняет:** SPEC §3 (П10, новая строка «API для продавцов и площадок», PS-30); AGENT-PROTOCOL §4 — состав `PaymentPackage` (описательно; схема — в ПАО 1.3.0 (→ 1.4.0, РП31; → 1.5.0, РП37) вместе с РП26 п. 8, совместимо: новая схема); ПИ-1 — пояснение к `BYPASS` и агентским инструментам без `aoi`; PARAMS — `merchant_jwks_max_age_sec`, `merchant_jwks_refetch_min_sec` (значения — в PS-30), `platform_keys_refetch_min_sec` (значение — в PS-05); РП26 п. 6 — ограничение перечитывания (п. 3); SECURITY.md — новая угроза «подмена каталога ключей агентов для продавца» (Н5/Н7: TLS, неизвестный `kid` → одно перечитывание не чаще окна, `agent_code` ↔ `x-agent-code`) рядом с С3, к С3 — ограничение перечитывания; GLOSSARY — «Каталог ключей агентов»; STATUS — «Заделы» к PS-12, PS-30, PS-05, CO-4 (agentic-core: проверка пакета по JWKS, частные члены JWK). Описательные правки SPEC, AGENT-PROTOCOL, ПИ-1, SECURITY.md, GLOSSARY вносятся первым шагом PS-12 в той же ветке; PARAMS и `params.stand.json` — вместе с кодом, который читает параметры. ### РП23. Ключи агентов и проверка подписи ПАО

- **Решение:**
  1. **Выдавшая сторона кода агента** — только оператор реестра Платформы, `nspk:agent`. Код присваивается при допуске: оператор агента в заявлении указывает код в пространстве `nspk:agent` (идентификатор и версию), реестр выдаёт его решением о допуске. Код с другой выдавшей стороной — `CODE_INVALID`. Операторы агентов коды не выдают. Признание внешних пространств имён (реестры других систем, A9) — отдельным решением.
  2. **Первый ключ — в заявлении.** В белый список РП21 п. 2 добавляются `alg` и `public_key`. Пару ключей генерирует оператор агента; закрытый ключ Платформа не получает. `public_key` — открытый ключ в DER SubjectPublicKeyInfo, base64 (как у `agentic-core` signing). Нет `alg` или `public_key` — `APPLICATION_INCOMPLETE`. Новое основание отказа **`KEY_INVALID`**: `alg` не из перечня контура (песочница — `ed25519`; ГОСТ — после точки расширения РП5, до неё — отказ), ключ не разбирается или не соответствует `alg`, ключ уже зарегистрирован в реестре (п. 3). Допуск неделим: запись агента и первый ключ сохраняются вместе или не сохраняются оба.
  3. **`kid` присваивает Платформа** — отпечаток JWK открытого ключа по RFC 7638: канонический JSON обязательных членов (`{"crv","kty","x"}` для Ed25519), SHA-256, base64url без дополнения. Эталон — RFC 8037 прил. A.3. `kid` глобально уникален в реестре; повторная регистрация того же ключа — тому же агенту, другому агенту или после отзыва — отказ (`KEY_INVALID`). При проверке подписи ключ ищется только среди ключей агента из `x-agent-code`; `kid` чужого агента — как неизвестный.
  4. **Срок и перекрытие.** `valid_to = valid_from + key_ttl_days`. При регистрации нового ключа у остальных действующих ключей агента `valid_to` сокращается до `min(valid_to, now + key_overlap_days)` (A2 п. 5.3). Ключ с наступившим `valid_to` — `EXPIRED`; статус вычисляется на момент проверки.
  5. **Отзыв.** Отозвать можно любой свой ключ, включая последний действующий: компрометация важнее доступности; новый ключ затем регистрирует оператор агента вне ПАО. Отзыв необратим; отозванный `kid` не возвращается. Действует на следующую проверку подписи (A2 п. 5.4, инвариант 8); авторизованное до отзыва исполняется.
  6. **Порядок проверки обращения ПАО:**
     1. `x-agent-code` нет или агента нет в реестре — `AGENT_UNKNOWN` (401);
     2. подпись через `agentic-core` `verifyRequest` с ключами только этого агента: состав компонентов, `content-digest` (у запроса без тела — от пустого тела, РП16), окно `signature_skew_sec`, повтор `x-nonce`, неизвестный у агента `kid`, несовпадение подписи — `SIGNATURE_INVALID` (401); ключ отозван или истёк — `AGENT_KEY_REVOKED` (401; отдельного кода истечения в ПАО нет). Nonce запоминается только после успешной проверки, в паре «агент + nonce», не меньше чем на 2 × `signature_skew_sec`;
     3. статус агента: `SUSPENDED` или `EXCLUDED` — `AGENT_SUSPENDED` (403) на все методы, кроме `GET /pao/v1/agent`: по нему агент узнаёт свой статус.
     Ошибка любой ступени — отказ (инвариант 3).
  7. **Тело ошибки** — строго по ПАО §6: `code`, `message`, `norm`, `retry`; HTTP и `retry` — из `x-pao-errors`. Поля RFC 9457 (`type`, `title`, `status`) — решением в PS-05, до него не добавляются.
- **Почему:** `POST /pao/v1/agent/keys` требует подписи действующим ключом, поэтому первый ключ может прийти только с допуском; если ключ генерирует Платформа, она знает закрытый ключ агента и подпись перестаёт доказывать, что обращался агент. Единая выдавшая сторона снимает вопрос «кто может выдавать коды» (STATUS «Открыто»): один реестр — одно пространство имён, равные условия для операторов (A6 п. 2.1). Отпечаток RFC 7638 вычисляется из ключа, не зависит от порядка регистрации и годится как `kid` каталога JWKS (РП22). `verifyRequest` в `agentic-core` ищет ключ только по `kid` — без привязки к `x-agent-code` агент A подписывал бы обращения за агента B своим ключом (инвариант 5); nonce проверяется до подписи, поэтому запоминать его до проверки — значит позволять неподписанным запросам занимать чужие nonce. Без исключения для `GET /pao/v1/agent` приостановленный агент не узнает свой статус, и перечень статусов `AgentSelf` теряет смысл.
- **Что меняет:** SPEC §3 «Реестр (П1)» — п. «Код агента», «Основания отказа», новые п. «Ключи», «Проверка обращения ПАО»; ФП1, ФП2 — ссылка на РП23; AGENT-PROTOCOL §2 — пример `keyid` по RFC 8037 прил. A.3 (редакционно, ПАО остаётся 1.2.0, `agent-protocol.yaml` не меняется); РП21 — пометка; `src/registry`, `src/pao`; STATUS — «Открыто» (выдавшая сторона снята), расхождение №10. ПАО не меняется: `Key`, `AgentSelf`, коды ошибок и их `retry` прежние.
- **Отменяет:** РП21 п. 1 в части выдавшей стороны («всё перед ними — выдавшая сторона»): грамматика прежняя, сторона только `nspk:agent`. РП21 п. 2 дополняется: `KEY_INVALID`, поля `alg`, `public_key`.
- **Дополнения (11.10.2026, аудиты PS-04; решение владельца):**

То же нужно в `ed25519Verifier` agentic-core — расхождение №11, CO-1.
  2. К п. 4–5 — **статус агента и ключи.** Исключённому (`EXCLUDED`) агенту новый ключ не регистрируется; приостановленному (`SUSPENDED`) — можно: смена ключа после компрометации. Проверка статуса неделима с добавлением ключа: условие вставки — версия записи агента, по которой проверен статус; изменилась — конкурентное изменение, ключ не добавлен.
  3. К п. 5 — **повторный отзыв** уже отозванного ключа не ошибка: возвращается тот же отозванный ключ с прежним `revoked_at`.
  4. К п. 6 — **сбой источника.** Сбой реестра или ключей на любой ступени — `UPSTREAM_UNAVAILABLE` (503, `same_key`, `Retry-After` по РП24), а не ошибка агента: при чтении записи агента — до `AGENT_UNKNOWN`, при поиске ключа — внутри ступени подписи. Nonce не запоминается; причина — в журнал процесса Платформы, агенту не передаётся. Прочие исключения проверки — `SIGNATURE_INVALID`.
  5. К п. 6.2 — **порядок внутри ступени подписи** задаёт `agentic-core` `verifyRequest`: состав компонентов, digest, окно, nonce, затем статус ключа, затем подпись. Поэтому `AGENT_KEY_REVOKED` приходит и на неподписанное обращение с отозванным `kid`. Принимается: статус ключа не секрет — ключи агентов доступны участникам (A2 п. 5.2; каталог JWKS, РП22). Перестановка — в agentic-core, если понадобится.
- **Дополнение (12.10.2026, расхождение №13; решение владельца):**
  6. К п. 2 — **каноническая запись `public_key`.** `public_key` принимается только в канонической записи base64 (RFC 4648 §3.5): строка совпадает с повторным кодированием своих байтов. Иная запись — лишние биты перед «=», без дополнения, пробелы и переводы строк, алфавит base64url — `KEY_INVALID`. **Почему:** иначе у одного ключа несколько строк (`…URo=` и `…URp=`); повтор отсекается по `kid`, но реестр хранил и отдавал в `GET /pao/v1/agent` присланную строку, и участник, сравнивающий ключи строками, видел бы у одного ключа две записи (инвариант 5, A2 п. 5.2). Нашёл агент (его расхождение № 8). **Что меняет:** SPEC §3 «Реестр (П1)», п. «Ключи»; `src/registry/keys.ts` (`spki`); `tests/unit/registry-keys.test.ts`, в том числе вектор y = p + 3 для проверки y < p (дополнение 1); `package.json` — `version` 0.1.1, тег `v0.1.1` после слияния (РП25 п. 5); STATUS — расхождение №13, «Передача агенту». ПАО не меняется: `Key.public_key` — `string`, ПАО 1.2.0, `agent-protocol.yaml` прежний. **Отменяет:** ничего.
- **Дополнение (16.10.2026, `/audit` К2.4 № 4; решение владельца):**
  7. К п. 3 — **идемпотентность ресурса.** Тот же агент регистрирует **свой действующий** (`ACTIVE`) ключ повторно — `register` возвращает существующий ключ без изменений: новой записи нет, сроки остальных ключей повторно не сокращаются. По ПАО — 201 с текущим `Key` (тот же `kid`), как при первой регистрации: ответ повтора совпадает с первым.

     - Одновременная вставка того же ключа тем же агентом (`KeyTakenError` хранилища) — перечитывание: свой действующий — тот же ответ, иначе `KEY_INVALID`.

     - **Почему:** если база падает после записи ключа, но до записи результата идемпотентности, по истечении аренды (60 с) повтор с тем же `Idempotency-Key` исполнялся заново и получал 422 по своему же ключу — агент считал бы ключ непринятым, хотя он действует. С идемпотентностью ресурса повтор получает тот же `Key`. Перебор чужих ключей это не открывает: свой ключ агент знает, чужой — по-прежнему `KEY_INVALID`.
     - **Проверка:** `pao-keys.test.ts`, `registry-keys.test.ts` — повтор с другим `Idempotency-Key` → 201 тот же `kid`, ключей и сроков не прибавилось; «потерянный ответ» → 201; чужой и свой отозванный → 422; свой истёкший → `TAKEN`. ПАО не меняется.

### РП24. Retry-After для ответов 503 ПАО

- **Решение:** стендовый параметр **`unavailable_retry_after_sec`** — значение заголовка `Retry-After` (секунды) для любого ответа ПАО с HTTP 503: `UPSTREAM_UNAVAILABLE` (с PS-04: сбой реестра или ключей при проверке обращения) и `STATE_UNAVAILABLE` (с PS-10). Параметр назван по ответу, а не по коду: новый код с HTTP 503 в `x-pao-errors` получает тот же `Retry-After` без нового параметра. Стенд — 1. Граница — целое 0…30; вне границы — отказ запуска (РП20). `Retry-After` для `RATE_LIMITED` (429) этим параметром не задаётся — вычисляется по лимиту частоты (PS-05).
- **Почему:** ПАО §2 требует `Retry-After` и с ответами 503 (РП16), а значения не было ни в ПАО, ни в PARAMS: после аудита PS-04 (№2) Платформа отвечала `UPSTREAM_UNAVAILABLE` без заголовка, то есть с нарушением ПАО. Значение в коде запрещено («В коде — только из конфигурации»). Ноль допустим схемой ПАО (`minimum: 0`) и означает «повторить сразу». Верхняя граница 30 — `maxRetryAfterSec` клиента ПАО agentic-core по умолчанию: `Retry-After` больше него эталонный клиент отвергает и отдаёт ошибку вызывающему вместо повтора; значение, которое эталонный клиент отвергнет, конфигурация Платформы принимать не должна.
- **Что меняет:** PARAMS.md — строка в таблице, правило в «Границах», журнал изменений; `config/params.stand.json`; `src/shared/config.ts` (`Params`, правило `int(0, 30)`); `src/pao/routes.ts` — `Retry-After` у всех ответов 503; тесты загрузчика и маршрута. ПАО не меняется: заголовок `Retry-After` у ответа-ошибки уже описан в `agent-protocol.yaml` (РП16). В `/.well-known/pao-configuration` параметр для агентов — вместе с остальными стендовыми (PS-05). Изменение `maxRetryAfterSec` в agentic-core — повод пересмотреть границу.
- **Отменяет:** —

### РП25. Стенд Платформы для тестов агента

- **Решение:**
  1. Платформа экспортирует **стенд для тестов** — `agentic-ps-platform/stand` (`src/stand`): среда dev (в одном процессе внутри теста агента), контур ключей sandbox (ed25519, РП23). Песочницей (средой sandbox) стенд не является. В стенде — реестр агентов, ключи и проверка обращений ПАО в памяти, сервер `buildServer` на стендовых параметрах `config/params.stand.json` Платформы, подставляемые часы, допуск агента по заявлению (РП21, РП23), запуск на свободном порту. Назначение — совместный тест С0 в репозитории агента (Р24 агента, вариант А): агент вносит себя в реестр стенда своим `public_key` и обращается к `GET /pao/v1/agent` клиентом ПАО agentic-core по HTTP.
  2. **Стенд — тестовый интерфейс, а не публичный контракт.** Публичный контракт для агентов — только ПАО (инвариант 10). Сигнатура стенда может меняться между тегами Платформы без правил версий ПАО; изменение записывается в STATUS, раздел «Передача агенту».
  3. **Оператор при допуске — от вызывающего.** Так стенд обходит отсутствие аутентификации операторов (расхождение №9). Это допустимо только в стенде. Рабочий сервер (`src/main.ts` и весь его граф импортов) `src/stand` не импортирует. Это проверяет тест в `tests`, комментария недостаточно. HTTP-допуска стенд не добавляет.
  4. **Сборка при установке из git:** скрипт `prepare` собирает `dist`. В пакет входят `dist` и `config/params.stand.json`. Путь к параметрам по умолчанию считается от корня пакета Платформы, а не от текущего каталога: иначе в чужом репозитории прочитается чужой `config/` (инвариант 3). `PARAMS_PATH` по-прежнему имеет приоритет.
  5. **Версии — по тегам Платформы.** Агент подключает стенд по `git+https` с тегом. Первый тег — `v0.1.0`, `version` в `package.json` — 0.1.0. Теги ставит владелец.
  6. **Срок.** Стенд закрывает только С0 и тесты агента до С2. К С2 его заменяет песочница отдельным процессом с проверкой чёрным ящиком по HTTP (Р24 агента, вариант Б). Приёмка агента (SPEC §11 п. 6) идёт только против песочницы, стенд для неё не годится.
- **Почему:** поднять сервер в тесте агента — самый быстрый путь к С0, и проверяется ровно тот код Платформы, который проверяет подпись (`agentic-core` `verifyRequest` через `PaoRequestVerifier`). Копия этого кода в агенте проверяла бы саму себя. Допуск с оператором от вызывающего — обход нормы (инвариант 5), поэтому граница «стенд ≠ рабочий сервер» доказывается тестом, а не соглашением. Сборка при установке нужна потому, что `dist` не хранится в git. Agentic-core подключается так же, через `prepare`.
- **Что меняет:** ARCHITECTURE «Среды» — строка «стенд для тестов агента»; SPEC §8 «Среды» — одна фраза; PARAMS.md — строка о `PARAMS_PATH` (путь по умолчанию от корня пакета); `src/stand`, `src/shared/config.ts` (путь по умолчанию), `package.json` (`version`, `exports`, `files` без `dist/main.*`, `prepare`, `test:install`), `package-lock.json` (версия); `tsconfig.build.json` (`declaration` — типы для агента); `tests/support/stand.ts` использует `src/stand`; `tests/unit/stand-boundary.test.ts` — граф импортов `src/main.ts`; `tests/unit/stand.test.ts`; `scripts/check-install.mjs` — установка из `npm pack` и по `git+https`; `.github/workflows/ci.yml` — оба шага установки; STATUS — «Передача агенту». ПАО не меняется.
- **Отменяет:** —

### РП26. Ключи Платформы: подпись ответов и событий

- **Решение:**
  1. **Два ключа по назначению:** подпись ответов ПАО и подпись событий агенту. Компрометация одного не затрагивает другой.
  2. **Алгоритм и хранение.** Песочница — ed25519, пара генерируется при старте во временный каталог; закрытый ключ не попадает в журнал процесса, ответы и репозиторий. Контур оператора — ГОСТ Р 34.10-2012 в HSM, ключ не извлекается (РП5). Ключи Платформы песочницы переходят в постоянное хранилище вместе с реестром в PS-05 (после CO-2, п. 7).
  3. **Формат подписи — RFC 9421**, как у обращений агента: заголовки `Signature-Input` и `Signature` с меткой `platform`; параметры `keyid` (`kid` ключа Платформы), `alg` (по ключу), `created`. Компоненты ответа: `@status`, `content-digest`, `x-agent-code`, `@method;req`, `@path;req`, `x-nonce;req` — ответ привязан к запросу, старый подписанный ответ к другому запросу не подставить; события: `content-digest`, `x-event-id`, `x-agent-code`. Подпись с `created` вне окна `signature_skew_sec` агент отвергает. Подпись Платформы вводится с ПАО 1.3.0 (→ 1.4.0, РП31; → 1.5.0, РП37) (п. 8); в 1.2.0 ответы и события не подписываются, имя `Platform-Signature` в AGENT-PROTOCOL §2 заменяется описанием формата 1.3.0 (→ 1.4.0, РП31; → 1.5.0, РП37) (в `agent-protocol.yaml` 1.2.0 этого заголовка нет, Платформа его не отправляла).
  4. **Событие подписывается при каждой отправке** текущим ключом событий, а не при создании: повторная доставка после ротации или перезапуска проверяется опубликованным ключом, старые закрытые ключи не хранятся.
  5. **Публикация:** открытые ключи — в `platform_keys` `/.well-known/pao-configuration` (схема `Key`); `kid` — отпечаток JWK по RFC 7638, как у агентов (РП23 п. 3). Назначение ключа в конфигурации — новое поле `use` (`response` / `event`) с ПАО 1.3.0 (→ 1.4.0, РП31; → 1.5.0, РП37) (п. 8); агент проверяет назначение: ключ без `use` или с чужим `use` — отказ.
  6. **Ротация и компрометация.** Новый ключ публикуется до начала использования; старый остаётся опубликованным на период перекрытия. Скомпрометированный — со статусом `REVOKED`. Агент кэширует `platform_keys`; неизвестный `kid` — одно перечитывание конфигурации, затем отказ; отозванный или истёкший ключ — отказ (инвариант 3). Сроки — параметры `platform_key_ttl_days`, `platform_key_overlap_days`: в PARAMS и `params.stand.json` вносятся в PS-05, когда появляется код, который их читает. Перечитывание по неизвестному `kid` — не чаще одного раза в `platform_keys_refetch_min_sec` (дополнение РП22 п. 3).
  7. **Постоянное хранилище.** До CO-1, CO-2 перезапуск песочницы меняет ключи Платформы; это ограничение — в SECURITY.md §6.
  8. **ПАО.** Правки `agent-protocol.yaml` (заголовки подписи у ответов, `use` у ключа) объединяются с заделами PS-05 в одно совместимое изменение ПАО 1.3.0 (→ 1.4.0, РП31; → 1.5.0, РП37) (AGENT-PROTOCOL §7: только новые необязательные поля и заголовки) — тогда же копия спецификации и типы в agentic-core.
- **Почему:** подпись Платформы в ПАО объявлена, но формат не определён — агент не может её проверить (ФП13, инвариант 9). RFC 9421 уже используется для обращений агента: одна база подписи, один разбор заголовков, `signatureBase` agentic-core. Отдельный ключ событий ограничивает ущерб: украденный ключ ответов не позволяет рассылать события. Подпись при отправке убирает хранение старых закрытых ключей. Одно изменение ПАО вместо нескольких — одна синхронизация с agentic-core.
- **Что меняет:** SECURITY.md §4; AGENT-PROTOCOL §2 — описание формата ПАО 1.3.0 (→ 1.4.0, РП31; → 1.5.0, РП37) с пометкой версии (YAML и версия ПАО — в PS-05); копии ПАО у агента (`agentic-buyer-ref/docs/core/protocol/`) и в agentic-core (`spec/`, `PaoClient`) — синхронизация при выпуске 1.3.0 (→ 1.4.0, РП31; → 1.5.0, РП37); STATUS «Передача агенту»; SPEC §3 «П9»; STATUS — «Заделы» к PS-05, PS-08, после CO-1/CO-2; задача к agentic-core — проверка подписи ответа и события (`verifyResponse`) для агента (AG-06).
- **Отменяет:** —

### РП27. mTLS песочницы

- **Решение:**
  1. **УЦ песочницы — у Платформы**, ключ ECDSA P-256 (поддержка в TLS шире, чем у ed25519). Пара генерируется при старте; ключ УЦ переходит в постоянное хранилище вместе с реестром и ключами Платформы в PS-05 (после CO-2) — иначе после перезапуска выданные сертификаты агентов не проверяются. До переезда: **перезапуск песочницы = повторный допуск агентов** (SECURITY.md §6).
  2. **Ключ сертификата генерирует оператор агента**, Платформа получает CSR (как ключ подписи, РП23 п. 2). Сертификат агента выдаётся в решении о допуске (ПС01): SAN URI `urn:nspk:agent:<id>:v<N>` — код агента. Сертификат оператора агента — SAN URI `urn:nspk:operator:<id>` (РП28).
  3. **Ступень 0 проверки обращения ПАО** (до РП23 п. 6.1): нет сертификата клиента, он выпущен не УЦ песочницы, вид субъекта не агент или код агента из сертификата не равен `x-agent-code` — `AGENT_UNKNOWN` (401); сертификат истёк или отозван — `AGENT_KEY_REVOKED` (401, `new_key`: исправимо новым сертификатом); сбой чтения списка отзыва — `UPSTREAM_UNAVAILABLE` (503, РП23 доп. 4). Новых кодов нет; описания `AGENT_UNKNOWN` и `AGENT_KEY_REVOKED` в `x-pao-errors` уточняются в ПАО 1.3.0 (→ 1.4.0, РП31; → 1.5.0, РП37) (РП26 п. 8). TLS запрашивает сертификат, но рукопожатие без него не обрывает: решение — в приложении, после грубого лимита по адресу (PS-05). `/.well-known/pao-configuration` и `/health` — без сертификата клиента.
  4. **Отзыв сертификата** — только при компрометации ключа сертификата и по заявлению оператора агента. Приостановление и исключение сертификат не отзывают: их режет статус (РП23 п. 6.3), и агент узнаёт свой статус через `GET /pao/v1/agent`. Список отзыва — в реестре рядом с записью агента; распространяется как отзыв ключа (инвариант 8).
  5. **Стенд dev (РП25) — без mTLS**: работает внутри процесса теста агента и песочницей не является.
  6. **Контур оператора** — ГОСТ TLS, сертификаты УЦ оператора; требования — SEC-2.
  7. **Код** — PS-05 (TLS шлюза, ступень 0, выпуск по CSR при допуске); ПС01 `it.todo` «сертификат mTLS» закрывается там.
- **Почему:** ПАО §2 обещает «сертификат выдаётся при допуске и связан с `agent_code`», но не говорит, кто выпускает и как связывает. Код в SAN проверяется без сопоставительных таблиц. Ключ сертификата у оператора — тот же довод, что у ключа подписи: знающая закрытый ключ сторона может выдать себя за агента. `AGENT_UNKNOWN` на несовпадение сертификата и кода не расширяет перечень ошибок ПАО.
- **Что меняет:** SECURITY.md §5, §6; AGENT-PROTOCOL §2 (описание mTLS песочницы; коды — существующие); SPEC §3 «П1» и «П9»; РП5 — пометка; STATUS — ПС01, «Заделы» к PS-05 и после CO-1/CO-2, «Передача агенту»; копия ПАО у агента — при 1.3.0 (→ 1.4.0, РП31; → 1.5.0, РП37).
- **Отменяет:** —

### РП28. Аутентификация операторов агентов

- **Решение:**
  1. **Оператор агента — отдельный субъект** со своим сертификатом mTLS от УЦ песочницы (РП27 п. 2). Агентский сертификат не даёт доступа к API операторов, операторский — к ПАО.
  2. **Учётная запись оператора:** в песочнице — по заявке, на одинаковых условиях для эталонного и сторонних операторов, только коды песочницы (РП17, A6 п. 2.1); в контуре оператора — по договору с Оператором Системы, вне Платформы, на публичных и одинаковых для всех операторов условиях (A6 п. 2.1, РП17): дискреционного фильтра до закрытого перечня РП21 нет.
  3. **Оператор — только из аутентифицированного контекста.** `AgentRegistry.admit` получает оператора в виде контекста, который создаёт только слой аутентификации; строку от вызывающего не принимает. Исключение — стенд dev (РП25 п. 3).
  4. **Выдача сторонним операторам** — та же процедура: заявка, сертификат оператора, допуск агента с ключом подписи и CSR (РП23, РП27), набор соответствия для контура оператора (РП17, PS-29).

### РП29. Ограничение частоты обращений к витринам эмулятора продавцов

- **Решение:**
  1. Все маршруты `/v1` эмулятора продавцов ограничены по частоте **по адресу** обращения — до опознания агента и до чтения каталога ключей, поэтому неподписанный поток ограничен тоже. Превышение — 429 с `Retry-After`, тело — только `{code: "RATE_LIMITED"}`, как у остальных отказов витрины.
  2. Механизм — `@fastify/rate-limit`, точная версия `11.2.0` (опубликована 29.07.2026). Транзитивные зависимости моложе 14 дней закрепляются через `overrides` на последних версиях старше 14 дней: `fastify-plugin` `6.0.0`, `ip-address` `10.7.2`. Установка — `npm ci`; в lock-файле agentic-core — `git+https`.
  3. Значение — стендовый параметр `merchant_rate_limit_per_min` (PARAMS, `config/params.stand.json`, загрузчик; целое ≥ 1). На стенде — 6 000 в минуту с адреса: щедро, чтобы тесты агента (AG-04, AG-09) не упирались в лимит. Значение для открытой песочницы — по прогону PS-26.
  4. Шлюз ПАО (PS-05) берёт ту же библиотеку для грубого лимита по адресу до проверки подписи; лимит по уровню агента после проверки — `RATE_LIMITED` ПАО §2, значения — отдельным решением в PS-05.
  5. Ключ лимита — `req.ip`. За обратным прокси он станет адресом прокси, и лимит окажется общим на всех агентов: настройка `trustProxy` и доверенных адресов — в PS-05 (шлюз) и PS-26 (открытая песочница).
- **Почему:** CodeQL `js/missing-rate-limiting` (№ 82, high) на `POST /v1/shops/{id}/orders/{order_id}/payment`. В PS-26 витрины и эквайрер войдут в открытую песочницу для сторонних агентов: без лимита это настоящая дыра, а не ложное срабатывание. Красный CodeQL в main до PS-05 (ждёт CO-2) обесценил бы проверку, а точке С6 нужен ноль открытых находок. Библиотека выбирается один раз для витрин и шлюза; CodeQL распознаёт известные библиотеки лимита, самописный счётчик находку не закрывает.

### РП30. Хранилища шлюза ПАО на PostgreSQL ядра: nonce и идемпотентность

- **Решение:**
  1. **Проверка подписи — `verifyRequestAsync` agentic-core v0.3.0.** Порядок прежний (РП23 п. 6): агент → подпись ключами только агента из `x-agent-code` → nonce → статус. Nonce проверяется и запоминается **одной операцией** `seen()` и только после верной подписи (Ш4 сохраняется). Сбой хранилища nonce, как и сбой реестра, — `UPSTREAM_UNAVAILABLE` (503, `Retry-After` по РП24), а не `SIGNATURE_INVALID`; обращение не принимается (fail-closed, инвариант 3).
  2. **Nonce — `PgNonceStore` с одной областью `scope = "pao"`**, значение — `<agent_code> <x-nonce>` через пробел, срок хранения `retainMs = 2 × signature_skew_sec` (РП23 п. 6; `skewSec` передаётся ядру для проверки).
     - Однозначность: пробела нет в грамматике кода агента (РП21: части `[a-z0-9-]` через «:»), поэтому разбор — по **первому** пробелу; `x-nonce` может содержать что угодно, включая пробелы. Разделитель «:» не годится: код агента содержит «:» с нефиксированным числом частей, и склейка `a:b:v1` + `:` + `z:v3:q` совпадает с `a:b:v1:z:v3` + `:` + `q`.
     - Одна область вместо областей по агентам: одна `purge()` без обхода реестра, исключённый агент не забывается.
     - Очистка — `purge()` раз в `signature_skew_sec` по таймеру процесса. Сбой очистки пишется в журнал процесса и на приём не влияет: окно проверяется по `x-timestamp`.
  3. **Идемпотентность — `PgIdempotencyStore` с областью `pao:<agent_code>` и ключом `Idempotency-Key`** (пара «агент + ключ», Ш16). Область по агенту здесь уместна: она входит в первичный ключ таблицы, вопроса разделителя нет.
     - Хэш тела — от `{method, path, query, body}`: сырые путь, запрос и байты тела. Тот же ключ на другом методе или пути — `IDEMPOTENCY_CONFLICT`, а не чужой ответ.
     - Сохраняется ответ обработчика (статус и тело ПАО, 2xx и 4xx); повтор возвращает его с тем же статусом. Сбой источника внутри обработчика (5xx) не сохраняется: захват снимается, повтор исполняется заново.
     - Тот же ключ, пока первое обращение выполняется (`IdempotencyInProgress`), — `UPSTREAM_UNAVAILABLE` 503 с `Retry-After` (`same_key`); новых кодов в ПАО 1.2.0 нет. Отдельный код — кандидат в ПАО 1.3.0 (→ 1.4.0, РП31; → 1.5.0, РП37) (STATUS, «Заделы к PS-05»).
     - Сбой хранилища идемпотентности — 503 `UPSTREAM_UNAVAILABLE` **до** обработчика: без захвата ключа изменение не выполняется. Без `Idempotency-Key` у изменяющего метода — `IDEMPOTENCY_REQUIRED` (ПАО §6) до обработчика.
     - Срок хранения результата — стендовый параметр `idempotency_ttl_sec` = 86 400 (24 ч, значение ядра по умолчанию), целое ≥ 60.
     - Аренда захвата `leaseMs` — значение ядра по умолчанию, 60 с, константой кода, не параметром. Условие К6 ядра: аренда не больше ttl (отсюда граница `idempotency_ttl_sec` ≥ 60) и больше самой долгой операции под ключом. Обработчики шлюза — запись в реестр без внешних вызовов (`POST /pao/v1/agent/keys` — заведомо). Обработчик с внешним вызовом — пересмотреть аренду в его задаче.
     - **Ограничение:** у `PgIdempotencyStore` ядра нет очистки — строки с истёкшим ttl перезахватываются, но не удаляются, и таблица `core_idempotency` растёт без предела. Для песочницы допустимо. Очистка — `purge(before)` в ядре (STATUS, «Заделы к agentic-core»). Прямой `DELETE` по таблице ядра из Платформы не делается: это обход контракта ядра.
  4. **`SqlClient` — `pg.Pool`** из `DATABASE_URL`. `pg` — точная версия `8.23.0` (08.08.2026, правило 14 дней РП29 п. 2), `@types/pg` `8.23.1` — в devDependencies. Пул закрывается вместе с сервером.
  5. **Миграции — `applyMigrations` ядра при запуске**, файлы 001–004 ядра (журнал, удержания, идемпотентность, nonce). Своего средства миграций у Платформы пока нет; до него схему применяет один экземпляр. Сбой миграции — отказ запуска. Одновременный запуск двух экземпляров на пустой базе не поддерживается: в песочнице экземпляр один (SECURITY.md §6). Своё средство и миграции Платформы — с переездом реестра (PS-06).
  6. **Без базы:**
     - среда `sandbox` без `DATABASE_URL` — **отказ запуска** (fail-closed);
     - `dev` без `DATABASE_URL` — хранилища ядра в памяти (`AsyncMemoryNonceStore`, `AsyncMemoryIdempotencyStore`, тот же договор) с предупреждением «один процесс»; `dev` с `DATABASE_URL` — PostgreSQL;
     - стенд для агента (`createStand`, РП25) — всегда в памяти: он живёт в процессе теста агента.
  7. **Проверка.** PG-тесты пропускаются без `DATABASE_URL`, как в ядре. В CI — сервис `postgres:16` в каждой ветке матрицы; страж в CI без `DATABASE_URL` — красный (PostgreSQL только в CI, решение владельца 15.10.2026). Обязательные проверки:
     - повтор nonce после «перезапуска» (новый пул и проверяющий на той же базе) — `SIGNATURE_INVALID`;
     - из 20 одновременных одинаковых обращений принято одно;
     - сбой базы — 503;
     - тот же `Idempotency-Key` у другого агента — не повтор;
     - другое тело — `IDEMPOTENCY_CONFLICT`.
- **Почему:** «Условие CO-2» (STATUS «Открыто», аудит PS-04 №4): nonce в памяти процесса повторяется после перезапуска и на втором экземпляре (Ш3а). Ш16: ключ идемпотентности без агента отдал бы чужой результат. Хранилища ядра v0.3.0 (CO-2) дают одну атомарную команду на проверку с записью и захват ключа с арендой — та же реализация у Платформы и у потребителей ядра, без своей второй. Ревью из чата к PR #29 (план, доп. 1–2; текст РП30, доп. 1–2) — одна область nonce, хэш с методом и путём, ограничение роста таблицы, аренда явно.
- **Что меняет:**

### РП31. Коды отказа ПАО: неполный запрос и недопустимый ключ (ПАО 1.3.0)

- **Решение:**
  1. **`REQUEST_INVALID`** — 400, `retry: after_fix`. Тело изменяющего метода не по схеме метода: не JSON, нет обязательного поля, неверный тип или значение вне перечня. Тело ошибки — ПАО §6, в `message` нет фрагментов присланного тела. Проверка — до обработчика и до захвата ключа идемпотентности: неполный запрос ключ не занимает. Закрывает № 15: ПС04 «400 при отсутствии реквизита» → `400 REQUEST_INVALID`.
  2. **`KEY_INVALID`** — 422, `retry: after_fix`. Ключ в `POST /pao/v1/agent/keys` не принят по РП23 п. 2–3 и дополнениям 1 и 6: `alg` не из перечня контура, ключ не разбирается, неканоническая запись `public_key`, слабый ключ, ключ уже зарегистрирован — у себя, у другого агента или после отзыва. Код один, причина агенту не раскрывается (как `KEY_INVALID` при допуске): исправление одно — новая пара ключей. Раскрытие «ключ уже у другого агента» позволило бы по ответам перебирать чужие ключи. Причина — в журнале процесса. Ответ сохраняется под ключом идемпотентности (4xx, РП30 п. 3).
  3. **Ответы методов** (`agent-protocol.yaml`): `POST /pao/v1/agent/keys` — 201 `Key`; 400 `REQUEST_INVALID` / `IDEMPOTENCY_REQUIRED`; 401; 409 `IDEMPOTENCY_CONFLICT`; 422 `KEY_INVALID`; 503 `UPSTREAM_UNAVAILABLE`. `POST /pao/v1/mandates` — 400 `REQUEST_INVALID` (ответ 400 уже объявлен).
  4. **Совместимость (AGENT-PROTOCOL §7).** Агент на ПАО 1.2.0 на неизвестный код останавливается: адаптер `pao` агента — `UNKNOWN`, одно обращение (fail-closed); `PaoClient` ядра берёт `retry` из тела, при `after_fix` не повторяет. Поведение совпадает с `after_fix` и безопасно. Дополнение §7: «новое значение `ErrorCode` с `retry` `after_fix` или `never` — совместимо: агент на неизвестный код останавливается». С `same_key` — нет: агент 1.2.0 не повторит там, где повтор ожидается.
  5. **ПАО 1.3.0 — только п. 1–4** (вариант (а), решение владельца 16.10.2026). Прежний пакет «ПАО 1.3.0» переименовывается в **ПАО 1.4.0** во всех трёх репозиториях: РП26 п. 8 (подпись ответов, `use` у ключа Платформы), РП27 п. 3 (`CERTIFICATE_INVALID`), РП22 (схема `PaymentPackage`), заделы PS-05 (общие 401/429/503, описание `public_key`), пакет агента (`currency`, `as_of`, порядок отзыва, `Mandate.agent_code`, `Key.valid_to`, `AgentSelf.class`), `REQUEST_IN_PROGRESS` и срок идемпотентности (РП30). В решениях РП22, РП26, РП27, РП30 «1.3.0» помечено «→ 1.4.0, РП31».
  6. **Порядок выпуска.** Платформа сверяет набор кодов с ядром (`ERROR_CODES_MATCH_CORE`, `src/shared/pao.ts`), ядро собирает типы и `PAO_ERRORS` из спецификации Платформы (`PAO_SPEC_SHA256`):
     1. текст 1.3.0 — `docs/proposals/agent-protocol-1.3.0.yaml` в ветке PS-05 (вне `docs/core`: `gen:shared` и тесты его не читают);
     2. короткая сессия ядра (16.10, первой): типы и `PAO_ERRORS` из этого файла, тег (новые значения перечня — добавление, не ломающее);
     3. платформа одним коммитом: файл → `docs/core/agent-protocol.yaml` побайтно (тот же SHA-256), §6 и §7 AGENT-PROTOCOL, `gen:shared`, тег ядра, ПС04 «Ожидаемо», SPEC §3, К2.4;
     4. агент — копия ПАО 1.3.0 и `PAO_SPEC_SHA256` (Р20), коды `after_fix` — в таблицу адаптера.
- **Почему:** № 15 — ПС04 требует 400, а кода нет; К2.4 — отказ на недопустимый ключ при регистрации по HTTP (РП23; ревью из чата к плану PR #29, доп. 2) по ПАО §6 не сформировать: `KEY_INVALID` был только основанием отказа в допуске. Новый код вместо ближайшего существующего: `SIGNATURE_INVALID` или `IDEMPOTENCY_REQUIRED` на плохое тело заставили бы агента менять ключ или повторять, а `after_fix` говорит «исправь запрос». Вариант (а) — регистрация ключа по HTTP для AG-03 после одного тега ядра, а не после всего пакета подписи ответов (неделя 43).

### РП34. Чтение мандата по ПАО: ответы `GET /pao/v1/mandates/{id}` (PS-06 К2.2)

### РП35. Статус CART при отзыве и истечении родителя; гонка «проверка родителя → запись CART» (PS-06 К2.3)

Решение владельца 17.10.2026 (PR #30, чат, окно Б); `/audit` К1.2 № 8, К1.3 № 6.

- **Решение:**
  1. **Статус CART под INTENT вычисляется при чтении вместе со статусом родителя**, по одному снимку цепочки корневого мандата (CART и родитель — в одной цепочке, SPEC §3):
     - собственный `REVOKED` или `REJECTED` у CART сохраняется;
     - родитель `REVOKED` (отзыв клиентом или отказ агента) или `REJECTED` → CART `REVOKED`;
     - родитель `EXPIRED` → CART `EXPIRED`;
     - иначе — собственный статус CART.
     
     `EXHAUSTED` родителя (из П3) войдёт в правило в PS-09. (РП41 п. 11: родитель `EXHAUSTED` → CART `EXHAUSTED`.) Записи потомкам не пишутся. Отзыв родителя действует на все его CART с момента записи отзыва (A7 п. 6.2–6.3).
  2. **Одно вычисление** (`withParentStatus` над свёрткой `deriveStatus`) используют `GET`, `verify`, подпись принципала (CART под не-`ACTIVE` родителем не подписывается) и ADP (PS-10). Своей проверки родителя у потребителей нет.
  3. **Ответ `POST` на CART:**
     - родитель уже отозван, отклонён или истёк на момент проверки — `409` (`MANDATE_REVOKED` / `MANDATE_EXPIRED` по РП33 п. 1). Это основной путь;
     - `201` со статусом `REVOKED` или `EXPIRED` на первый запрос — только при гонке: отзыв записан в цепочку между проверкой родителя и записью CART. Ядро перечитывает конец цепочки и пишет CART после отзыва, запись не удалить (инвариант 6), а свёртка даёт `REVOKED` с первого ответа. Повтор тем же ключом даёт тот же ответ;
     - на повтор тем же ключом после 24 ч памяти ключей (РП33 доп. п. 6) `201` несёт статус на момент повтора, поэтому `REVOKED`/`EXPIRED` возможен и без гонки, если родитель отозван позже. В пределах 24 ч повтор отдаёт сохранённый ответ со статусом первого ответа, даже если CART уже отозван через родителя. Актуальный статус — только из `GET`.
  4. **Гонка закрывается правилом п. 1**, для любого порядка записей: решает статус родителя на момент чтения, а не на момент проверки. Условная вставка в журнал ядра (РП33 доп. п. 9) — дальнейшее усиление, а не условие.
  5. **В `GET` отзыв CART через родителя и собственный отзыв не различаются**: в `Mandate` поля причины нет. Причина видна в выписке (`evidence`, часть 2 PS-06).
  6. **Совместимость (AGENT-PROTOCOL §7):** перечень `status` в `Mandate` уже содержит `REVOKED` и `EXPIRED`, схема не меняется. Меняется только смысл `201` у `POST /pao/v1/mandates`: описание ответа в `agent-protocol.yaml` дополнено. Изменение совместимо, версия ПАО остаётся 1.3.0. Агент, не проверяющий `status`, лишних полномочий не получает: подпись, `verify` и ADP берут статус из той же свёртки и отказывают. SHA-256 файла меняется — `4569a86b…` (`PAO_SPEC_SHA256` → ядру той же передачей, что РП33 и РП34).
- **Почему:** раньше статус CART учитывал только собственные записи. После отзыва или истечения INTENT корзина оставалась `PENDING_SIGNATURE` или `ACTIVE`, её можно было подписать, проверить и расходовать: нарушение A7 п. 6 и инварианта 8. Альтернатива «отзыв родителя пишет записи всем потомкам» неатомарна: сбой на середине оставляет часть потомков действительными, а гонка с одновременно записанным CART остаётся.
- **Что меняет:** `src/consent/model.ts` (`withParentStatus`), `src/consent/journal.ts` (статус CART — по снимку цепочки вместе с родителем, в том числе в ответе `POST`); `docs/core/agent-protocol.yaml` (описание `201`), `src/shared/pao-errors.generated.ts` (`PAO_SPEC_SHA256`); SPEC §3 «Журнал согласий (П2)»; AGENT-PROTOCOL §3; STATUS «Открыто», «Передача агенту».
- **Нужно от agentic-buyer-ref:** после `201` на `POST /pao/v1/mandates` агент **обязательно** проверяет `status` в ответе. `REVOKED` или `EXPIRED` означает отказ, корзиной пользоваться нельзя. Статус CART меняется вместе с родителем — актуальный статус берётся из `GET`; повтор `POST` в пределах 24 ч отдаёт сохранённый ответ и об отзыве не говорит.
- **Отменяет:** —

### РП36. Порт «банк»: уровень интеграции пилота, протокол участника, подпись клиента удостоверяет банк, точка входа подписи (PS-06 К2.4, Б2)

Решение владельца 18.10.2026 (PR #30, чат, окно Б).

- **Решение:**
  1. **Уровень интеграции пилота — А.** Решение ADP принимается до выпуска реквизита; банк выпускает одноразовую виртуальную карту с лимитом ровно на заказ, дальше авторизация идёт обычным путём (продавец → эквайрер → ОПКЦ → эмитент, РП2). От банка нужно: выпуск карты по API, лимит, вебхуки. Уровень Б (вызов ADP из авторизации, ПИ-1) — позже.
  2. **Форма порта — собственный канонический протокол участника и адаптеры.** Платформа говорит с банком на своём протоколе участника (ПИ-8, каноническая модель); под него — адаптер банка, адаптер песочницы (эмуляторы) и пустой слот НСПК. Для каждого адаптера — набор тестов соответствия. Платформа не зависит от API конкретного банка; форматы банка — только в адаптере (`src/adapters/`, РП6).
  3. **Подпись клиента удостоверяет банк.** Банк присылает подтверждение подписи клиента, подписанное ключом банка над хэшем мандата — `Mandate.hash`, хэш записи `MANDATE_REQUESTED` в журнале (исправлено в К2.4: ранее ошибочно `terms_hash`; см. дополнение п. 1). Платформа проверяет подпись банка по реестру участников. Ключей и данных входа клиентов у Платформы нет.
  4. **Точка входа подписи (К2.4) — запрос участника через шлюз участников, всегда с подписью участника.** Неаутентифицированной точки нет нигде, в том числе на стенде: эмулятор эмитента подписывает своим тестовым ключом тем же способом. Пока шлюза участников (PS-20) нет — минимальный список доверенных ключей участников в конфигурации; PS-20 его расширяет.
  5. **63-ФЗ (A7 п. 3.1–3.2).** Клиент подписывает мандат простой ЭП в приложении банка по договору клиента с банком (соглашение о простой ЭП — между клиентом и банком). Подпись банка над хэшем мандата — подтверждение этой подписи для Платформы, а не подпись клиента и не ЭП Платформы. Ключей и данных входа клиента у Платформы нет; усиленная ЭП свыше порогов (ЕСИА / УКЭП, ФП3) — тем же порядком: банк удостоверяет факт подписи, `signature_type` указывает её вид.
- **Почему:** уровень А не требует доработки авторизации у банка — пилот возможен до интеграции с процессингом. Свой протокол и адаптеры отделяют ядро от API банка (правило «только через порт»). Удостоверение подписи банком снимает с Платформы ключи и данные входа клиентов и даёт доказательство, проверяемое без банка (подпись над хэшем мандата). Точка без аутентификации даже на стенде — образец, который переносится в боевой контур.

- **Нужно от agentic-buyer-ref:** ничего нового в ПАО: подпись принципала агент видит как смену `status` мандата (`GET`, событие `mandate.signed` — PS-08).

### РП37. Порядок отзыва в мандате — от Платформы из соглашения участника; ПАО 1.4.0 (PS-06 К2.10, № 22)

Решение владельца 18.10.2026 (PR #30, вариант В; версии — ответ владельца в окне 18.10).

- **Решение:**
  1. **Порядок отзыва** (A7 п. 2.1–2.2) — ссылка на соглашение банка с клиентом: `revocation_order`, например `bank:<participant_code>:revocation:v1` (до 128 знаков `[A-Za-z0-9:._-]`). Текст для человека — у банка; в ПАО и журнале — только код.

Поле с тем же именем в теле агента игнорируется (инвариант 5): порядок отзыва определяют клиент и банк, а не агент.
  3. **В записи мандата:** `revocation_order` — в `payload` записи `MANDATE_REQUESTED`, значит, в `Mandate.hash`: банк подписывает мандат вместе с порядком отзыва (РП36 доп. п. 1), клиент видит его на экране банка.
  4. **Не задан** (участников нет) — мандат не пишется: 503 `STATE_UNAVAILABLE`, нового кода нет (fail-closed, инвариант 3). Индекс и предмет не пишутся.
  5. **Повтор** тем же `Idempotency-Key` записанного мандата — тот же мандат с **записанным** порядком отзыва: сверяются только реквизиты агента, смена конфигурации участника после записи повтор не ломает (ПАО §2; `/audit` К2.10 № 1). Прерванная запись (индекс без записи журнала), доделываемая после смены порядка у участника, — `IDEMPOTENCY_CONFLICT` (хэш реквизитов индекса не совпадает); узкий случай, агент — новым ключом после нового подтверждения.
  6. **CART наследует порядок отзыва родителя** (тот же банк, то же соглашение; `/audit` К2.10 № 2); участник при этом должен быть задан (иначе 503, fail-closed). Со вторым банком выбор для корневого мандата — по банку клиента в Б2 вместе с форматом `principal_ref`.
  6а. **Запись без порядка отзыва** (до РП37) не читается как действующая — `ConsentStateUnknown`, 503 (A7 п. 2.2: отсутствие реквизита — недействителен; `/audit` К2.10 № 3). Таких записей нет: стенд и dev — в памяти, PG CI — новая схема на прогон.
  7. **На стенде** — `bank:stand:issuer-emulator:revocation:v1` (эмулятор эмитента).
  8. **ПАО 1.4.0** (совместимо, AGENT-PROTOCOL §7; путь `/pao/v1`): `Mandate.revocation_order` — новое необязательное поле ответа (в ответах Платформы есть всегда); `Mandate.agent_code` — в `required` (Платформа и так всегда отдаёт); правило «обязательность поля ответа, которое Платформа отдавала всегда, — совместима» дописано в AGENT-PROTOCOL §7 (`/audit` К2.10 № 4). Запрос `MandateRequest` не меняется. `Evidence.mandate_chain` ссылается на `Mandate` — К2.8 отдаёт `agent_code` и `revocation_order`.
  9. **Версии ПАО:** прежний пакет «ПАО 1.4.0» (подпись ответов и событий РП26 п. 8, `use` у ключа, общие 401/403/429/503, схема `PaymentPackage`, пакет агента п. 1–4, задел РП30) — теперь **ПАО 1.5.0** во всех трёх репозиториях, по образцу РП31 п. 5: агент по номеру 1.4.0 не ждёт подписи, которой нет (SEC-1-код — Б4). Пометки «→ 1.5.0, РП37» — в РП22, РП26, РП27, РП30; AGENT-PROTOCOL §2, §4, SECURITY.md §4, STATUS.

### РП38. Отзыв мандата клиентом и агентом, `verify` и выписка (PS-06 К2.6–К2.8)

Решение владельца 18.10.2026 (PR #30, проект — комментарий PR; п. 4 — вариант А).

- **Решение:**
  1. **Отзыв клиентом — запрос участника с подписью, по одному мандату:** ПИ-8 `POST /participants/v1/mandates/{id}/revoke`, тот же порядок, что у `sign` (РП36 п. 4). Одна подпись Ed25519 ключом банка над `canonicalJson` записи `{context, participant_code, kid, mandate_id, mandate_hash, revocation_ref, revoked_at}`; `context` = `pao:participant-mandate-revocation:v1` — своя метка: подпись решения не годится как отзыв, и наоборот. Запись `MANDATE_REVOKED`, в `payload` — запись участника и подпись: в выписке видно, кто отозвал и чем удостоверено. Отказы — как у `sign`: 400 `REQUEST_INVALID`, 401 `SIGNATURE_INVALID`, 404 `MANDATE_NOT_FOUND`, 409 `MANDATE_HASH_MISMATCH`, 503.
  2. **`revoke-all` по `principal_ref` — в PS-20** (план «Россия» ред. 4): сначала привязка мандата к банку и формат `principal_ref` (РП36 доп. п. 8). **Ограничение до PS-20:** банк отзывает мандаты клиента по одному.
  3. **Отказ агента** — ПАО `POST /pao/v1/mandates/{id}/relinquish`: изменяющий метод (подпись обращения, `Idempotency-Key`), тело пустое; только свой мандат, чужой — 404 `MANDATE_NOT_FOUND`, как у `GET`. Запись `MANDATE_RELINQUISHED`, `payload` — `{agent_code, kid}` из проверенного обращения (инвариант 5). Ответ — `Mandate` со статусом после записи.
  4. **Когда отзыв пишется.** Только при `PENDING_SIGNATURE` или `ACTIVE` по свёртке `load` (у CART — вместе с родителем, РП35). `REVOKED`, `REJECTED`, `EXPIRED` — 200 с текущим статусом без записи: полномочий уже нет, повтор идемпотентен по смыслу. Отзыв родителя действует на его CART свёрткой (РП35), записей потомкам нет. Отзыв, отказ агента и решение банка по одному мандату внутри процесса — по очереди, под одним локом записи по мандату (РП36 доп. п. 4).
  5. **Свёртка: `REVOKED` поглощает последующие записи (вариант А).** После `REVOKED` записи отзыва, отказа агента и решения банка пропускаются, статус остаётся `REVOKED`; после `REJECTED` пропускаются записи отзыва и отказа. Отзыв — подтверждённая запись, последующая запись полномочий не возвращает: это не догадка (инвариант 3). Снимает 503 в гонках «отзыв против отзыва» и «подпись против отзыва» на двух экземплярах (остаточный риск РП36 доп. п. 4 в этой части); остаётся риск «две разные подписи» (503 до условной вставки ядра). Лок внутри процесса нужен для порядка записей в выписке: после отзыва нет записи решения, банк получает 409 `MANDATE_NOT_PENDING`, а не 200.
  6. **`verify` (A7 п. 9.2) — без предмета, схема не меняется:** ответ — ровно `{outcome, amount_left, valid_to, as_of}`. `outcome`: `CONFIRMED` — только `ACTIVE`; `OUT_OF_SCOPE` — `PENDING_SIGNATURE`, `REJECTED`, `REVOKED`, `EXPIRED`; `STATE_UNKNOWN` — с П3 (PS-09): журнал цел, бюджет не подтверждён. Нарушенная цепочка или неопределимый статус — 503 `STATE_UNAVAILABLE`, как у `GET` (верного `valid_to` нет). **Ограничение до PS-09:** `amount_left` = `amount_limit` у `ACTIVE` (расходования нет: реквизитов и ADP ещё нет), 0 у остальных; с PS-09 — из П3, вместе с `EXHAUSTED`. (Ограничение отменено РП41 п. 10.) `revocation_order` и статус — из `GET`; `currency` и обязательное `as_of` — ПАО 1.5.0 (пакет агента п. 3–4).
  7. **Выписка (A7 п. 9.3) — цепочка и подписи банка, проверяемые без банка:** (дополнено РП42 п. 8: `payload` не объект — `BROKEN`) `mandate_chain` — `Mandate` как в `GET` (с `agent_code` и `revocation_order`), у CART — родитель и CART; **`records`** — записи цепочки журнала целиком, с первой: `{seq, kind, ref, parent_ref, at, payload, prev_hash, hash}`. По ним пересчитываются хэши и `Mandate.hash`, подпись банка в `payload` решения и отзыва проверяется его открытым ключом. Цепочка принадлежит одному агенту (корневой мандат и его CART); предмета в записях нет — только обязательство. `operations` — `[]` до PS-16 и PS-22. `integrity` — `OK`; нарушенная цепочка — 200 с `integrity: BROKEN` и пустыми массивами (причина — в журнал процесса): для спора это ответ, а не сбой; цельная цепочка с неопределимым статусом — 503. **Ограничение:** раскрытие предмета (соль для сверки `subject_commitment`) — только по запросу клиента через банк (ПИ-8, PS-20, PS-22), в PS-06 не делается; агенту соль не отдаётся. Открытый ключ банка — из реестра участников (PS-20), до него — `PARTICIPANT_KEYS_PATH`.
  8. **ПАО — правка неопубликованной 1.4.0** (совместимо, AGENT-PROTOCOL §7): `Evidence.records` — новое необязательное поле ответа; описания `relinquish`, `verify`, `evidence`. 1.4.0 ядру ещё не передана (передача — после слияния PR #30): номер не меняется, меняется SHA-256 — новое значение `PAO_SPEC_SHA256` уходит ядру той же передачей. 404 и 503 у `relinquish` и `evidence` в YAML не объявлены, как у прочих изменяющих методов (№ 20) — объявление в ПАО 1.5.0. ПИ (1.0.0-draft) — новый путь `revoke`.
  9. **Распространение отзыва (инвариант 8):** ADP (PS-10) и `/credentials` (PS-14) берут статус свёрткой `load` на момент решения — отзыв действует со следующего чтения, кэша нет. Событие `mandate.revoked` агенту — PS-08; «авторизованное до отзыва исполняется» — PS-09, PS-10 (ПС16).
- **Почему:** в ПИ-8 был только `revoke-all` без тела, а он требует привязки мандата к банку; свёртка давала 503 на повтор отзыва и на гонку с подписью, хотя исход однозначен — полномочий нет; по `Mandate` цепочку не проверить — `Mandate.hash` считается от записи с `subject_commitment`, а не с предметом, и подписи банка в `Evidence` не было. Вариант Б п. 5 (оставить 503 до условной вставки ядра) отклонён: мандат без полномочий отвечал бы «состояние неизвестно».

### РП39. Лента событий агенту: Outbox в транзакции записи журнала, порядок номеров по агенту, события без подписи до ПАО 1.5.0 (PS-08 К1.1)

Решение владельца 18.10.2026 (PR #31: проект — комментарий Claude Code, решение — комментарий владельца; вариант А, блокировка на агента, барьерный тест, ПАО 1.4.1 не выпускать).

- **Решение:**
  1. **Лента — Outbox в транзакции записи журнала (вариант А).** Таблица `pao_events` (миграция `sql/101_events.sql`), только вставка (триггеры, как у `consent_*`): `agent_code`, `seq` (номер события у агента), `event_id` (UNIQUE), `type`, `at`, `data`, `journal_chain`, `journal_seq`; `UNIQUE (journal_chain, journal_seq)`; внешний ключ `(journal_chain, journal_seq)` → `core_journal (chain, seq)`. Платформа открывает транзакцию сама: соединение пула, `BEGIN`, запись журнала через `PgJournalStore` на этом соединении, вставка события, `COMMIT`. Ядро транзакций не открывает и при гонке конца цепочки повторяет вставку (РП33 доп. п. 8), а ошибка внутри транзакции её обрывает, поэтому каждая попытка вставки записи идёт под `SAVEPOINT` (заменено доп. п. 1: попытка — своя транзакция). Запись без события и событие без записи невозможны: откат — вместе, внешний ключ не пускает событие без записи. В памяти (dev, стенд) событие добавляется в том же вызове `append`, что и запись. Outbox ядра (в памяти) хранилищем не служит; для повтора доставки берётся `nextAttemptDelayMs` ядра (К1.3).
  2. **Порядок номеров = порядок фиксации, по агенту.** Номер `seq` выдаётся под `pg_advisory_xact_lock` по коду агента: блокировка держится до конца транзакции, `seq = max + 1` среди событий этого агента. Поэтому событие с номером `N + 1` фиксируется только после `N`, курсор не проскакивает незафиксированное событие и номера у агента идут без пропусков. Блокировка — на агента, не общая: агенты друг друга не ждут. Ключ блокировки — 64-битный от SHA-256 с меткой `pao:event-seq-lock:v1` и кодом агента; совпадение ключей у двух агентов лишь сериализует их запись, порядок не ломает. **Барьерный тест:** «номер выдан раньше, транзакция зафиксирована позже» — без блокировки красный (поломка → откат, как К3.2 служебной).
  3. **Одна запись журнала — одно событие:** `MANDATE_SIGNED` → `mandate.signed`, `MANDATE_REJECTED` → `mandate.rejected`, `MANDATE_REVOKED` и `MANDATE_RELINQUISHED` → `mandate.revoked`. У `MANDATE_REQUESTED` события нет: агент получил ответ на свой `POST`. Подчинённые CART при отзыве или истечении родителя своих записей не получают (РП35) — событий у них нет, статус CART — через `GET`. Событие получает агент мандата (`consent_mandates.agent_code`), чужим агентам оно не видно.
  4. **`event_id`** = `evt_` + UUID v8 (RFC 9562 §5.8) из SHA-256(`pao:event-id:v1\n` + `chain` + `\n` + `seq` записи), по образцу id мандата (РП33 доп. п. 5): у одной записи один `event_id` на всех экземплярах, второе событие на ту же запись невозможно (UNIQUE). `at` события — `at` записи журнала.
  5. **`data` — только `{mandate_id}`** (A7 п. 8.3: каждому — только нужный объём): ни статуса, ни предмета, ни сумм, ни ссылок банка. Полная картина — `GET /pao/v1/mandates/{id}`.
  6. **Событие — сигнал, а не источник статуса.** Подпись ответов и событий Платформы — ПАО 1.5.0 (SEC-1, Б4; РП26 п. 3, текст РП26 не правится). До неё агент по событию перечитывает мандат через `GET /pao/v1/mandates/{id}` (ответ — по mTLS от Платформы) и действует по прочитанному статусу, а не по `type`; правило остаётся безопасным и после 1.5.0. Дубли допустимы: между экземплярами свёртка терпит повторное решение и запись после отзыва (РП38 п. 5) — такая запись тоже даёт событие, статус по `GET` при этом не меняется.
  7. **`GET /pao/v1/events?after=<event_id>`** — события этого агента с `seq` больше, чем у `after`, по возрастанию `seq`, не больше `event_page_max` за ответ (новый параметр стенда: 100, целое ≥ 1). Без `after` — с начала ленты. Чужой или неизвестный `after` — 400 `REQUEST_INVALID`, одинаково для обоих (как РП34 п. 2): молча начать с начала нельзя. Повторное чтение даёт те же события с теми же `event_id`. Срок хранения на стенде не ограничен; очистка по сроку — STATUS «Открыто».
  8. **ПАО 1.4.1 не выпускается** (решение владельца): ядро берёт ПАО 1.4.0 по окончательному хэшу (v0.4.0, `4948c74`), `agent-protocol.yaml` в PS-08 не меняется. Ответы 400/401/403/503 у `/pao/v1/events` и `/pao/v1/subscription` объявляются в ПАО 1.5.0 вместе с общими ответами (расхождение № 20); до того — пометка в контрактном тесте. Правило п. 6, курсор п. 7 и `data` п. 5 — в AGENT-PROTOCOL §5 (текст MD хэш YAML не меняет).
  9. **Подписка и доставка** (К1.3): `PUT /pao/v1/subscription` — адрес только `https://`. Платформа шлёт POST по адресу, присланному агентом, — угроза SSRF: проверка адреса (запрет внутренних адресов, список разрешённых на стенде) — отдельным `/decision` в начале К1.3. Повтор по `nextAttemptDelayMs` до `event_retry_max`; после исчерпания событие остаётся в ленте. Порядок push-доставки не гарантируется, порядок даёт только `seq` ленты. Уточнено РП40 (проверка адреса, попытки, `SUSPENDED`/`EXCLUDED`).
- **Почему:** у журнала ядра нет общего порядка записей между цепочками (`core_journal` — ключ `(chain, seq)`, `at` — часы экземпляра, а не порядок фиксации): лента-представление пропускала бы событие, зафиксированное позже курсора (угроза С4, ФП13); общий номер в таблице ядра — правка ядра вне окна Б. События PS-16, PS-17, PS-19 рождаются вне журнала — очередь нужна в любом случае. Номер, выданный без блокировки, может зафиксироваться позже следующего — курсор агента прошёл бы мимо; блокировка на агента до фиксации это исключает и не связывает агентов между собой. ### РП40. Подписка на события: проверка адреса (SSRF), доставка с повтором, лента и push при `SUSPENDED`/`EXCLUDED` (PS-08 К1.3а)

Решение владельца 18.10.2026 (PR #32: проект — комментарий Claude Code, «да» владельца в окне Б; SSRF — по рекомендации чата в PR #31; лента и push при `SUSPENDED`/`EXCLUDED` — решение владельца: лента закрыта, как `GET` мандата).

- **Решение:**
  1. **`PUT /pao/v1/subscription`** (ПАО 1.4.0, схема `Subscription` без изменений; `Idempotency-Key` обязателен, как у прочих изменяющих методов): подписка хранится в записи агента в реестре (С6), заменяется целиком. `events` — подмножество `Event.type`; неизвестный тип — 400 `REQUEST_INVALID`; пустой список — push выключен (лента остаётся). Новая подписка действует на события, записанные после её фиксации; прежние события — через ленту.
  2. **Форма адреса (при `PUT`):** только `https://`; порт — не указан или 443; без userinfo и фрагмента; хост — имя DNS, не IP-литерал; длина ≤ 2048. Хост — только из списка разрешённых `event_subscription_allow_hosts` (точное совпадение имени, без масок). Пустой список — отказ всем (fail-closed, как `PARTICIPANT_KEYS_PATH`, РП36): в бою адрес фиксируется в соглашении участника (PS-20), до того в рабочем сервере список задаёт оператор. Имя разрешается уже при `PUT`: если хоть один адрес не глобальный (п. 3) — отказ. Отказ — 400 `REQUEST_INVALID` (своего кода в ПАО 1.4.0 нет; `SUBSCRIPTION_URL_REJECTED` — в ПАО 1.5.0 и в реестр кодов PS-ДГ); причина (`scheme`, `port`, `ip_literal`, `host_not_allowed`, `address_not_global`, `resolve_failed`) — в журнал процесса.
  3. **Не глобальный адрес** — всё, кроме глобального одноадресного (`net.BlockList`): IPv4 `0.0.0.0/8`, `10/8`, `100.64/10`, `127/8`, `169.254/16` (в т. ч. `169.254.169.254`), `172.16/12`, `192.0.0/24`, `192.0.2/24`, `192.168/16`, `198.18/15`, `198.51.100/24`, `203.0.113/24`, `224/4`, `240/4`; IPv6 `::`, `::1`, `fc00::/7`, `fe80::/10`, `ff00::/8`, `2001:db8::/32`; IPv4-mapped `::ffff:0:0/96` и NAT64 `64:ff9b::/96` — по встроенному IPv4.
  4. **Каждая отправка:** имя разрешается заново; хоть один не глобальный адрес или сбой разрешения — попытка неуспешна, без соединения (причина — в журнал процесса). Соединение — с уже проверенным IP (SNI и `Host` — имя, сертификат проверяется по имени), чтобы подмена DNS между проверкой и соединением не сработала. Перенаправления не выполняются: 3xx — неуспешная попытка. Успех — только 2xx. Тайм-аут всей попытки — `event_delivery_timeout_ms`; тело ответа не читается (соединение закрывается после статуса), поэтому предела размера ответа не нужно. Тело запроса — `Event`, как в ленте, заголовок `x-event-id`; подписи нет до ПАО 1.5.0 (РП39 п. 6). В журнале процесса — только хост, не путь (путь может нести секрет агента).
  5. **Попытки:** таблица `pao_event_deliveries` (изменяемая, отдельно от `pao_events`, которая остаётся «только вставка»): `event_id` (PK, FK → `pao_events`), `agent_code`, `attempts`, `next_at`, `state` (`PENDING` / `DELIVERED` / `EXHAUSTED` / `SKIPPED`), `last_reason`. Строка создаётся в той же транзакции, что событие (РП39 п. 1), если в этот момент агент `ACTIVE` и подписан на этот тип; иначе push по событию не будет — только лента. Обработчик берёт готовые строки `FOR UPDATE SKIP LOCKED` (несколько экземпляров не шлют одно событие одновременно), увеличивает `attempts` до отправки (сбой после отправки → повтор того же `event_id`: «не менее одного раза», инвариант 9). Неуспех попытки `n` → `next_at = now + nextAttemptDelayMs(n)` ядра (1 с, удвоение, предел 15 мин — значения ядра по умолчанию). `event_retry_max` — число попыток всего, включая первую (как `Outbox` ядра). После исчерпания — `EXHAUSTED`, событие остаётся в ленте. Порядок push не гарантируется (РП39 п. 9).
  6. **`SUSPENDED`:** `GET /pao/v1/events` и `PUT /pao/v1/subscription` — 403 `AGENT_SUSPENDED`, как `GET` мандата: исключение в `src/pao/verify.ts` (`STATUS_EXEMPT` — только `GET /pao/v1/agent`) не расширяется. Push не выполняется: при создании события строка попытки не создаётся, а у строки `PENDING` обработчик перед отправкой читает статус агента из реестра и при не-`ACTIVE` ставит `SKIPPED` без попытки. События копятся в `pao_events` и доступны через ленту после снятия приостановки; push по накопленным не догоняет — после `agent.reinstated` агент читает ленту с последнего курсора. Статус не прочитан — отправки нет, попытка не тратится, `next_at` сдвигается на `nextAttemptDelayMs(attempts)` (fail-closed, инвариант 3).
  7. **`EXCLUDED`:** 403 на всё, кроме `GET /pao/v1/agent`; в ПАО 1.4.0 код один — `AGENT_SUSPENDED` (отдельный `AGENT_EXCLUDED` — ПАО 1.5.0 и PS-ДГ). Push не выполняется никогда, подписка в записи остаётся, но не используется.
  8. **Стенд:** проверка адреса на стенде не отключается. Подменяются только два порта — разрешение имени и транспорт. Эмулятор агента-получателя (`src/env/`) работает в процессе под именем `agent-emulator.stand` из `event_subscription_allow_hosts` стенда. Стендовое разрешение имени отдаёт для него фиксированный глобальный адрес-заглушку (адреса `TEST-NET` не глобальные и были бы отвергнуты п. 3). Стендовый транспорт передаёт запрос по проверенному адресу эмулятору, не выходя в сеть. Подмена DNS в тестах — через тот же порт разрешения имени. В рабочем сервере (`stand: false`) стендовые порты в списке — отказ запуска (как ключ эмулятора эмитента, РП36 п. 9).
- **Почему:** Платформа шлёт POST по адресу, который прислал агент (Н2, Н3, Н4): без проверки это запрос из сети Платформы к её внутренним службам и метаданным облака (SSRF). Проверка только при `PUT` обходится подменой DNS после подписки, проверка перед соединением без привязки к IP — подменой между проверкой и соединением; перенаправление выводит на внутренний адрес в обход проверки. Список разрешённых хостов закрывает и то, что разрешение имени не ловит. Приостановленный агент не получает ничего, кроме собственного статуса (A2 п. 7.1; правило шлюза РП21): лента — то же чтение, что `GET` мандата; события не теряются — они в `pao_events`.
- **Что меняет:** миграция `sql/102_subscriptions.sql` (поля подписки в записи агента, `pao_event_deliveries`); `src/registry/` (подписка в записи агента), `src/pao/` (`PUT /pao/v1/subscription`, проверка адреса, обработчик доставки), `src/consent/store.ts` (строка попытки в транзакции события), `src/env/` (эмулятор агента-получателя), `src/shared/config.ts`; PARAMS и `params.stand.json`; SECURITY §3.5 (С4, С6, новые С7, С8); AGENT-PROTOCOL §5; SPEC §3 П9 и ФП13; CLAUDE.md и INDEX — РП1–РП40; STATUS (№ 24 — дополнить, «Передача агенту», «Открыто»); CHANGELOG.

Стенд — без таймера: `stand.deliverEvents()` по часам стенда (повтор — тест двигает часы), эмулятор агента-получателя `stand.agentReceiver` (ответы по очереди, идемпотентен по `event_id`), строка попытки — `stand.delivery(event_id)`.

**Дополнение РП40 (PS-08 К1.10, 18.10.2026; по `/audit` и ревью из чата, PR #32 #issuecomment-6253942929, «да» владельца):**
15. **Предел попыток при повторном взятии строки** (уточняет п. 5 и доп. п. 7): обработчик упал после отправки, но до `finish` — после аренды строку берут снова, `attempts` растёт. Первая проверка попытки, до чтения статуса и разрешения имени: `attempts > event_retry_max` → `EXHAUSTED` с причиной `lease_expired`, без отправки; в журнал процесса — предупреждение (как исчерпание, доп. п. 13). Отправок одного события — не больше `event_retry_max`; «не менее одного раза» сохраняется (последняя засчитанная попытка отправлена); событие — в ленте.
16. **«Статус не прочитан» — задержка растёт, причина в журнале** (уточняет доп. п. 9 и п. 13): попытка по-прежнему возвращается (`attempts − 1`), срок следующего взятия — `nextAttemptDelayMs(claims)`, а не от `attempts − 1`: `claims` растёт при каждом взятии, поэтому при долгом сбое реестра строка берётся всё реже, до потолка ядра (15 мин), а `event_retry_max` не тратится. `status_unavailable` — предупреждение в журнале процесса (код агента, `event_id`). Остаточный риск: при сбое реестра дольше суммы задержек событие доходит только лентой — допустимо, push ленту не заменяет (п. 1).
17. **Служебные AS112 и AMT — не глобальные** (дополняет п. 3 и доп. п. 1): глобальны по маршрутизации, но служебные. IPv4 `192.31.196.0/24` (AS112, RFC 7535), `192.52.193.0/24` (AMT, RFC 7450), `192.175.48.0/24` (AS112 direct delegation, RFC 7534); IPv6 `2620:4f:8000::/48` (AS112, RFC 7534) — внутри `2000::/3`, исключается по байтам, как `2001:db8::/32`. Проверка — та же при `PUT` и перед каждой отправкой.
18. **Остаточные риски доставки с условиями снятия** (ревью из чата № 1, № 2; решение владельца 18.10.2026):
    - **(а) Один медленный агент задерживает доставку всем:** проход берёт до 20 строк подряд, каждая — до `event_delivery_timeout_ms`, проходы не накладываются; адрес, висящий до тайм-аута, занимает проход ≈ 100 с. **Условие:** до подключения второго агента — не больше одной попытки на агента за проход или ограниченный параллелизм с пределом на агента. SECURITY С9, STATUS «Открыто».
    - **(б) Зависшее разрешение имени занимает пул потоков libuv:** `dns.lookup` — getaddrinfo в пуле (по умолчанию 4 потока); `withTimeout` отдаёт отказ по сроку, а запрос висит в пуле до системного тайм-аута — встают файлы, zlib, часть crypto; на стенде разрешение подменено, тестами не видно. **Условие:** до боевого запуска рабочего сервера — `dns.promises.Resolver` (c-ares, вне пула) с `timeout`/`tries`, `resolve4` + `resolve6`, `cancel()` по сроку. ### РП41. Бюджет мандата в П3: удержания agentic-core, срок резерва, `verify.amount_left`, `EXHAUSTED` (PS-09)

«Да» владельца 19.10.2026 (PR #34 #issuecomment-6263053824), с дополнениями 1–2 ревью из чата.


- **Решение:**
  1. **Деньги.** Только целые минимальные единицы с валютой (`Money` ядра: `amount` — безопасное целое, `currency` — ISO 4217). Float нет. Инвариант ядра: `закреплено + зарезервировано ≤ предел`, `доступно = предел − закреплено − зарезервировано ≥ 0`.
  2. **Учёт — только удержания ядра (CO-2), своих реализаций нет.**
     - `sandbox`, а также `dev` с `DATABASE_URL` — `PgHoldLedger` на `pg.Pool` в autocommit (таблицы `core_hold_accounts` и `core_holds`, миграция ядра `002_holds.sql` уже применяется по РП30 п. 5). Клиент внутри транзакции Платформы не передаётся: так требует договор ядра.
     - `dev` без базы и стенд для агента — `AsyncMemoryHoldLedger` ядра: тот же договор, один процесс, как хранилища по РП30 п. 6.
     - Прямых запросов Платформы к таблицам удержаний нет ни на чтение, ни на запись: это был бы обход контракта ядра (РП30 п. 3).
  3. **Счёт = мандат.**
     - Id счёта — `mandate:<mandate_id>`, предел — `{amount_limit, currency}` из записи мандата (инвариант 5).
     - `openAccount` вызывается после записи `MANDATE_SIGNED` (статус `ACTIVE`). Повтор с тем же пределом возвращает прежний счёт.
     - Сбой открытия подпись не отменяет. Счёт открывается заново при первом резерве: если ядро ответило `UNKNOWN_ACCOUNT`, а мандат `ACTIVE` по свёртке — `openAccount` из записи и один повтор `reserve`.
     - `ACCOUNT_CONFLICT` (счёт с другим пределом) — нарушение целостности: `STATE_UNAVAILABLE` и инцидент в журнал процесса.
     - У CART счёт свой, предел — `amount_limit` CART.
  4. **Резерв** (`StateService.reserve(mandate_id, money, op_key)`).
     - Порядок:
       1. статус мандата по свёртке `ConsentJournal.load` (РП35 п. 2);
       2. валюта операции = валюта мандата;
       3. лимит клиента (п. 9);
       4. `reserve(account, money, ref, expires_at)`.
     - `ref` глобален в журнале удержаний, поэтому в него входят мандат и ключ операции: `mandate:<mandate_id>:op:<op_key>`. `op_key` — ссылка операции процессинга; откуда её брать, определяет PS-10.
     - Повтор с тем же `ref`, суммой и валютой возвращает прежнее удержание.
     - `expires_at = now + reservation_ttl_sec × 1000` (п. 6).
     - Итог — удержание (`hold.id` хранит вызывающий: запись операции, PS-10/PS-16) или код П3.
  5. **Коды П3.** Внутренние: на границе их сопоставляет вызывающий (код отказа ADP — PS-10; HTTP П10 — PS-20).

     | Причина | Код П3 |
     |---|---|
     | `INSUFFICIENT` | `LIMIT_EXCEEDED` |
     | `REF_CONFLICT` (тот же `ref`, другая сумма или валюта) | `IDEMPOTENCY_CONFLICT` |
     | валюта операции ≠ валюте мандата (проверка до ядра; `CURRENCY_MISMATCH` ядра — то же) | `MANDATE_SCOPE` |
     | `BAD_AMOUNT`, `BAD_CURRENCY` (сумма не целое ≥ 1) | `REQUEST_INVALID` |
     | мандат не `ACTIVE` | код по статусу: `MANDATE_REVOKED`, `MANDATE_EXPIRED`, `PRINCIPAL_SIGNATURE_PENDING`, `LIMIT_EXCEEDED` у `EXHAUSTED`; резерва нет |
     | сбой хранилища удержаний или журнала; статус не прочитан; `ACCOUNT_CONFLICT` | `STATE_UNAVAILABLE` (на HTTP — 503 с `Retry-After` по РП24); резерв не создаётся (fail-closed, инвариант 3, A3 п. 4.5) |

     Неизвестная ошибка ядра — тоже `STATE_UNAVAILABLE`, без догадки.
  6. **Срок резерва.**
     - `expires_at` задаётся при резерве. Освобождает проход `expire(now)` ядра по таймеру процесса раз в 60 с — константа кода, не параметр (как аренда в РП30 п. 3). Сбой прохода пишется в журнал процесса, следующий проход его повторяет.
     - Между `expires_at` и проходом закрепление ещё проходит: ядро срок при `commit` не проверяет, а бюджет до прохода удержан, так что перерасхода нет.
     - После прохода закрепление — `BAD_STATE` ядра. Платформа отказывает в закреплении кодом П3 `RESERVATION_RELEASED`, пишет в журнал процесса инцидент «поздний клиринг» и строку в STATUS «Открыто». Нового резерва в обход не делает.
     - **Открытый вопрос к PS-07 (порт «банк»):** срока подтверждения авторизации банком в PARAMS нет. Условие «`reservation_ttl_sec` не меньше срока подтверждения банком» и его проверка при старте — в STATUS «Открыто» до PS-07; новый параметр сейчас не вводится.
  7. **Закрепление и освобождение.**
     - `commit` — всегда с `releaseRest = true`: одно представление на удержание. Частичное представление закрепляет свою сумму, остаток освобождается (SPEC §5, A1 п. 6.3).
     - Причина: закрепление в ядре не идемпотентно по ссылке. Повтор частичного закрепления без `releaseRest` закрепил бы сумму дважды.
     - Повтор закрепления: ядро отвечает `BAD_STATE`; Платформа читает удержание (`get`):
       - `committed` = запрошенной сумме — повтор, прежний результат;
       - иначе `COMMIT_CONFLICT`;
       - `committed = 0` (освобождено) — `RESERVATION_RELEASED` (п. 6).
     - Несколько представлений на одну авторизацию (раздельная отгрузка) — не в PS-09, отдельным решением.
     - `release` (реверсал, отказ эмитента после ADP) идемпотентен в ядре.
     - Сумма больше открытой части (`BAD_AMOUNT`) — `REQUEST_INVALID`.
     - Возврат и `restore_budget_on_refund` (РП9) — PS-16/PS-22.
  8. **Отзыв** (A3 п. 6.3, инвариант 8, ПС16).
     - Новые резервы после отзыва — нет (п. 4.1).
     - Закрепление и освобождение резерва, сделанного до отзыва, — да: статус мандата при `commit` и `release` не проверяется.
     - **Остаточный риск:** отзыв, записанный между проверкой статуса и `reserve`, оставляет резерв, созданный после отзыва. Окно — одна операция БД. Решение ADP по этому резерву — PS-10; там же сверка статуса после резерва с освобождением при `REVOKED`.
  9. **Меньшее из пределов** (A3 п. 7.2).
     - Ядро держит один предел на счёт — предел мандата.
     - Лимит клиента или инструмента проверяет Платформа до `reserve` через точку расширения `ClientLimitCheck` (интерфейс в `src/state`). В PS-09 он не подключён и всегда разрешает; подключение — с шлюзом участников (PS-20).
     - Пока точка не подключена, «меньшее из пределов» сводится к пределу мандата. Это ограничение записано в SPEC §5.
  10. **`verify.amount_left`** (РП38 п. 6; отменяет «Ограничение до PS-09»):
      - `ACTIVE` — `CONFIRMED`, `amount_left = max(0, available(mandate:<id>))`;
      - счёта ещё нет (`UNKNOWN_ACCOUNT`) — `amount_limit`, расходования не было; чтение счёт не создаёт;
      - сбой чтения П3 при целом журнале — 200 `STATE_UNKNOWN`, `amount_left = 0` (A7 п. 8.6: «не подтверждено» = вне пределов);
      - нарушенная цепочка или неопределимый статус — по-прежнему 503 `STATE_UNAVAILABLE`;
      - `EXHAUSTED` и прочие не `ACTIVE` — `OUT_OF_SCOPE`, `amount_left = 0`.
      - У CART `amount_left` — по счёту CART.
  11. **`EXHAUSTED` и `mandate.exhausted`** — по закреплению, не по резерву.
      - Когда после успешного `commit` у счёта `committed = limit`, Платформа пишет в цепочку мандата запись `MANDATE_EXHAUSTED` (`payload`: `{committed, currency}`). Запись идёт под тем же локом записи по мандату (`writing`, РП38) и в транзакции журнала вместе с событием `mandate.exhausted` (`data` — `{mandate_id}`), как события РП39.
      - До записи проверяется, нет ли её уже: одна запись на мандат в процессе.
      - Свёртка: `ACTIVE` + `MANDATE_EXHAUSTED` → `EXHAUSTED`. `EXHAUSTED` конечный (`restore_budget_on_refund = false`, РП9).
      - Отзыв и отказ агента при `EXHAUSTED` — 200 с текущим статусом, без записи (как `EXPIRED`, РП38).
      - CART: родитель `EXHAUSTED` → CART `EXHAUSTED` (дополняет РП35 п. 1). Собственный `EXHAUSTED` у CART — по его счёту.
      - Статус для `GET`, `verify`, ADP — из записи журнала (инвариант 5: источник — записи), а `amount_left` — из П3.
      - **Остаточные риски:**
        - сбой процесса между `commit` ядра и записью `MANDATE_EXHAUSTED`: статус остаётся `ACTIVE`, а `amount_left = 0`, резервы отклоняются `LIMIT_EXCEEDED` (безопасная сторона), события нет. Запись дописывается при повторе закрепления (п. 7) или при следующем отказе в резерве (доп. 1 ниже);
        - два экземпляра одновременно могут написать две записи; вторая поглощается свёрткой, событие придёт дважды — дубль допустим (РП39 п. 6).
      - **Дописывание при отказе в резерве** (дополнение 1, ревью из чата): `reserve` получил `INSUFFICIENT` — Платформа читает счёт; если `committed = limit`, а статус по свёртке `ACTIVE`, она дописывает `MANDATE_EXHAUSTED` с событием тем же путём (под локом `writing`, с проверкой «записи ещё нет»). Ответ остаётся `LIMIT_EXCEEDED`; сбой дописывания — в журнал процесса, ответ не меняется. В путь `verify` запись не добавляется: чтение не пишет.
  12. **Проверка.**
      - Unit-тесты на памяти ядра: сопоставление каждого кода п. 5, повтор резерва и закрепления, закрепление после освобождения и после прохода `expire`, отзыв (нет нового резерва, есть закрепление прежнего), сбой хранилища — `STATE_UNAVAILABLE`; `commit` прошёл, записи `MANDATE_EXHAUSTED` нет — следующий `reserve` дописывает её, событие одно (доп. 1).
      - PG-тест в CI — через `StateService` на `PgHoldLedger`: 20 одновременных резервов по 100 000 коп. при пределе 300 000 — принято ровно 3, остальные `LIMIT_EXCEEDED`, `reserved` = 300 000 (ПС10 на уровне П3). Два одновременных прохода `expire` по PG — без ошибки, удержание освобождено один раз (проход идёт на каждом экземпляре; ревью из чата).
      - Поломка — обход ledger (чтение `available` → проверка → `UPDATE` без условия) — красная через CI своим сообщением, затем откат. Через CI, потому что тест зависит от PostgreSQL (правило 18.10.2026).
  13. **Коды П3 вне ПАО** — `RESERVATION_RELEASED`, `COMMIT_CONFLICT` (дополнение 2, ревью из чата): войдут в реестр кодов Платформы в PS-ДГ (`component: platform`, действие `after_human`); до того — строка в STATUS «Открыто».
- **Почему:** РП11 и инвариант 4 требуют неделимого расходования. В ядре (CO-2) условие по остатку и изменение — один SQL-оператор, с теми же векторами в памяти и на PG. Вторая реализация в Платформе разошлась бы с ядром и с эскроу НСВР, у которых тот же механизм. Fail-closed (A3 п. 4.5) — отказ при любом неподтверждённом состоянии. `EXHAUSTED` по резерву давал бы ложный конечный статус после реверсала. Закрепление в ядре не идемпотентно, поэтому одно представление на удержание и повтор распознаются по чтению. Учтены рекомендации чата от 19.10.2026 (п. 1–9), ревью РП41 из чата (дополнения 1–2, проход `expire` на двух экземплярах) и уточнения владельца (срок подтверждения банком — открытый вопрос к PS-07; версия ядра не меняется).
- **Что меняет:**
  - SPEC: §3 П2 «Записи», «Статус CART», «Проверка», «События мандата»; §5 (реализация, меньшее из пределов, срок резерва).
  - AGENT-PROTOCOL: §4 `verify` и §5 `mandate.exhausted`.
  - PARAMS: `reservation_ttl_sec` (проход раз в 60 с, открытый вопрос PS-07).
  - STATUS «Открыто».
  - `agent-protocol.yaml` не меняется: `EXHAUSTED`, `STATE_UNKNOWN` и `mandate.exhausted` уже в ПАО 1.4.0, `PAO_SPEC_SHA256` прежний. Описание `verify` в YAML («До PS-09 …») обновится вместе с ПАО 1.5.0.
- **Отменяет:** РП38 п. 6 «Ограничение до PS-09» (`amount_left = amount_limit`), с пометкой «отменено РП41 п. 10». Дополняет РП35 п. 1 (`EXHAUSTED` родителя).

**Дополнение РП41 (PS-09 К1.5, 19.10.2026; ревью из чата «Ревью К1.2–К1.4», PR #34 #issuecomment-6263697820, «да» владельца):**
14. **Коды по статусу (дополняет п. 5):** резерв по мандату `REJECTED` — `MANDATE_REVOKED`, не `MANDATE_SCOPE`. В ПАО `MANDATE_REVOKED` — «отозван или отклонён», действие агента — стоп; `MANDATE_SCOPE` (A7 п. 5.2) велел бы агенту пересобрать корзину, а для мандата, который банк отклонил, это неверный сигнал. Полностью: `PENDING_SIGNATURE` → `PRINCIPAL_SIGNATURE_PENDING`, `REVOKED` и `REJECTED` → `MANDATE_REVOKED`, `EXPIRED` → `MANDATE_EXPIRED`, `EXHAUSTED` → `LIMIT_EXCEEDED`.
15. **Неизвестный `hold_id` (дополняет п. 5, 7):** закрепление или освобождение по `hold_id`, которого нет в ядре (`UNKNOWN_HOLD`), — `STATE_UNAVAILABLE` с записью в журнал процесса, отдельного кода нет. Это нарушение целостности у вызывающего (запись операции — PS-10), fail-closed (инвариант 3).
16. **Свёртка `MANDATE_EXHAUSTED` (уточняет п. 11):** запись — в цепочке мандата с `ref` и `parent_ref` = id мандата, как решение банка; у CART — своя запись по счёту CART. `ACTIVE` + `MANDATE_EXHAUSTED` → `EXHAUSTED`; дубль пропускается; отзыв или отказ агента после неё (гонка двух экземпляров: внутри процесса при `EXHAUSTED` они не пишутся) — `REVOKED`, отзыв клиента записан и не теряется; `MANDATE_EXHAUSTED` при `PENDING_SIGNATURE` или `REJECTED` — неопределимый статус (503). Срок `valid_to` на `EXHAUSTED` не действует. Запись делает журнал только при статусе `ACTIVE` по свёртке под локом записи — проверка «записи ещё нет» и есть эта свёртка.
17. **Дописывание (уточняет п. 11 и доп. 1):** после успешного `commit`, после распознанного повтора `commit` и при `INSUFFICIENT` в `reserve` П3 читает счёт и при `committed = limit` вызывает запись. Сбой чтения или записи — предупреждение в журнал процесса, ответ П3 не меняется.
18. **`verify` без счёта (уточняет п. 10):** мандат `ACTIVE`, счёт не открыт (подпись прошла без П3 или открытие упало) — `amount_left` = `amount_limit`; чтение счёт не открывает.

### РП42. Реестр кодов Платформы в формате К17 ядра и самопроверка при старте (PS-ДГ, #35)

«Да» владельца 19.10.2026 (чат, окно Б; текст — PR #36 #issuecomment-6265680474), с уточнением: `STARTUP_PAO_SPEC_MISMATCH` и `STARTUP_DIAG_INCOMPLETE` — источник `platform`, действие `after_fix` (дефект сборки, не окружения).

- **Решение:**
  1. **Формат — только `/diag` ядра v0.8.0.** Записи `DiagEntry` (`code`, `component`, `source[]`, `action`, `human`, `operator`, `norm`, `since`), проверка полноты `checkDiagRegistry`, действие по коду `diagAction` (код не из реестра — `stop`), отчёт `SelfCheckReport` (`buildSelfCheckReport`, `checkSelfCheckReport`). Своих форм записи, проверки и отчёта у Платформы нет.
  2. **Три реестра, не объединённых в один.** Десять из 13 кодов ПИ совпадают по имени с кодами ПАО (`AGENT_UNKNOWN`, `AGENT_SUSPENDED`, `CREDENTIAL_INVALID`, `MANDATE_*`, `LIMIT_EXCEEDED`, `STATE_UNAVAILABLE`, `CONFIRMATION_REQUIRED`), а получатель и действие у них разные. Поэтому реестры раздельные, по компоненту:
     - **`PAO_DIAG` ядра — как есть**, свой реестр ПАО не пишется. Тест сверяет его с перечнем Платформы: те же 20 кодов `x-pao-errors`, `action` — по `retry` Платформы (`PAO_RETRY_ACTION`).
     - **`PI_DIAG`** (`component: "pi"`) — 13 кодов `DECISION_REASON` из `processing-interface.yaml`. Получатель — процессинг и эквайрер, `since` — версия ПИ (`1.0.0-draft`). Номер кода ответа ОПКЦ — `[альбом]`, в запись не входит (РП6).
       Действия кодов ПИ — для получателя процессинг/эквайрер, перечень — `PI_DIAG`; `CREDENTIAL_INVALID` — `stop`, не `after_fix`: реквизит агента процессинг и эквайрер исправить не могут (ревью из чата, решение владельца 19.10.2026, PS-ДГ К1.4). Число совпадающих имён — 10, не 11 (исправлено в К1.4 по тесту: не совпадают `AOI_MISSING`, `AOI_MISMATCH`, `ADP_UNAVAILABLE`).
     - **`PLATFORM_DIAG`** (`component: "platform"`) — коды вне протоколов: коды П3 без пары в ПАО — `RESERVATION_RELEASED`, `COMMIT_CONFLICT` (РП41 п. 5; источник `platform`, действие `after_human`) — и коды самопроверки (п. 4). `since` — версия пакета Платформы, в которой код появился.

     Тексты — `ru` обязателен; другие языки — точка расширения (правило совместимости 3), без бренда и подстановок (К17 п. 6). В ПАО и канонической модели по-прежнему только коды.
  3. **Тест полноты (К17 п. 3; «код без записи — красный»)** — `checkDiagRegistry` по каждому реестру против его машинного перечня: `PI_DIAG` ← `DECISION_REASON`; `PLATFORM_DIAG` ← коды П3 без пары в ПАО и перечень кодов самопроверки; `PAO_DIAG` ← `PAO_ERROR_CODES` Платформы. У `StateCode` П3 появляется перечень-константа `STATE_CODES`, тип выводится из него; каждый код П3 — либо код ПАО, либо в `PLATFORM_DIAG`, третьего нет. Замечание теста называет код и поле записи.
  4. **Самопроверка при старте** (К17 п. 8; `src/shared/selfcheck.ts`, вызов в `src/main.ts`). Проверки и коды (`component: "platform"`; источник `environment`, действие `after_human`, кроме оговорённых):

     | `check` | `fail` | `warn` |
     |---|---|---|
     | `params` | `STARTUP_PARAMS_INVALID` — стендовые параметры не прошли `loadParams` | — |
     | `proxies` | `STARTUP_PROXIES_INVALID` — `PAO_TRUSTED_PROXIES` (РП32 п. 5) | — |
     | `db.storage` | `STARTUP_DB_REQUIRED` — `sandbox` без `DATABASE_URL` (РП30 п. 5) | `STARTUP_DB_MEMORY` — `dev` без базы: хранилища в памяти, один процесс |
     | `db.migrations` | `STARTUP_DB_MIGRATIONS` — миграции ядра и Платформы не применены | — |
     | `participants` | `STARTUP_PARTICIPANTS_INVALID` — доверенные ключи участников (РП36 п. 4) | — |
     | `pao.spec` | `STARTUP_PAO_SPEC_MISMATCH` — версия или `PAO_SPEC_SHA256` ядра ≠ Платформы; **источник `platform`, действие `after_fix`** | — |
     | `diag.registry` | `STARTUP_DIAG_INCOMPLETE` — `checkDiagRegistry` хоть одного реестра не пуст; **источник `platform`, действие `after_fix`** | — |

     - Отчёт собирается до `listen`; `component: "platform"`, `version` — версия пакета. Отчёт проверяется `checkSelfCheckReport` по `PLATFORM_DIAG`; замечание к отчёту — тоже отказ запуска (неподтверждённая готовность — не готовность).
     - Отчёт — в журнал процесса одной записью, только коды; тексты для оператора — по реестру, причина исключения — отдельным полем журнала, не в отчёте.
     - **`ready: false` — трафик не принимается: процесс не слушает порт и завершается с кодом 1** (A3 п. 4.5, инвариант 3). `warn` готовность не снимает.
     - Нынешние разрозненные отказы запуска (исключения) сводятся в отчёт, поведение «отказ запуска» сохраняется.
     - Отдача отчёта по HTTP (`/health` или служебный маршрут) — отдельным решением; `/health` не меняется.
  5. **Ограничение до PS-10 (инвариант 2).** Сейчас Платформа не в пути авторизации (ADP — PS-10), поэтому при `ready: false` процесс не стартует целиком. С PS-10, когда ADP в пути авторизации, `ready: false` останавливает только агентские операции, неагентские идут (`BYPASS` — первая проверка ADP, РП4); как именно — решается в PS-10 вместе с порядком проверок ADP.
  6. **Стенд для агента (`createStand`)** самопроверку при старте не выполняет: параметры и хранилища у него фиксированы. Полноту реестров стенд получает из того же теста полноты Платформы.
  7. **Коды витрин эмулятора (`MerchantErrorCode`) в реестры Платформы не входят:** это окружение, а не Платформа. В STATUS «Открыто» — где они получат запись в формате К17 (стенд или агент; AG-04, AG-09, ревью #23 п. 7 агента).
  8. **Дополнение к РП38 п. 7 (выписка; нюанс PS-ДГ К1.1).** `payload` записи журнала в `records` выписки — объект (`JournalRecord` ПАО 1.4.0 ядра). Запись с `payload` не объектом в цепочке — нарушение целостности: `integrity: "BROKEN"`, а не приведение типа. Хэш-цепочку это не затрагивает: Платформа такую запись не пишет, проверка — на чтении (fail-closed).
  9. **ПАО не меняется:** `PAO_SPEC_SHA256` прежний (`48bd3397…9ad9da`), новых кодов для агента нет. Коды ПИ и Платформы агент не видит; на границе ПАО их сопоставляет вызывающий (ADP — PS-10, П10 — PS-20; РП41 п. 5).
- **Почему:** один формат с ядром и агентом (К17) — «кто ошибся» и действие получателя читаются одинаково во всех трёх компонентах. Раздельные реестры не дают кодам с одинаковым именем и разным получателем (ПИ и ПАО) затереть друг друга. Самопроверка с кодами вместо разрозненных исключений даёт оператору отчёт «готов / не готов» и сохраняет fail-closed. Несовпадение спецификации ПАО с ядром и неполный реестр — дефект сборки, их чинят исправлением, а не окружением (уточнение владельца). Отклонено: один объединённый реестр (коллизия десяти имён ПИ и ПАО); свой реестр ПАО (дублирование `PAO_DIAG`, #35); запуск при `ready: false` с отказами по каждому запросу (неподтверждённое состояние было бы принято, A3 п. 4.5).
- **Что меняет:**
  - SPEC: §3 — подраздел «Диагностика (РП42)»; §8 — требование самопроверки при старте.
  - DECISIONS: РП38 п. 7 — ссылка на п. 8.
  - STATUS «Открыто»: (ж) закрыт; строка о кодах витрин эмулятора (п. 7).
  - CLAUDE.md: «РП1–РП42».
  - Код (К1.3–К1.5): `src/shared/diag.ts`, `src/shared/selfcheck.ts`, `src/state/service.ts` (`STATE_CODES`), `src/main.ts`; тесты полноты и самопроверки.
  - `agent-protocol.yaml`, `processing-interface.yaml`, NORMS, SCENARIOS, PARAMS не меняются; agentic-buyer-ref — ничего (ПАО прежний).
- **Отменяет:** — (дополняет РП38 п. 7).
