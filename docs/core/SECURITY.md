# Безопасность Платформы: модель угроз и ключи

Редакция 2 · 13.10.2026 (ред. 1 · 12.10.2026 · SEC-1; ред. 2 — С3а и ограничение перечитывания в С3 по РП22). Решения — РП26 (ключи Платформы), РП27 (mTLS песочницы), РП28 (аутентификация операторов агентов), РП22 (каталог ключей агентов для продавцов); ранее — РП5, РП17, РП21, РП23, РП24, РП25. Меняется через `/decision`; статусы угроз в таблицах — по мере закрытия задач. Проверка по этой модели против кода обоих репозиториев — SEC-2 перед пилотом.

## 1. Границы и что защищается

```
агент ──mTLS + подпись обращения──▶ шлюз ПАО (П9) ──▶ реестр (П1), журнал (П2), реквизиты (П5)
  ▲                                      │
  └──── события, подпись Платформы ◀─────┘
оператор агента ──mTLS (сертификат оператора)──▶ API допуска (PS-31)
процессинг (ОПКЦ) ──ПИ-1──▶ ADP (П4) ──▶ состояние (П3)
эмитент (приложение клиента) ──ПИ-8──▶ шлюз участников (П10) ──▶ журнал (П2)
```

Что защищается: полномочия клиента (мандат и бюджет), подлинность агента и оператора, неизменность журнала согласий, подлинность ответов и событий Платформы, отсутствие платёжных реквизитов и ПДн вне эмитента (инвариант 1, SPEC §11 п. 7).

Границы доверия:
- **агент и оператор агента** — внешние, не доверенные: всё, что они присылают, проверяется по записям Платформы (инвариант 5);
- **процессинг и эмитент** — доверенные участники платёжной системы, канал защищён средствами оператора (ПИ, `[альбом]`); в песочнице — эмуляторы в одном доверенном контуре;
- **хранилища Платформы** — доверенные, но журнал согласий проверяем и против внутреннего нарушителя (хэш-цепочка, A7 п. 4).

## 2. Кто атакует

| Код | Нарушитель | Возможности |
|---|---|---|
| Н1 | Посторонний в сети | Перехват и повтор трафика, подделка запросов, перебор, поток неподписанных обращений |
| Н2 | Допущенный агент вне своих полномочий | Действительные ключ и сертификат; обращения за другого агента, выход за мандат, повторы |
| Н3 | Агент с украденным ключом или сертификатом | То же, что агент-владелец, до отзыва |
| Н4 | Недобросовестный оператор агента | Заявления на допуск, регистрация ключей, попытка выдать себя за другого оператора или выпустить версию чужого агента |
| Н5 | Продавец или площадка | Подмена суммы и состава заказа, повтор криптограммы, ложные события |
| Н6 | Внутренний нарушитель с доступом к БД | Правка или удаление строк журнала и реестра в обход приложения |
| Н7 | Подмена Платформы для агента | Поддельные ответы и события, подмена ключей Платформы |

## 4. Ключи Платформы (РП26)

- **Два ключа по назначению:** подпись ответов ПАО и подпись событий агенту. Назначение — свойство ключа; компрометация одного не затрагивает другой.
- **Песочница:** ed25519, пара генерируется при старте во временный каталог (CLAUDE.md, «Секреты»); закрытый ключ не попадает в журнал процесса, ответы, репозиторий. **Контур оператора:** ГОСТ Р 34.10-2012 в HSM, ключ не извлекается (РП5).
- **Публикация:** открытые ключи — в `platform_keys` `/.well-known/pao-configuration` (схема `Key`: `kid`, `alg`, `public_key`, `status`, `valid_from`, `valid_to`); `kid` — отпечаток JWK по RFC 7638, как у агентов.
- **Подпись** — с ПАО 1.5.0 (РП26 п. 8, РП31, РП37; в 1.2.0–1.4.0 Платформа ответы и события не подписывает). RFC 9421, заголовки `Signature-Input` и `Signature` с меткой `platform`, параметры `keyid` (ключ Платформы), `alg`, `created`. Компоненты ответа: `@status`, `content-digest`, `x-agent-code`, `@method;req`, `@path;req`, `x-nonce;req` — ответ привязан к запросу; события: `content-digest`, `x-event-id`, `x-agent-code`. Подпись с `created` вне окна `signature_skew_sec` — отказ.
- **Назначение ключа** (`use`: `response` / `event`) агент проверяет: ключ без `use` или с чужим `use` — отказ. Только так компрометация ключа ответов не даёт рассылать события.
- **Ротация:** новый ключ публикуется до начала использования; старый остаётся опубликованным на период перекрытия. **Компрометация:** ключ публикуется со статусом `REVOKED`, подпись им агент отвергает.
- **Агент:** кэширует `platform_keys`; неизвестный `kid` — одно перечитывание конфигурации, затем отказ; `REVOKED` и истёкший — отказ (инвариант 3).
- **Событие подписывается при каждой отправке**, а не при создании: повторная доставка проверяется действующим ключом.

## 5. mTLS песочницы и операторы (РП27, РП28)

- **УЦ песочницы** — у Платформы, ключ ECDSA P-256. Выпускает сертификаты агентов (SAN URI `urn:nspk:agent:<id>:v<N>`) и операторов агентов (SAN URI `urn:nspk:operator:<id>`).
- **Ключ сертификата** генерирует оператор агента и присылает CSR; сертификат агента выдаётся в решении о допуске (ПС01), оператора — при регистрации оператора.
- **Выпуск** (РП65): один шаблон — P-256, `ecdsa-with-SHA256`, пустой субъект, SAN-URI агента из записи реестра (не из CSR), CA:false, clientAuth; CSR проверяется по подписи и строго по DER с пределом длины; свой код без сторонних библиотек, перекрёстная проверка `openssl` в CI.
- **Ступень 0 проверки обращения ПАО** (РП27 п. 3, РП66 п. 1–2): своя проверка DER из соединения по часам Платформы — нет сертификата, цепочка не к УЦ песочницы, SAN не ровно один URI агента, серийного номера нет в реестре (чтение на каждом обращении, без кэша) или запись другого агента, код из SAN не равен `x-agent-code`, сертификат вне срока или отозван — `AGENT_UNKNOWN` (401, `never`: сертификат канала перевыпускает оператор агента, а `AGENT_KEY_REVOKED` вёл бы агента к ротации ключа подписи); сбой чтения списка отзыва — `UPSTREAM_UNAVAILABLE` (503). Вид причины — только в журнал процесса; отдельный код канала — кандидат в ПАО 1.5.0 (#37). Далее — РП23 п. 6. TLS запрашивает сертификат, но рукопожатие без него не обрывает: решение — в приложении, после грубого лимита по адресу (Ш12). `/.well-known/pao-configuration` и `/health` — без сертификата клиента.
- **TLS — только на Платформе** (РП66 п. 3): TCP-прокси допустим; сертификат клиента из заголовка L7-прокси не принимается до решения в PS-26. **`PAO_TRUSTED_PROXIES` при TLS в процессе — остаточный риск снят** (РП67, v0.32.1; КТ1 К3.1 № 3): прокси перед песочницей — только L4, `X-Forwarded-For` он не добавляет, и заголовок приходит от клиента внутри TLS; при непустом списке агент подставил бы адрес и обошёл грубый лимит (Ш12, РП32 п. 5). Поэтому sandbox с непустым списком не запускается — `STARTUP_PROXIES_INVALID`, вид причины `TLS_IN_PROCESS`; dev — без изменений; будущая среда, кроме dev, — тоже запрет (РП67 п. 7). Запасной запрет — в `buildServer`: `tls` с непустым списком — исключение до `listen` при любом месте вызова (РП67 п. 6). За L4-прокси без PROXY protocol адрес клиента — адрес прокси, грубый лимит общий для всех за ним; пересмотр — PS-26 (прокси седьмого уровня). Сертификат сервера — от УЦ песочницы, имена — `PLATFORM_TLS_HOSTNAMES`, ключ — в памяти, новый при каждом запуске (п. 4). `notBefore` выданных сертификатов — с запасом `cert_not_before_backdate_sec` на чужие часы (п. 5). Только TLS 1.3; TLS и ступень 0 — только вместе, иначе отказ запуска; `authorized` TLS — условие ступени 0 в дополнение к своей проверке; сертификат и запись `agent_certificates` — одно чтение за обращение, отзыв во время чтения тела текущее обращение не прерывает, если с предпроверки прошло не больше `revocation_propagation_max_ms` (РП66 «Дополнение и нюансы К3»). **Возобновления сессии TLS нет** (развилка № 8 (А), РП66 «Нюансы 2б-1» п. 1): каждое подключение — полное рукопожатие с сертификатом клиента, блоб сессии у клиента канал не даёт. Пересмотр — после нагрузочного теста этапа 6 (тогда короткий срок сессии, не 300 с).
- **Свой ключ сертификата на агента** (РП66 п. 8): реестр повтор ключа между агентами не проверяет, но украденный общий ключ даёт канал за всех агентов с ним — оператору агента генерировать отдельную пару на каждый агент.
- **Отзыв сертификата** — только при компрометации ключа сертификата и по заявлению оператора агента; приостановление и исключение сертификат не отзывают — их режет статус (РП23 п. 6.3), и агент по-прежнему узнаёт свой статус через `GET /pao/v1/agent`. Список отзыва — в реестре, распространяется как отзыв ключа (инвариант 8).
- **Операторы:** учётная запись оператора в песочнице — по заявке на одинаковых условиях (РП17, A6 п. 2.1); в контуре оператора — по договору с Оператором Системы, вне Платформы, на публичных и одинаковых для всех операторов условиях. `AgentRegistry.admit` получает оператора только из контекста, созданного слоем аутентификации.
- **Стенд dev** (РП25) — без mTLS: работает внутри процесса теста агента и песочницей не является.
- **Контур оператора:** ГОСТ TLS, сертификаты — УЦ оператора; требования — SEC-2.

## 6. Ограничения песочницы до постоянного хранилища (CO-1, CO-2)

- **Ключ УЦ — файл на постоянном томе** (РП65 п. 4, РП66 п. 6; код — SEC-1-код ч. 2б-1, К1.1). Реестр, ключи агентов и сертификаты — на PostgreSQL с v0.29.0 и переживают перезапуск; ключ УЦ — в файле `PLATFORM_CA_KEY_PATH` (права 0600 или 0400, вне репозитория и журнала), песочница без него не запускается. Файл создаёт только явная инициализация (`npm run ca:init`, без перезаписи): нет пути, нет файла, права шире 0600, файл не разбирается, ключ не от сертификата, УЦ вне срока — отказ запуска `STARTUP_CA_KEY_INVALID` с видом причины в журнале, а не новый УЦ (неверно смонтированный том иначе молча обесценил бы все выданные сертификаты; РП66 п. 6); тот же код **без вида причины** — УЦ загружен, но сертификат сервера не выпущен (имена `PLATFORM_TLS_HOSTNAMES`, параметры срока): **УЦ не пересоздавать** (РП66 «Нюансы хвостов» п. 2); `ca:init` выводит отпечаток SHA-256 и открытый корневой сертификат PEM — агент сверяет отпечаток при настройке. dev — без TLS и УЦ (п. 7). **Остаточный риск:** при потере файла выданные сертификаты не проверяются, а повторный допуск — `CODE_TAKEN`; процедура оператора — «Перед пилотом с банком» (STATUS «Открыто»). Ключи Платформы до SEC-1-кода ч. 3 не созданы: ответы и события не подписаны (до ПАО 1.5.0).
- **Один экземпляр.** Миграции ядра применяются при запуске одним экземпляром (РП30 п. 5): второй экземпляр песочницы не запускается. Реестр агентов — на PostgreSQL без кэша (PS-05в, v0.29.0), так что отзыв ключа виден с любого экземпляра по коду; PG-теста «отзыв на одном экземпляре → `AGENT_KEY_REVOKED` на другом» нет (Ш7 «частично», §7; PS-05в ч. 3). Nonce — на PostgreSQL (Ш3а закрыто, РП30). *(Уточнено сверкой 02.11: прежде — «отзыв виден только внутри процесса, реестр в памяти до PS-06».)*
- **Журнал согласий** — на PostgreSQL, только вставка: UPDATE, DELETE и TRUNCATE отвергаются триггерами, подмена в обход журнала обнаруживается хэш-цепочкой (Ж1 закрыто, §7). *(Уточнено сверкой 02.11: прежде — «до CO-1 не защищён».)*

После CO-1 и CO-2 ключ УЦ и ключи Платформы (в песочнице — в постоянном хранилище; в контуре оператора — HSM) переезжают вместе с реестром, ключами агентов и списком отзыва — в PS-05 (зависит от CO-2) *(уточнено РП65: реестр, ключи агентов и список отзыва — PostgreSQL; ключ УЦ — файл на постоянном томе, не PG; ключи Платформы — SEC-1-код ч. 3)*; nonce и идемпотентность — CO-2, PS-05; очередь событий — PS-08 на Outbox agentic-core. ## 8. Внешние зависимости пилота (SEC-2 ч. 2, К5)
