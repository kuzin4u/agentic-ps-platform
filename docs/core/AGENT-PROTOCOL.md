## 1. Назначение и границы

ПАО — интерфейс, через который агент покупателя (BuyerAgent и любые другие допущенные агенты) взаимодействует с Платформой платёжной системы.

Через ПАО агент:
- узнаёт свой статус и управляет ключами;
- запрашивает мандаты, а принципал подписывает их в банке;
- проверяет мандат и остаток;
- получает **агентский платёжный реквизит** на конкретный заказ;
- узнаёт о подтверждениях, авторизациях, расчётах, отзывах и приостановлениях;
- подаёт спор по поручению человека и получает выписку из журнала.

Чего через ПАО **нет**:
- авторизации платежа — её инициирует продавец через эквайрера (РП2);
- номера карты, счёта и любых платёжных реквизитов принципала;
- персональных данных принципала — только ссылка `principal_ref`;
- изменения ограничений — это делает человек в банке (A3 п. 2.2).

## 2. Транспорт и безопасность

- HTTPS, TLS 1.2+; **mTLS**: клиентский сертификат выдаётся при допуске и связан с `agent_code`. В контуре оператора — ГОСТ TLS. В песочнице (РП27): ключ сертификата генерирует оператор агента и передаёт CSR; сертификат выпускает УЦ песочницы, код агента — в SAN URI `urn:nspk:agent:<id>:v<N>`; код из сертификата должен совпасть с `x-agent-code`, иначе `AGENT_UNKNOWN`; истёкший или отозванный сертификат — `AGENT_KEY_REVOKED`. Приостановление и исключение сертификат не отзывают.
- **Подпись каждого обращения** (HTTP Message Signatures): подписываются `@method`, `@path`, `@query`, `content-digest`, `x-agent-code`, `x-timestamp`, `x-nonce`. У запросов без тела (GET, DELETE без тела) `content-digest` вычисляется от пустого тела: `sha-256=:47DEQpj8HBSa+/TImW+5JCeuQeRkm5NMpJWZG3hSuFU=:` (РП16). Алгоритм — по ключу (`ed25519` в песочнице, ГОСТ Р 34.10-2012 в контуре оператора). Окно времени — `signature_skew_sec`; `x-nonce` не повторяется в пределах окна.
- **Код агента, класс и уровень** Платформа берёт из реестра по сертификату и ключу. Значения в теле запроса игнорируются.
- **Идемпотентность:** изменяющие методы требуют `Idempotency-Key`. Повтор с тем же ключом и тем же телом возвращает прежний результат; с тем же ключом и другим телом → `IDEMPOTENCY_CONFLICT`.
  - **Мандаты** (`POST /pao/v1/mandates`, РП33 доп.): id мандата Платформа вычисляет из кода агента и ключа. Повтор того же запроса с тем же ключом возвращает тот же мандат в любой срок, в том числе после долгого сбоя и через 24 ч. В течение 24 ч это сохранённый ответ (статус — на момент первого ответа); позже — мандат со статусом на момент повтора (после `valid_to` — `EXPIRED`). Актуальный статус всегда — `GET /pao/v1/mandates/{id}`. Ключ, по которому запрошен мандат, для другого запроса не используйте: `IDEMPOTENCY_CONFLICT` 409 в любой срок, а не только 24 ч. Ответ 503 — повтор тем же ключом (`same_key`) не раньше `Retry-After`: запись, прерванная сбоем, будет доделана. Если состояние не восстанавливается до исчерпания ваших повторов — сообщите клиенту об ошибке и не создавайте новый мандат молча: новый ключ (и новый мандат) — только после нового подтверждения поручения клиентом.
- **Ограничение частоты** зависит от уровня допуска; превышение → `RATE_LIMITED` с `Retry-After`. `Retry-After` передаётся и с ответами 503.
- **Ответы и события Платформы подписаны** её ключами — **с ПАО 1.5.0** (РП26, РП31, РП37; в 1.2.0–1.4.0 Платформа их не подписывает). RFC 9421: `Signature-Input` и `Signature` с меткой `platform`, параметры `keyid` (ключ Платформы), `alg`, `created`; компоненты ответа — `@status`, `content-digest`, `x-agent-code`, `@method;req`, `@path;req`, `x-nonce;req`, события — `content-digest`, `x-event-id`, `x-agent-code`. `created` вне окна `signature_skew_sec` — отказ. Ключи ответов и событий разные: ключ без `use` или с чужим `use` — отказ. Агент обязан проверять подпись событий. Ключи Платформы — в `platform_keys` `/.well-known/pao-configuration`; неизвестный `kid` — одно перечитывание конфигурации, затем отказ; `REVOKED` — отказ.

Пример заголовков:

```
POST /pao/v1/credentials
X-Agent-Code: nspk:agent:buyref-01:v3
X-Timestamp: 2026-10-08T08:41:12Z
X-Nonce: 3f9a1c0e
Idempotency-Key: 7c1f-...-a904
Content-Digest: sha-256=:9f2b...:
Signature-Input: sig1=("@method" "@path" "@query" "content-digest" "x-agent-code" "x-timestamp" "x-nonce");keyid="kPrK_qmxVWaYVA9wwBF6Iuo3vVzz7TxHCTwXBygrS4k";alg="ed25519"
Signature: sig1=:MEQCIF...:
```

`keyid` — отпечаток JWK открытого ключа агента по RFC 7638, присваивает Платформа (РП23); в примере — ключ RFC 8037 прил. A.3.

## 4. Агентский платёжный реквизит и пакет для продавца

`POST /pao/v1/credentials`:

```json
{
  "mandate_id": "MND-8f31c0",
  "order_ref": "ORD-77a1",
  "merchant_id": "MER-1042",
  "amount_max": 189000,
  "currency": "RUB",
  "kind": "CARD"
}
```

Условия выдачи: мандат CART действует; `merchant_id` в его области; `amount_max` ≤ сумме мандата корзины; агент ACTIVE. Ответ:

```json
{
  "credential_ref": "CRD-91b0",
  "kind": "CARD",
  "payload": { "token_ref": "tok_ag_7f2c", "cryptogram": "base64...", "valid_to": "2026-10-08T08:56:12Z" },
  "aoi": { "indicator": true, "agent_code": "nspk:agent:buyref-01:v3", "mandate_id": "MND-8f31c0" }
}
```

Агент передаёт продавцу **пакет агентской оплаты** — `PaymentPackage` (РП22 п. 5):

| Поле | Что |
|---|---|
| `credential_ref` | ссылка на реквизит из ответа `POST /credentials`; ключ сверки продавца с Платформой (РП22 п. 6) |
| `kind` | вид реквизита, как в ответе |
| `payload` | как в ответе, без изменений |
| `aoi` | признак агентной операции, как в ответе |
| `cart_mandate_id` | ссылка на мандат корзины |
| `order_ref` | ссылка продавца на заказ |

Пакет подписан агентом по RFC 9421 тем же ключом, что и обращения ПАО: продавец находит его по `kid` в каталоге ключей агентов (JWKS, РП22 п. 1) и проверяет `agent_code` ключа. **Суммы в пакете нет**: сумма операции берётся только из сообщения процессинга (инвариант 5). Продавец или эквайрер переносят `aoi` в авторизацию (ПИ-2). Криптограмма одноразовая и годится только для этого продавца и суммы не выше `amount_max`. Состав описан в v1.2 описательно; схема `PaymentPackage` — в ПАО 1.5.0 (РП31, РП37) (совместимое изменение: новая схема, §7). Разбор и проверка пакета у продавца — набор продавца agentic-core (CO-4).

Для `kind = SBP` в `payload` — идентификатор агентского списания по привязке счёта; списание инициирует продавец через банк-участник.

## 5. События

Доставка — POST на адрес подписки, тело подписано Платформой (с ПАО 1.5.0, §2); повтор с экспоненциальной задержкой до `event_retry_max`. Обработка у агента обязана быть идемпотентной по `event_id`.

**До ПАО 1.5.0 события не подписаны (РП39 п. 6): событие — сигнал, а не источник статуса.** По `mandate.*` агент перечитывает `GET /pao/v1/mandates/{id}` и действует по прочитанному статусу, а не по `type`; это правило безопасно и после 1.5.0. Дубли, а также события, после которых статус не изменился, — норма (повторное решение или запись после отзыва на другом экземпляре, РП38 п. 5).

- **Лента (pull):** `GET /pao/v1/events?after=<event_id>` — события только вашего агента после `after`, по порядку, не больше `event_page_max` за ответ; без `after` — с начала. Курсор — `event_id` последнего обработанного события; повторное чтение даёт те же события с теми же `event_id`. Чужой или неизвестный `after`, а также пустой, повторённый или не по форме `evt_` + UUID — 400 `REQUEST_INVALID` (в YAML — с ПАО 1.5.0). Порядок событий задаёт только лента; push-доставка порядка не гарантирует.
- **Подписка (push):** `PUT /pao/v1/subscription` с `Idempotency-Key` — `url` только `https://`, порт 443, имя хоста (не IP) из списка оператора; иначе 400 `REQUEST_INVALID` (свой код — с ПАО 1.5.0); имя должно разрешаться только в глобальные адреса, проверка — при подписке и перед каждой отправкой. 400 — отказ самого адреса (форма, не глобальный адрес, имени нет в DNS); он сохраняется под ключом идемпотентности, исправленный адрес — с новым `Idempotency-Key`. Временный сбой или таймаут DNS — 503 `STATE_UNAVAILABLE` без сохранения: повтор тем же ключом по `Retry-After`. `events` — типы из таблицы ниже; пустой список выключает push. Подписка действует на события после неё; события, ещё не доставленные push, уходят по **текущей** подписке: после смены `url` повтор идёт на новый адрес, тип исключён из `events` — push по нему прекращается, событие остаётся в ленте (РП40 доп. п. 11). Платформа шлёт POST с `Event` и заголовком `x-event-id`; успех — только 2xx в пределах `event_delivery_timeout_ms`; перенаправления не выполняются; повтор — до `event_retry_max` попыток всего с растущей задержкой, затем событие — только в ленте. Push не заменяет ленту: после сбоя, при старте и после приостановки читайте ленту с курсора (РП40).
- **Приостановление и исключение:** при `SUSPENDED` и `EXCLUDED` лента и подписка — 403 `AGENT_SUSPENDED` (как `GET` мандата; открыт только `GET /pao/v1/agent`, а при `SUSPENDED` — ещё `POST /pao/v1/mandates/{id}/relinquish`, РП38 доп. п. 8), push не выполняется. События сохраняются и после снятия приостановки доступны через ленту; push по накопленным не догоняет (РП40 п. 6–7). О собственном приостановлении агент узнаёт по 403 `AGENT_SUSPENDED` на любом методе, кроме `GET /pao/v1/agent` и отказа от полномочий; событие `agent.suspended` ему push не доставляется.
- **`data` событий мандата** — только `{mandate_id}`: ни статуса, ни предмета, ни сумм. Событие даёт запись журнала по мандату: `mandate.signed`, `mandate.rejected`, `mandate.revoked` (отзыв клиентом — одного мандата или всех полномочий клиента одним действием в банке, РП45 п. 4; или ваш `relinquish`), `mandate.exhausted` — закреплён (списан по клирингу) весь предел; резервы, которые ещё не списаны, его не вызывают. Событие может прийти дважды или с задержкой; при нехватке бюджета авторизации отклоняются и до него, статус — через `GET` (РП41 п. 11). У CART, которые теряют силу вместе с родителем, своих событий нет — статус CART берите через `GET` (§3, РП35). **Исключение — отзыв всех полномочий клиента (`revoke-all`, РП46 (а)):** Платформа пишет отзыв каждому действующему мандату клиента, сначала CART, затем родителю, — `mandate.revoked` приходит по каждому, в том числе по CART. Мандаты перестают действовать с фиксации отзыва в Платформе, до прихода событий: `GET` и `verify` уже отвечают `REVOKED` / `OUT_OF_SCOPE`. Мандат, подписанный банком после отзыва, — новое согласие и действует.

| Событие | Когда | Что обязан сделать агент (SPEC BuyerAgent) |
|---|---|---|
| `mandate.signed` | Принципал подписал | Продолжить стадию |
| `mandate.rejected` | Принципал отказал | Сообщить человеку, остановиться |
| `mandate.revoked` | Отзыв | Остановить начатое, отчитаться о незавершённом (Т13) |
| `mandate.exhausted` | Бюджет исчерпан: закреплён весь предел | Уведомить человека |
| `confirmation.required` | ADP потребовала подтверждения | Передать человеку ссылку, не имитировать (Т7) |
| `confirmation.approved` / `.rejected` / `.expired` | Итог подтверждения | Повторить через продавца с `confirmation_ref` / остановиться |
| `operation.authorized` | Авторизация одобрена | Показать человеку |
| `operation.declined` | Отказ, `reason` из ПИ-1 | Поведение по таблице отказов (раздел 6) |
| `operation.settled` | Клиринг, запись об исполнении | Итог и документы человеку (Т11) |
| `operation.refunded` | Возврат | Показать человеку |
| `agent.key_revoked` | Отзыв ключа | Перейти на новый ключ или остановиться |
| `agent.suspended` / `agent.reinstated` | Статус допуска | Остановиться / продолжить |
| `dispute.updated` | Решение по спору | Сообщить человеку |

**Правило источника истины.** О результате операции агент узнаёт из события Платформы, а не со слов продавца. Если сообщение продавца расходится с событием Платформы, агент верит Платформе и записывает расхождение. До ПАО 1.5.0 событие не подписано: по нему агент перечитывает статус через `GET` и верит прочитанному (РП39 п. 6).

## 6. Ошибки

Тело ошибки: `{ "code", "message", "norm", "retry": "never|after_fix|same_key|new_key|after_human" }`. Перечень кодов с HTTP-статусом и `retry` — в `agent-protocol.yaml`, расширение `x-pao-errors` (источник; таблица ниже — для чтения, при расхождении верен YAML; РП16).

Значения `retry`:

| Значение | Что делает клиент |
|---|---|
| `never` | Не повторяет. |
| `after_fix` | Повтор только после исправления запроса или состояния на своей стороне. |
| `same_key` | Повтор с тем же `Idempotency-Key`; новые `x-nonce`, `x-timestamp` и подпись. Если есть `Retry-After` — не раньше указанного. Число повторов ограничивает клиент; после исчерпания — ошибка вызывающему. У `IDEMPOTENCY_REQUIRED` — добавить ключ и повторять с ним же. |
| `new_key` | Нужен новый ключ подписи агента (не ключ идемпотентности); повтор — после выпуска и регистрации ключа. |
| `after_human` | Повтор после действия человека (подпись, подтверждение, изменение мандата). |


| Код | HTTP | Причина | `retry` |
|---|---|---|---|
| AGENT_UNKNOWN | 401 | Нет в реестре | never |
| AGENT_SUSPENDED | 403 | Приостановлен | never |
| AGENT_KEY_REVOKED | 401 | Ключ отозван или истёк | new_key |
| SIGNATURE_INVALID | 401 | Подпись, окно времени, повтор nonce | after_fix |
| MANDATE_NOT_FOUND | 404 | Мандат не найден | after_human |
| MANDATE_EXPIRED | 409 | Мандат истёк | after_human |
| MANDATE_REVOKED | 409 | Мандат отозван | never |
| MANDATE_SCOPE | 409 | Продавец, категория или сумма вне мандата | after_human |
| PRINCIPAL_SIGNATURE_PENDING | 409 | Мандат ещё не подписан | after_human |
| LIMIT_EXCEEDED | 409 | Ограничение инструмента или лимит клиента в банке (`per_operation`, `per_period` — РП45 п. 1; сужение лимита в банке действует сразу, в том числе в текущем периоде, РП46 (г); повтор не поможет до нового периода или правки лимита в банке) | after_human |
| STATE_UNAVAILABLE | 503 | Состояние не подтверждено | same_key |
| CONFIRMATION_REQUIRED | 428 | Нужно подтверждение | after_human |
| CREDENTIAL_INVALID | 409 | Реквизит использован, истёк, не для этого продавца | after_fix |
| CREDENTIALS_FORBIDDEN | 422 | В запросе есть платёжные реквизиты | never |
| IDEMPOTENCY_REQUIRED | 400 | Нет ключа | same_key |
| IDEMPOTENCY_CONFLICT | 409 | Тот же ключ, другое тело | after_fix |
| RATE_LIMITED | 429 | Частота | same_key |
| UPSTREAM_UNAVAILABLE | 503 | Компонент Платформы недоступен | same_key |
| REQUEST_INVALID | 400 | Тело изменяющего метода не по схеме метода (v1.3.0, РП31) | after_fix |
| KEY_INVALID | 422 | Ключ не принят в `POST /pao/v1/agent/keys` (v1.3.0, РП31) | after_fix |

## 7. Версии и совместимость

- Версия в пути (`/pao/v1`). Совместимые изменения — новые необязательные поля и новые типы событий; обязательность поля **ответа**, которое Платформа отдавала во всех ответах и прежде (агенту — ослабление: поле, которое он мог не получить, приходит всегда; РП37, `Mandate.agent_code`), — тоже; обязательность поля запроса — несовместима; агент обязан игнорировать неизвестные поля и события. Совместимо и ослабление `retry` у существующего кода — разрешение повтора там, где его не было (`never` или `after_fix` → `same_key`); обратный переход несовместим (РП18). Совместимость не отменяет обоснования: перевод кода из never в same_key — отдельным решением РП с оценкой безопасности повтора.
- Новое значение `ErrorCode` с `retry` `after_fix` или `never` — совместимо: агент на неизвестный код останавливается (fail-closed), и это поведение совпадает с `after_fix`. Новое значение с `same_key` — несовместимо: агент прежней версии не повторит там, где повтор ожидается (РП31 п. 4).
- Несовместимые изменения — только новой версией с периодом параллельной работы не меньше `protocol_overlap_days`.
- `GET /.well-known/pao-configuration` сообщает поддерживаемые версии и дату вывода старых.

## 8. Соответствие отраслевым протоколам

| ПАО | AP2 | EMVCo (черновик) | A2A |
|---|---|---|---|
| Мандат INTENT | Intent Mandate | Open mandate / Intent | — |
| Мандат CART | Cart Mandate | Checkout / closed mandate | — |
| Реквизит + `aoi` | Payment Mandate | Agentic Transaction Indicator | — |
| Журнал согласий, `verify` | — | Intent Services | — |
| Реестр, ключи | — | Know Your Agent | Agent Card (подписанная) |

Агент публикует Agent Card (A2A) с расширением `x-system`: `agent_code`, класс, принципал (тип), источник знания, ссылка на `/.well-known/pao-configuration` Платформы. Платформа при допуске сверяет карточку с заявлением. Отступления фиксируются в журнале расхождений (A9 п. 5).

## 8а. Условное исполнение (v1.1.0)

Мандат с `settlement_mode = CONDITIONAL` и `conditional = {provider, deal_ref}` направляет оплату на счёт эскроу поставщика условного исполнения. `deal_ref` переносится в признак и операции; итог сделки приходит событиями `deal.funded`, `deal.released`, `deal.returned`. Метода «раскрыть эскроу» в ПАО нет. Подробно — `CONDITIONAL-EXECUTION.md`.
