## 1. Назначение и границы

ПАО — интерфейс, через который агент покупателя (BuyerAgent и любые другие допущенные агенты) взаимодействует с Платформой платёжной системы.

Через ПАО агент:
- узнаёт свой статус и управляет ключами;
- запрашивает мандаты, а принципал подписывает их в банке;
- проверяет мандат и остаток;
- получает **агентский платёжный реквизит** на конкретный заказ;
- узнаёт о подтверждениях, авторизациях, расчётах, отзывах и приостановлениях;
- подаёт спор по поручению человека и получает выписку из журнала.

Чего через ПАО **нет**:
- авторизации платежа — её инициирует продавец через эквайрера (РП2);
- номера карты, счёта и любых платёжных реквизитов принципала;
- персональных данных принципала — только ссылка `principal_ref`;
- изменения ограничений — это делает человек в банке (A3 п. 2.2).

## 2. Транспорт и безопасность

- HTTPS, TLS 1.2+; **mTLS**: клиентский сертификат выдаётся при допуске и связан с `agent_code`. В контуре оператора — ГОСТ TLS. В песочнице (РП27): ключ сертификата генерирует оператор агента и передаёт CSR; сертификат выпускает УЦ песочницы, код агента — в SAN URI `urn:nspk:agent:<id>:v<N>`; код из сертификата должен совпасть с `x-agent-code`, иначе `AGENT_UNKNOWN`; истёкший или отозванный сертификат канала — тоже `AGENT_UNKNOWN` (РП66): это не ключ подписи, его перевыпускает оператор агента — агенту остановиться и обратиться к оператору, а не регистрировать новый ключ (отдельный код — кандидат в ПАО 1.5.0). Приостановление и исключение сертификат не отзывают. Ключ сертификата — свой у каждого агента.
- **Подпись каждого обращения** (HTTP Message Signatures): подписываются `@method`, `@path`, `@query`, `content-digest`, `x-agent-code`, `x-timestamp`, `x-nonce`. У запросов без тела (GET, DELETE без тела) `content-digest` вычисляется от пустого тела: `sha-256=:47DEQpj8HBSa+/TImW+5JCeuQeRkm5NMpJWZG3hSuFU=:` (РП16). Алгоритм — по ключу (`ed25519` в песочнице, ГОСТ Р 34.10-2012 в контуре оператора). Окно времени — `signature_skew_sec`; `x-nonce` не повторяется в пределах окна.
- **Код агента, класс и уровень** Платформа берёт из реестра по сертификату и ключу. Значения в теле запроса игнорируются.
- **Идемпотентность:** изменяющие методы требуют `Idempotency-Key`. Повтор с тем же ключом и тем же телом возвращает прежний результат; с тем же ключом и другим телом → `IDEMPOTENCY_CONFLICT`.
  - **Мандаты** (`POST /pao/v1/mandates`, РП33 доп.): id мандата Платформа вычисляет из кода агента и ключа. Повтор того же запроса с тем же ключом возвращает тот же мандат в любой срок, в том числе после долгого сбоя и через 24 ч. В течение 24 ч это сохранённый ответ (статус — на момент первого ответа); позже — мандат со статусом на момент повтора (после `valid_to` — `EXPIRED`). Актуальный статус всегда — `GET /pao/v1/mandates/{id}`. Ключ, по которому запрошен мандат, для другого запроса не используйте: `IDEMPOTENCY_CONFLICT` 409 в любой срок, а не только 24 ч. Ответ 503 — повтор тем же ключом (`same_key`) не раньше `Retry-After`: запись, прерванная сбоем, будет доделана. Если состояние не восстанавливается до исчерпания ваших повторов — сообщите клиенту об ошибке и не создавайте новый мандат молча: новый ключ (и новый мандат) — только после нового подтверждения поручения клиентом.
- **Ограничение частоты** зависит от уровня допуска; превышение → `RATE_LIMITED` с `Retry-After`. `Retry-After` передаётся и с ответами 503.
  - **Два слоя** (РП32, РП63). Первый — по адресу обращения, до проверки подписи: общий для всех агентов за одним адресом, в `AgentSelf` не отражается. Второй — по коду агента после верной подписи: предел в минуту по уровню допуска — **`rate_limit_per_min` в `GET /pao/v1/agent`**; считается фиксированными окнами по 30 с, в окне — не больше половины `rate_limit_per_min`. Окно не скользит: на стыке двух окон подряд может пройти до `rate_limit_per_min`, за любые 60 с — до 1,5 × `rate_limit_per_min`; ровную частоту держите сами — не больше `rate_limit_per_min` в минуту. `Retry-After` у 429 — от 1 до 30. Обращение с неверной подписью квоту агента не тратит. После 429 второго слоя nonce обращения уже израсходован: повтор подписывается заново (новый `x-nonce`) с тем же `Idempotency-Key`. Значения на стенде — PARAMS (`pao_agent_rate_limit_per_min_l1` / `_l2` / `_l3`).
- **Ответы и события Платформы подписаны** её ключами — **с ПАО 1.5.0** (РП26, РП31, РП37; в 1.2.0–1.4.0 Платформа их не подписывает). RFC 9421: `Signature-Input` и `Signature` с меткой `platform`, параметры `keyid` (ключ Платформы), `alg`, `created`; компоненты ответа — `@status`, `content-digest`, `x-agent-code`, `@method;req`, `@path;req`, `x-nonce;req`, события — `content-digest`, `x-event-id`, `x-agent-code`. `created` вне окна `signature_skew_sec` — отказ. Ключи ответов и событий разные: ключ без `use` или с чужим `use` — отказ. Агент обязан проверять подпись событий. Ключи Платформы — в `platform_keys` `/.well-known/pao-configuration`; неизвестный `kid` — одно перечитывание конфигурации, затем отказ; `REVOKED` — отказ.

Пример заголовков:

```
POST /pao/v1/credentials
X-Agent-Code: nspk:agent:buyref-01:v3
X-Timestamp: 2026-10-08T08:41:12Z
X-Nonce: 3f9a1c0e
Idempotency-Key: 7c1f-...-a904
Content-Digest: sha-256=:9f2b...:
Signature-Input: sig1=("@method" "@path" "@query" "content-digest" "x-agent-code" "x-timestamp" "x-nonce");keyid="kPrK_qmxVWaYVA9wwBF6Iuo3vVzz7TxHCTwXBygrS4k";alg="ed25519"
Signature: sig1=:MEQCIF...:
```

`keyid` — отпечаток JWK открытого ключа агента по RFC 7638, присваивает Платформа (РП23); в примере — ключ RFC 8037 прил. A.3.

## 4. Агентский платёжный реквизит и пакет для продавца

`POST /pao/v1/credentials`:

```json
{
  "mandate_id": "MND-8f31c0",
  "order_ref": "ORD-77a1",
  "merchant_id": "MER-1042",
  "amount_max": 189000,
  "currency": "RUB",
  "kind": "CARD"
}
```

Условия выдачи: мандат CART действует; `merchant_id` в его области; `amount_max` ≤ сумме мандата корзины; агент ACTIVE. Порядок и коды (РП47 п. 4): мандат не найден или чужой — 404 `MANDATE_NOT_FOUND`; не подписан — 409 `PRINCIPAL_SIGNATURE_PENDING`; истёк — 409 `MANDATE_EXPIRED`; отозван или отклонён — 409 `MANDATE_REVOKED`; `EXHAUSTED` — 409 `LIMIT_EXCEEDED` (у CART статус — вместе с родителем); не CART, продавец вне области, валюта ≠ валюте CART, `amount_max` > `amount_limit` CART, клиент не дал согласия на токен (`token_consent: false`), продавца области CART нет в справочнике продавцов оператора (РП49 (д); проверяется при первой выдаче по CART, когда выпускается токен) — 409 `MANDATE_SCOPE` (`after_human`: нужен новый мандат); `kind: SBP` — 409 `CREDENTIAL_INVALID` (`after_fix`: брать `CARD`; СБП — с PS-21); состояние не прочитано — 503 `STATE_UNAVAILABLE`, токен-сервис или банк недоступны — 503 `UPSTREAM_UNAVAILABLE`. Остаток бюджета при выдаче не резервируется — деньги проверяет ADP в авторизации.

**Повтор по заказу (РП47 п. 5, ПС05):** реквизит определяется парой «CART + `order_ref`». Повтор с теми же `merchant_id`, `amount_max`, `currency` возвращает тот же реквизит — тот же `credential_ref`, ту же криптограмму и `valid_to`, текущий `status`; тот же `order_ref` с другими значениями — 409 `IDEMPOTENCY_CONFLICT`. Использованный или истёкший реквизит повтором не обновляется — новая оплата идёт с новым `order_ref`. Криптограмма гасится только одобренной авторизацией: после отказа или `CONFIRMATION_REQUIRED` тот же реквизит годен для повтора заказа.

**Повтор под тем же `Idempotency-Key` (РП48 (в)):** тот же реквизит с той же криптограммой и текущим `status` (`USED` после одобренной авторизации, `EXPIRED` после `valid_to`). Платформа не хранит значение криптограммы под ключом и пересчитывает её при повторе; если токен-сервис в этот момент недоступен — 503 `UPSTREAM_UNAVAILABLE`, если запись реквизита не подтверждена — 503 `STATE_UNAVAILABLE` (оба `same_key`, по `Retry-After`); сохранённый 201 при повторе никогда не становится окончательным отказом, ответ не теряется. 503 при повторе может держаться долго (до срока хранения ключа, 24 ч) — число повторов ограничивает агент; после исчерпания — ошибка вызывающему. Состояние мандата при повторе под ключом не перепроверяется — это прежний ответ; авторизацию по отозванному мандату отклонит Платформа.

**Платёжных реквизитов в теле нет** (РП47 доп. п. 2): поле `pan`, `card_number`, `cvv`, `expiry` и подобные или похожая на номер карты серия с верной суммой Луна в любом значении или имени поля — 422 `CREDENTIALS_FORBIDDEN` (`never`) до разбора тела; ключ идемпотентности при этом не занимается. Похожая серия (РП49 (а)) — сплошные 13–19 цифр или группы по 4 цифры через одиночный пробел или дефис (последняя — 1–4, всего 13–19), в том числе внутри серии чисел через одиночный пробел или дефис (сплошная серия длиннее 19 цифр не проверяется); фрагменты в форме UUID не проверяются — `order_ref` с UUID допустим. Ссылки заказа и продавца — непрозрачные: `order_ref` из таких цифр (например, `ORD-2026-1021-0001-0002`, если сумма Луна сошлась) получит 422. `kind: SBP` проверяется после мандата и области (несуществующий мандат — 404). Сумма операции выше `amount_max` — `LIMIT_EXCEEDED` в авторизации, событием `operation.declined` (PS-16).

Ответ:

```json
{
  "credential_ref": "CRD-91b0",
  "kind": "CARD",
  "payload": { "token_ref": "tok_ag_7f2c", "cryptogram": "base64...", "valid_to": "2026-10-08T08:56:12Z" },
  "aoi": { "indicator": true, "agent_code": "nspk:agent:buyref-01:v3", "mandate_id": "MND-8f31c0" }
}
```

Агент передаёт продавцу **пакет агентской оплаты** — `PaymentPackage` (РП22 п. 5):

| Поле | Что |
|---|---|
| `credential_ref` | ссылка на реквизит из ответа `POST /credentials`; ключ сверки продавца с Платформой (РП22 п. 6) |
| `kind` | вид реквизита, как в ответе |
| `payload` | как в ответе, без изменений |
| `aoi` | признак агентной операции, как в ответе |
| `cart_mandate_id` | ссылка на мандат корзины |
| `order_ref` | ссылка продавца на заказ |

Пакет подписан агентом по RFC 9421 тем же ключом, что и обращения ПАО: продавец находит его по `kid` в каталоге ключей агентов (JWKS, РП22 п. 1) и проверяет `agent_code` ключа. **Суммы в пакете нет**: сумма операции берётся только из сообщения процессинга (инвариант 5). Продавец или эквайрер переносят `aoi` в авторизацию (ПИ-2). Криптограмма одноразовая и годится только для этого продавца и суммы не выше `amount_max`. Состав описан в v1.2 описательно; схема `PaymentPackage` — в ПАО 1.5.0 (РП31, РП37) (совместимое изменение: новая схема, §7). Разбор и проверка пакета у продавца — набор продавца agentic-core (CO-4).

Для `kind = SBP` в `payload` — идентификатор агентского списания по привязке счёта; списание инициирует продавец через банк-участник.

**Знак готовности продавца** (A5 п. 5; РП22 п. 7, РП57 п. 2–4). Зону `CONTOUR` определяет знак по записи Платформы, а не то, что о себе сообщает витрина. Знак подаёт и подтверждает эквайрер продавца по ПИ-8, приостанавливает и снимает приостановление оператор. Агент читает знак только через ПАО:

- `GET /pao/v1/merchants/{merchant_id}/readiness` — подписанный запрос агента (§2), пустое тело;
- ответ 200 — `{merchant_id, status, since}`: `status` — `ACTIVE` (знак действует) | `SUSPENDED` (приостановлен оператором) | `NONE` (знака нет, снят эквайрером или продавец Платформе неизвестен); `since` — время записи, от которой действует статус, у `NONE` без записей — `null`;
- `Cache-Control: no-store`: ответ личный и подписанный, перечитывать при каждом решении о зоне;
- `merchant_id` не по форме (пустой, длиннее 128 знаков) — 400 `REQUEST_INVALID`; агент `SUSPENDED` / `EXCLUDED` — 403 `AGENT_SUSPENDED`; проверка обращения — как у остальных методов (§2, §6); сбой хранилища — 503 `STATE_UNAVAILABLE`.
- Причины приостановления агенту не отдаются. Знак не влияет на порядок выдачи (A5 п. 5.2, A6 п. 2.1): Платформа витрины не сортирует и не фильтрует.
- **До ПАО 1.5.0 пути нет в `agent-protocol.yaml`** (РП57 п. 4, как № 41): код и это описание — с v0.24.0, `PAO_SPEC_SHA256` прежний; клиент ПАО агента описывает путь вручную; объявление — в пакете 1.5.0 (#37).

**Длина параметра пути — общее правило транспорта** (РП57 доп. 1; все методы ПАО, не только знак). Параметр пути (`{id}`, `{ref}`, `{op_ref}`, `{merchant_id}` и другие) длиной до 256 знаков доходит до проверки обращения и обработчика: форму и длину по схеме проверяет метод и отвечает по §6 (`REQUEST_INVALID`, `MANDATE_NOT_FOUND` и т. п.). Параметр длиннее 256 знаков отклоняется транспортом раньше проверки обращения: HTTP 414, тело — по §6 (с PS-05б ч. 3, РП62: до ПАО 1.5.0 — `REQUEST_INVALID` `after_fix`, с 1.5.0 — `URI_TOO_LONG`) — не повторять без исправления запроса. Ни один параметр пути ПАО длиннее 256 знаков по схеме не бывает.

**Сверка пакета у продавца** (РП22 п. 6, РП57 п. 5): эквайрер продавца присылает Платформе метаданные пакета (`credential_ref`, `order_ref`, `aoi`) по ПИ-8 и получает сверку `credential_ref` → `op_ref`. Агенту в этом участвовать не нужно: решение ADP от метаданных не зависит.

## 5. События

Доставка — POST на адрес подписки, тело подписано Платформой (с ПАО 1.5.0, §2); повтор с экспоненциальной задержкой до `event_retry_max`. Обработка у агента обязана быть идемпотентной по `event_id`.

**До ПАО 1.5.0 события не подписаны (РП39 п. 6): событие — сигнал, а не источник статуса.** По `mandate.*` агент перечитывает `GET /pao/v1/mandates/{id}` и действует по прочитанному статусу, а не по `type`; это правило безопасно и после 1.5.0. Дубли, а также события, после которых статус не изменился, — норма (повторное решение или запись после отзыва на другом экземпляре, РП38 п. 5).

- **Лента (pull):** `GET /pao/v1/events?after=<event_id>` — события только вашего агента после `after`, по порядку, не больше `event_page_max` за ответ; без `after` — с начала. Курсор — `event_id` последнего обработанного события; повторное чтение даёт те же события с теми же `event_id`. Чужой или неизвестный `after`, а также пустой, повторённый или не по форме `evt_` + UUID — 400 `REQUEST_INVALID` (в YAML — с ПАО 1.5.0). Порядок событий задаёт только лента; push-доставка порядка не гарантирует.
- **Подписка (push):** `PUT /pao/v1/subscription` с `Idempotency-Key` — `url` только `https://`, порт 443, имя хоста (не IP) из списка оператора; иначе 400 `REQUEST_INVALID` (свой код — с ПАО 1.5.0); имя должно разрешаться только в глобальные адреса, проверка — при подписке и перед каждой отправкой. 400 — отказ самого адреса (форма, не глобальный адрес, имени нет в DNS); он сохраняется под ключом идемпотентности, исправленный адрес — с новым `Idempotency-Key`. Временный сбой или таймаут DNS — 503 `STATE_UNAVAILABLE` без сохранения: повтор тем же ключом по `Retry-After`. `events` — типы из таблицы ниже; пустой список выключает push. Подписка действует на события после неё; события, ещё не доставленные push, уходят по **текущей** подписке: после смены `url` повтор идёт на новый адрес, тип исключён из `events` — push по нему прекращается, событие остаётся в ленте (РП40 доп. п. 11). Платформа шлёт POST с `Event` и заголовком `x-event-id`; успех — только 2xx в пределах `event_delivery_timeout_ms`; перенаправления не выполняются; повтор — до `event_retry_max` попыток всего с растущей задержкой, затем событие — только в ленте. Push не заменяет ленту: после сбоя, при старте и после приостановки читайте ленту с курсора (РП40).
- **Приостановление и исключение:** при `SUSPENDED` и `EXCLUDED` лента и подписка — 403 `AGENT_SUSPENDED` (как `GET` мандата; открыт только `GET /pao/v1/agent`, а при `SUSPENDED` — ещё `POST /pao/v1/mandates/{id}/relinquish`, РП38 доп. п. 8, и `POST /pao/v1/agent/keys/{kid}/revoke`, РП60 п. 3), push не выполняется. События сохраняются и после снятия приостановки доступны через ленту; push по накопленным не догоняет (РП40 п. 6–7). О собственном приостановлении агент узнаёт по 403 `AGENT_SUSPENDED` на любом методе, кроме `GET /pao/v1/agent`, отказа от полномочий и отзыва своего ключа, и по push `agent.suspended` — **единственному событию, которое доставляется при `SUSPENDED`**, если тип есть в подписке (РП54 п. 9).
- **`agent.suspended` / `agent.reinstated`** (РП54): `data` — только `{agent_code}`, основания приостановления в событии нет. **До ПАО 1.5.0 событие не подписано:** по push без проверки не действовать — подтвердить статус по `GET /pao/v1/agent`; поддельный `agent.suspended` останавливает агента зря, поддельный `agent.reinstated` ничего не открывает. Событие может не прийти (сбой записи у Платформы, РП54 п. 2): признак приостановления — 403 `AGENT_SUSPENDED`, признак снятия — `ACTIVE` в `GET /pao/v1/agent`. При `EXCLUDED` события нет до ПАО 1.5.0.
- **После снятия приостановления** (РП54 п. 10): `GET /pao/v1/agent` — `ACTIVE`, лента и подписка открыты; лента с прежнего курсора отдаёт всё, что накопилось (`agent.suspended`, `operation.declined` с `AGENT_SUSPENDED`, события мандатов и подтверждений, `operation.*` по авторизованному до приостановления, `agent.reinstated`); push по накопленным не догоняет. Мандаты — в статусе по `GET`, приостановление их не меняет. **Реквизиты и `confirmation_ref`, выданные до приостановления, не действуют и после снятия:** авторизация по такому реквизиту — `CREDENTIAL_INVALID`; повтор `POST /pao/v1/credentials` на тот же заказ вернёт тот же недействующий реквизит — оплата только новым заказом продавца (новый `order_ref`); подтверждение — новым запросом (`CONFIRMATION_REQUIRED`). Граница — до миллисекунды: реквизит и запрос с той же меткой времени, что приостановление, считаются выданными до него — после снятия `CREDENTIAL_INVALID` (fail-closed; DECISIONS РП64 дополнение «2б-2» п. 1, с v0.29.0; контракт ПАО не меняется). Тестам на стенде с подставными часами — после снятия сдвинуть часы хотя бы на 1 мс, иначе новый реквизит попадёт в ту же миллисекунду. Ключи, ключи идемпотентности и nonce не сбрасываются; новый ключ при `KEY_COMPROMISE` — через оператора Системы.
- **`data` событий мандата** — только `{mandate_id}`: ни статуса, ни предмета, ни сумм. Событие даёт запись журнала по мандату: `mandate.signed`, `mandate.rejected`, `mandate.revoked` (отзыв клиентом — одного мандата или всех полномочий клиента одним действием в банке, РП45 п. 4; или ваш `relinquish`), `mandate.exhausted` — закреплён (списан по клирингу) весь предел; резервы, которые ещё не списаны, его не вызывают. Событие может прийти дважды или с задержкой; при нехватке бюджета авторизации отклоняются и до него, статус — через `GET` (РП41 п. 11). У CART, которые теряют силу вместе с родителем, своих событий нет — статус CART берите через `GET` (§3, РП35). **Исключение — отзыв всех полномочий клиента (`revoke-all`, РП46 (а)):** Платформа пишет отзыв каждому действующему мандату клиента, сначала CART, затем родителю, — `mandate.revoked` приходит по каждому, в том числе по CART. Мандаты перестают действовать с фиксации отзыва в Платформе, до прихода событий: `GET` и `verify` уже отвечают `REVOKED` / `OUT_OF_SCOPE`. Мандат, подписанный банком после отзыва, — новое согласие и действует.
- **`data` событий подтверждения** — только `{confirmation_id}` (РП51 п. 1–7). Событие пишется на каждый переход запроса: создание — `confirmation.required`, решение человека — `confirmation.approved` / `.rejected`, истечение — `confirmation.expired`; погашение ссылки своего события не даёт. Номер в ленте — общий с событиями мандатов. По событию — `GET /pao/v1/confirmations/{id}`: сообщить человеку, что нужно подтверждение, `link` передать, ничего не подтверждать самому (Т7); `link` ведёт на страницу УПК (с v0.18.0): человек видит итог, выбирает инструмент и подтверждает одноразовым кодом из своего банка — агенту код недоступен; решить можно и в приложении банка; `confirmation_ref` из `GET` — продавцу, повтор авторизации — новой операцией; `REJECTED`, `EXPIRED` — остановиться, новый заказ — с новым `order_ref` (РП50 п. 9). **Истечение отмечается при обращении**, фоновой задачи нет: после `expires_at` перечитайте `GET` — это чтение переведёт запрос в `EXPIRED` и даст `confirmation.expired`. Инструмент выбирает человек: ссылка действует только в авторизации по выбранному им каналу (`channel`), иначе — `CONFIRMATION_REQUIRED` без нового запроса; решение банка без выбора — по любому каналу при совпадении итоговых значений (РП50 п. 7, РП51 п. 13–14). До PS-21 на странице — только карта (`upk_sbp_enabled`); выбор СБП банком до PS-21 останавливает заказ (РП51 «Дополнения» п. 6).
- **`data` событий операции** — только `{op_ref}` (РП52 п. 7): ни суммы, ни продавца, ни реквизита, ни причины. По событию — `GET /pao/v1/operations/{op_ref}` и действие по прочитанным `status` и `reason`. **`GET` операции — с PS-16 ч. 2;** до неё событие `operation.*` — только сигнал: итог стадии 5 по событиям подтверждается с ч. 2 (РП52 п. 10, решение владельца 22.10). **`operation.authorized`** — только после одобрения эмитента (не по решению ADP); **`operation.declined`** — отказ ADP или эмитента, в том числе при отзыве и истечении мандата и при приостановлении агента (тогда событие ждёт в ленте до снятия приостановки) — `mandate.*` и `agent.*` итог операции не заменяют (РП52 п. 4). Событие отказа ADP приходит не позже **`operation_outcome_max_delay_sec`** (стенд — 30 с) после решения, событие по ответу эмитента — сразу; ожидание итога стройте от этого предела (РП52 п. 12). **Нет события за `operation_outcome_max_delay_sec` — перечитайте `GET /pao/v1/operations/{op_ref}`** (с ч. 2): итог отказа ADP `GET` отдаёт из записи операции и тогда, когда события нет (например, после простоя сборщика дольше горизонта, РП52 «Дополнения» п. 1). Отказ, при котором Платформа не установила агента по своей записи токена (`AOI_MISSING`, `AGENT_UNKNOWN`, неопознанный реквизит), событием не приходит (РП52 п. 5): итог стадии 5 тогда — «не подтверждён». На `CONFIRMATION_REQUIRED` события `operation.*` нет — есть `confirmation.required`.
- **Причины `operation.declined` — закрытый перечень** (РП52 п. 6; в 1.4.0 `reason` — строка, `enum` — с ПАО 1.5.0): `AOI_MISMATCH`, `AGENT_SUSPENDED`, `CREDENTIAL_INVALID`, `MANDATE_NOT_FOUND`, `MANDATE_EXPIRED`, `MANDATE_REVOKED`, `MANDATE_SCOPE`, `LIMIT_EXCEEDED`, `STATE_UNAVAILABLE`, `ISSUER_DECLINED` (отказ эмитента; причина эмитента, в том числе нехватка средств, — до 1.5.0 только так). Неизвестная причина — остановиться по операции, без повтора.
- **`GET /pao/v1/operations/{op_ref}`** (с PS-16 ч. 2, РП52 п. 10, РП53 п. 10; в v0.19.0 маршрута нет — 404): только операция вашего агента с итогом; тело `Operation` 1.4.0 — `status` `AUTHORIZED` | `DECLINED` | `CONFIRMATION_REQUIRED` | `SETTLED`, `reason`, `order_ref`, `amount`, `merchant_id`, `channel`, `aoi`, `fulfilment`. Итог отказа ADP и `CONFIRMATION_REQUIRED` — из записи операции, без ожидания события. Чужая, неизвестная, без установленного агента или ещё без итога (между одобрением ADP и ответом эмитента) — 400 `REQUEST_INVALID` (`OPERATION_NOT_FOUND` — с 1.5.0); `SUSPENDED` — 403 `AGENT_SUSPENDED`. С PS-16 ч. 3 (РП55) — ещё `REVERSED` и `REFUNDED` (ниже).
- **`REVERSED` — реверсал и истечение авторизации** (РП55 п. 1–2): процессинг отменил авторизацию (`reason: REVERSAL`) или она истекла без клиринга (`reason: AUTH_EXPIRED`); бюджет мандата освобождён. **События нет до ПАО 1.5.0** (`operation.reversed` — с 1.5.0): после `operation.authorized`, пока нет `operation.settled`, перечитывайте `GET /pao/v1/operations/{op_ref}` не чаще раза в **`operation_reread_interval_sec`** (стенд — 3 600 с) и прекращайте на `SETTLED`, `REFUNDED`, `REVERSED` или по истечении срока авторизации — до отдельного параметра срока (PS-07) это `reservation_ttl_sec` (стенд — 7 дней) от `operation.authorized`. Реверсал может прийти и до ответа эмитента: тогда `operation.authorized` не будет, итог — `REVERSED` по `GET`. **Клиринг старше реверсала** (РП55 «Дополнения КТ1» п. 3): если после реверсала всё же пришёл клиринг, приходит `operation.settled`, `GET` — `SETTLED` с `fulfilment.scope_check: NOT_RESERVED` (деньги списаны, бюджет мандата этого не учёл — показать человеку); возврат после него — `REFUNDED`.
- **`REFUNDED` и `operation.refunded` — возврат** (РП55 п. 3): после клиринга продавец или спор вернули деньги; `data` — `{op_ref}`, по событию — `GET`: `status: REFUNDED`, `fulfilment` прежний, `reason: null`; сумма возврата — с 1.5.0. **Бюджет мандата при возврате не восстанавливается** (`restore_budget_on_refund = false`, РП9): исчерпанный мандат остаётся `EXHAUSTED`. Один возврат на операцию; несколько — PS-23. Возврат приходит и после отзыва мандата и приостановления агента (при `SUSPENDED` — в ленте после снятия).
- **`GET /pao/v1/operations?mandate_id=`** (РП55 п. 6): массив `Operation` вашего агента по этому мандату — только операции с итогом, у которых мандат записи операции — этот (операции CART при запросе по INTENT не входят; запрашивайте по CART), по времени решения. Чужой, неизвестный, не по форме мандат или запрос без `mandate_id` — 404 `MANDATE_NOT_FOUND` (в YAML — с 1.5.0); больше `event_page_max` операций по мандату — 400 `REQUEST_INVALID` (постраничный вывод — с 1.5.0; в счёт входят и операции ещё без итога, которых в ответе нет — РП55 «Нюансы реализации (К2.1)» п. 1); `SUSPENDED` — 403 `AGENT_SUSPENDED`.
- **`operation.settled` и запись об исполнении** (РП53): событие — после клиринга (`PRESENTMENT`), `data` — `{op_ref}`; по нему — `GET`: `status: SETTLED`, `fulfilment` — `fulfilment_ref`, `final_amount` (сумма клиринга в минимальных единицах; валюта — валюта операции, поле `currency` — с 1.5.0), `scope_check`, `spent_position`, `at`. Запись формирует Платформа по сообщению процессинга, не по словам продавца или агента (A1 п. 6.2). **`scope_check`** (в 1.4.0 — строка, `enum` — с 1.5.0): `WITHIN_LIMITS` — в пределах одобренного; `EXCEEDS_AUTHORIZATION` — клиринг больше одобренной суммы (бюджет закреплён на одобренную, основание для спора); `NOT_RESERVED` — хотя бы одно удержание операции освобождено до клиринга (бюджет учёл списание не полностью); `NOT_RESERVED` перекрывает `EXCEEDS_AUTHORIZATION`, а `spent_position` при нём может быть ненулевым (РП53 «Дополнения КТ1» п. 2). Человеку показывается всё, кроме `WITHIN_LIMITS`; неизвестное значение — показать как есть, без догадки. **`spent_position`** — сколько из предела мандата операции (`aoi.mandate_id`) израсходовано (закреплено) на момент записи после этого клиринга, в минимальных единицах валюты операции; у одного CART с несколькими платёжными событиями по одному `order_ref` (A1 п. 6.3) — накопленная сумма. Частичный клиринг закрепляет свою сумму, остаток резерва освобождается. **`aoi` при `AOI_MISMATCH` в `GET` не отдаётся** (РП53 «Дополнения КТ1» п. 3): признак в сообщении называет другого агента и чужой мандат; агенту достаточно причины, полный признак — в записи Платформы для спора.

| Событие | Когда | Что обязан сделать агент (SPEC BuyerAgent) |
|---|---|---|
| `mandate.signed` | Принципал подписал | Продолжить стадию |
| `mandate.rejected` | Принципал отказал | Сообщить человеку, остановиться |
| `mandate.revoked` | Отзыв | Остановить начатое, отчитаться о незавершённом (Т13) |
| `mandate.exhausted` | Бюджет исчерпан: закреплён весь предел | Уведомить человека |
| `confirmation.required` | ADP потребовала подтверждения | Передать человеку ссылку, не имитировать (Т7) |
| `confirmation.approved` / `.rejected` / `.expired` | Итог подтверждения | Повторить через продавца с `confirmation_ref` / остановиться |
| `operation.authorized` | Авторизация одобрена эмитентом | `GET` операции; показать человеку |
| `operation.declined` | Отказ ADP или эмитента; `reason` — из перечня выше | `GET` операции; поведение по причине (SPEC BuyerAgent §7б) |
| `operation.settled` | Клиринг, запись об исполнении | Итог и документы человеку (Т11) |

| `agent.suspended` / `agent.reinstated` | Статус допуска (`data` — `{agent_code}`, РП54) | `GET /pao/v1/agent`; остановиться / продолжить по прочитанному статусу |
| `dispute.updated` | Решение по спору | Сообщить человеку |

**Правило источника истины.** О результате операции агент узнаёт из события Платформы, а не со слов продавца. Если сообщение продавца расходится с событием Платформы, агент верит Платформе и записывает расхождение. До ПАО 1.5.0 событие не подписано: по нему агент перечитывает статус через `GET` и верит прочитанному (РП39 п. 6).

## 6. Ошибки

Тело ошибки: `{ "code", "message", "norm", "retry": "never|after_fix|same_key|new_key|after_human" }`. Перечень кодов с HTTP-статусом и `retry` — в `agent-protocol.yaml`, расширение `x-pao-errors` (источник; таблица ниже — для чтения, при расхождении верен YAML; РП16).

**Ответы транспорта** (РП62, с PS-05б ч. 3; ПАО остаётся 1.4.0): в пути `/pao` и отказ до проверки обращения приходит телом §6, без полей RFC 9457 — нет маршрута (404, в том числе `HEAD`), тело больше 64 КиБ (413), параметр пути длиннее 256 знаков (414), испорченное процентное кодирование или `%` в пути, неразборный `Content-Type` (400), сбой Платформы (503 `UPSTREAM_UNAVAILABLE` с `Retry-After`). **До ПАО 1.5.0** у 404 / 413 / 414 код тела — `REQUEST_INVALID` (`after_fix`), а HTTP — свой, не 400 из таблицы: не повторяйте, сверяйте запрос. **С 1.5.0** — свои коды: `NOT_FOUND` 404 `never`, `PAYLOAD_TOO_LARGE` 413 `after_fix`, `URI_TOO_LONG` 414 `after_fix` (совместимо по §7). Два значения подписываемого заголовка или тело у `GET` — `SIGNATURE_INVALID`; два `Idempotency-Key` — `REQUEST_INVALID`.

Значения `retry`:

| Значение | Что делает клиент |
|---|---|
| `never` | Не повторяет. |
| `after_fix` | Повтор только после исправления запроса или состояния на своей стороне. |
| `same_key` | Повтор с тем же `Idempotency-Key`; новые `x-nonce`, `x-timestamp` и подпись. Если есть `Retry-After` — не раньше указанного. Число повторов ограничивает клиент; после исчерпания — ошибка вызывающему. У `IDEMPOTENCY_REQUIRED` — добавить ключ и повторять с ним же. |
| `new_key` | Нужен новый ключ подписи агента (не ключ идемпотентности); повтор — после выпуска и регистрации ключа. |
| `after_human` | Повтор после действия человека (подпись, подтверждение, изменение мандата). |


| Код | HTTP | Причина | `retry` |
|---|---|---|---|
| AGENT_UNKNOWN | 401 | Нет в реестре | never |
| AGENT_SUSPENDED | 403 | Приостановлен | never |
| AGENT_KEY_REVOKED | 401 | Ключ отозван или истёк | new_key |
| SIGNATURE_INVALID | 401 | Подпись, окно времени, повтор nonce | after_fix |
| MANDATE_NOT_FOUND | 404 | Мандат не найден | after_human |
| MANDATE_EXPIRED | 409 | Мандат истёк | after_human |
| MANDATE_REVOKED | 409 | Мандат отозван | never |
| MANDATE_SCOPE | 409 | Продавец, категория или сумма вне мандата | after_human |
| PRINCIPAL_SIGNATURE_PENDING | 409 | Мандат ещё не подписан | after_human |
| LIMIT_EXCEEDED | 409 | Ограничение инструмента или лимит клиента в банке (`per_operation`, `per_period` — РП45 п. 1; сужение лимита в банке действует сразу, в том числе в текущем периоде, РП46 (г); повтор не поможет до нового периода или правки лимита в банке) | after_human |
| STATE_UNAVAILABLE | 503 | Состояние не подтверждено | same_key |
| CONFIRMATION_REQUIRED | 428 | Нужно подтверждение | after_human |
| CREDENTIAL_INVALID | 409 | Реквизит использован, истёк, не для этого продавца | after_fix |
| CREDENTIALS_FORBIDDEN | 422 | В запросе есть платёжные реквизиты | never |
| IDEMPOTENCY_REQUIRED | 400 | Нет ключа | same_key |
| IDEMPOTENCY_CONFLICT | 409 | Тот же ключ, другое тело | after_fix |
| RATE_LIMITED | 429 | Частота | same_key |
| UPSTREAM_UNAVAILABLE | 503 | Компонент Платформы недоступен | same_key |
| REQUEST_INVALID | 400 | Тело изменяющего метода не по схеме метода (v1.3.0, РП31) | after_fix |
| KEY_INVALID | 422 | Ключ не принят в `POST /pao/v1/agent/keys` (v1.3.0, РП31) | after_fix |

## 7. Версии и совместимость

- Версия в пути (`/pao/v1`). Совместимые изменения — новые необязательные поля и новые типы событий; обязательность поля **ответа**, которое Платформа отдавала во всех ответах и прежде (агенту — ослабление: поле, которое он мог не получить, приходит всегда; РП37, `Mandate.agent_code`), — тоже; обязательность поля запроса — несовместима; агент обязан игнорировать неизвестные поля и события. Совместимо и ослабление `retry` у существующего кода — разрешение повтора там, где его не было (`never` или `after_fix` → `same_key`); обратный переход несовместим (РП18). Совместимость не отменяет обоснования: перевод кода из never в same_key — отдельным решением РП с оценкой безопасности повтора.
- Новое значение `ErrorCode` с `retry` `after_fix` или `never` — совместимо: агент на неизвестный код останавливается (fail-closed), и это поведение совпадает с `after_fix`. Новое значение с `same_key` — несовместимо: агент прежней версии не повторит там, где повтор ожидается (РП31 п. 4).
- Несовместимые изменения — только новой версией с периодом параллельной работы не меньше `protocol_overlap_days`.
- `GET /.well-known/pao-configuration` сообщает поддерживаемые версии и дату вывода старых.

Агент публикует Agent Card (A2A) с расширением `x-system`: `agent_code`, класс, принципал (тип), источник знания, ссылка на `/.well-known/pao-configuration` Платформы. Платформа при допуске сверяет карточку с заявлением. Отступления фиксируются в журнале расхождений (A9 п. 5).

## 8а. Условное исполнение (v1.1.0)

Мандат с `settlement_mode = CONDITIONAL` и `conditional = {provider, deal_ref}` направляет оплату на счёт эскроу поставщика условного исполнения. `deal_ref` переносится в признак и операции; итог сделки приходит событиями `deal.funded`, `deal.released`, `deal.returned`. Метода «раскрыть эскроу» в ПАО нет. Подробно — `CONDITIONAL-EXECUTION.md`.
