# Экран мандатов в приложении банка — инструкция встраивания

Эталонный модуль `src/ui/mandates/` (UI-К2 ч. 1–3; DECISIONS РП36 «Нюансы UI-К2» ч. 1–3, РП74). На стенде он работает с данными стенда (`src/env/issuer/screen.ts`, `stand.bankApp`). Банк ставит модуль у себя и подключает его к своему серверу через порт. Экран ничего не решает и не пишет сам: решения клиента банк подписывает своим ключом и отправляет по ПИ-8.

## 1. Что умеет экран

| Страница | Что видит и делает клиент | ПИ-8 |
|---|---|---|
| `/` | Покупки, ждущие подтверждения, затем мандаты: сначала ждущие подписи. Ссылки «Отозвать все полномочия», «Агенты», «Уведомления», выход | чтения — РП74 п. 3, 7 |
| `/m/{id}` | Мандат: агент, вид, состояние, предел с валютой, срок, продавцы, поручение, корзина, контрольная сумма. Кнопки «Подписать» / «Отклонить» (только `PENDING_SIGNATURE` в сроке), «Отозвать» (только `ACTIVE`), ссылка на историю, раздел «Споры» (только надпись) | `POST …/mandates/{id}/sign`, `…/revoke`; чтение — РП74 п. 4 |
| `/m/{id}/history` | История мандата по журналу Платформы | чтение — РП74 п. 6 |
| `/m/{id}/revoke`, `/revoke-all` | Шаг подтверждения отзыва, затем запись | `…/revoke`, `…/principals/{ref}/revoke-all` |
| `/c/{id}` | Подтверждение покупки: продавец, сумма, заказ, агент, мандат, срок; подсказка о приостановленном агенте; кнопки «Подтвердить покупку» / «Отклонить» | `POST /participants/v1/confirmations/{id}`; чтение — РП74 п. 7 |
| `/agents` | Агенты клиента: класс и статус | чтение — РП74 п. 8 |
| `/notifications` | Уведомления `client.*` клиента | `GET /participants/v1/notifications` (есть) |

**Обновление главной без F5 — только стенд** (РП36 «Нюанс UI-К2 — З9» п. 2). Параметр модуля `refresh_sec` — целое 2…60, иначе модуль не запустится; не задан — обновления нет, так модуль и отдаётся банку. На стенде — 5 с: главная `/` при ответе 200 получает `<meta http-equiv="refresh">`, новое поручение или корзина появляются без перезагрузки. На страницах решения и в формах обновления нет. Скриптов нет, CSP прежняя. Сессия обращениями не продлевается: через 15 минут (срок сессии стенда) главная отвечает 401 без мета-тега, обновление останавливается, вход заново — по ссылке с монитора.

Номера карты на экране нет (инвариант 1). Суммы выводятся из минимальных единиц с учётом валюты (правило совместимости 2). Тексты — только из словаря экрана `text.ts` на ru и en, коды Платформы человеку текстом не показываются.

## 2. Порт банка

`MandatesScreenPort` (`src/ui/mandates/port.ts`) — единственная связь экрана с банком. Каждый метод получает `principal_ref` из сессии экрана.

- **Чтения:** `mandates`, `mandate`, `history`, `confirmations`, `confirmation`, `agent`, `notifications`.
  - Чужое и неизвестное возвращается как `undefined` (экран отвечает 404).
  - Сбой — исключение (экран отвечает 503 без кнопок, инвариант 3).
  - Значения берутся из записей Платформы (инвариант 5), банк их не пересчитывает.
- **Действия:** `decide`, `revoke`, `revokeAll`, `confirm`. Банк подписывает запись ПИ-8 своим ключом участника и разбирает ответ ПИ-8 в результат порта:
  - образец разбора — адаптер стенда `src/env/issuer/screen.ts`;
  - прочие ответы (401, 503, неожиданный HTTP) — исключение.
- **`confirm`** подписывает `totals_hash` из формы — итог, который видел человек, а не пересчитанный в момент нажатия (инвариант 7). `instrument_chosen` банк не передаёт (РП51 п. 13).
- **`decide`.** `SIGN` уходит с `token_consent: true`, `REJECT` — с `false` (РП12). Подпись мандата и согласие на токен — одно действие.
- **`revokeAll`.** `revocation_ref` создаёт экран на странице подтверждения. При сбое (503) повтор идёт с тем же `revocation_ref` — это безопасно.

**Чтения для настоящего банка.** Из чтений, которые нужны экрану, у банка в ПИ-8 сейчас есть только лента уведомлений. Мандаты, история, запросы подтверждения и статус агента для `ISSUER` описаны в РП74 и делаются отдельной задачей «перед пилотом с банком». До неё экран работает только на стенде.

**Уведомления.** Лента ПИ-8 — общая для всех клиентов банка. Порт отбирает записи клиента по `data.principal_ref`. Адаптер стенда перечитывает ленту с начала при каждом показе страницы, банку так делать не нужно: он хранит прочитанную ленту у себя (курсор `after`, вебхук-сигнал по `notify_url`) и отбирает записи по клиенту в своём хранилище.

## 3. Вход

1. Банк уже опознал клиента в своём приложении и выдаёт одноразовую ссылку `loginPath(principal_ref)` → `/login/{token}`.
2. Переход по ссылке гасит токен и открывает сессию в cookie `__Host-bank-mandates` с атрибутами `HttpOnly; Secure; SameSite=Strict; Path=/`.
3. Неизвестный, погашенный и истёкший токен получают один и тот же ответ 401. В хранилище лежит только SHA-256 токена.
4. **Сроки — параметр `ttl` модуля:**
   - срок ссылки `login_ttl_sec` — 1…600 с, на стенде 120;
   - абсолютный срок сессии `session_ttl_sec` — 1…3600 с, на стенде 900.
5. **Срок сессии и срок запроса подтверждения.** На стенде срок сессии равен `order_hold_sec` (900 с). Человек, открывший экран раньше, чем пришёл запрос, может не успеть ответить в той же сессии. Тогда он входит заново из приложения банка, а запрос действует до своего `expires_at`. Банк выбирает срок сессии сам, с учётом сроков удержания заказа у своих продавцов.
6. **Сессии хранятся в памяти экземпляра модуля.** Если у банка несколько экземпляров, клиент должен попадать на один и тот же (привязка на балансировщике), либо банк хранит сессии у себя.
7. **Остаточные риски** (РП36 «Нюанс ч. 1» п. 6):
   - предзагрузчик ссылок в мессенджере или почте может погасить ссылку — человек увидит 401 и войдёт заново;
   - вход по чужой ссылке откроет сессию чужого клиента — поэтому ссылку выдаёт только приложение банка внутри своей сессии клиента, внешних ссылок нет.

## 4. Транспорт и безопасность

- **Только TLS.** Cookie всегда с `Secure`. По http браузер принимает её только с `localhost` или `127.0.0.1` (так устроен стенд); на любом другом адресе по http человек после ссылки увидит 401.
- **Встраивание** — веб-вид (WebView) верхнего уровня, не фрейм. Заголовки безопасности экрана запрещают показ во фрейме.
- **CSRF.** У каждой формы есть токен сессии, сравнение — за постоянное время. Без токена или с чужим ответ 403, сессия не закрывается.
- **Журнал процесса** — через `logger` модуля: в журнал попадают метод и шаблон маршрута (`/login/:token`), без токена ссылки, cookie и CSRF (РП61 п. 3, РП63 п. 13).
- **Лимит частоты — `rate_limit_per_30s`** (целое ≥ 1, иначе модуль не запустится; на стенде 600). Это грубый лимит по адресу обращения на всё приложение экрана, окно 30 с, IPv6 считается по /64. При превышении — страница 429 с `Retry-After` не больше 30.
  - **Величину задаёт банк.** В приложении банка многие клиенты могут выходить в сеть с одного адреса (NAT оператора связи). Предел подбирается под пиковое число клиентов за одним адресом, иначе они получат 429.
  - **Прокси перед экраном.** Модуль создаёт свой сервер Fastify без `trustProxy`, поэтому адрес обращения — это адрес ближайшего узла. За прокси банка все клиенты считаются с адреса прокси и делят один счётчик. Пока у модуля нет параметра доверенных прокси (STATUS «Открыто»), лимит по адресу клиента ставится на прокси банка, а `rate_limit_per_30s` модуля задаётся с запасом на весь поток через прокси.

## 5. Язык и бренд

- **Настройка `settings` (`UiSettings`):**
  - `lang` — `ru` или `en`, язык по умолчанию; переключение — параметром `?lang=` или полем формы `lang`;
  - `brand.name` — 1–64 знака;
  - `brand.color` — `#rrggbb`;
  - `brand.logo_url` — необязательно, только `https://`;
  - `time_zone` — необязательно, имя пояса IANA (например, `Europe/Moscow`); не задан — пояс процесса.
- **Время для человека** (РП36 «Нюанс UI-К2 — З9» п. 1): «действует до», «решить до», история и уведомления — по языку страницы (`ru` — «10.11.2026, 13:54», `en` — «10/11/2026, 13:54») в поясе `time_zone`. Машинное значение — в `<time datetime>`. Строка не в формате RFC 3339 показывается как есть.
- Неверная настройка — отказ запуска, а не страница с чужим кодом (правило совместимости 3).
- Тексты лежат в `src/ui/mandates/text.ts`, по словарю на ru и en. Новый язык — новый словарь с теми же ключами. Неизвестный код Платформы экран показывает как есть и без действий.

## 6. Что экран не делает

- **Не скрывает кнопку «Подтвердить» у приостановленного агента** (РП54, РП74 п. 9). Подсказка поясняет, что оплаты не будет; отказ ставит ADP.
- **Не показывает признак дробления** `split_detected` (РП74 п. 10).
- **Не ведёт споры:** раздел «Споры» — только надпись. Споры — PS-22, «перед пилотом с банком».
- **Не подписывает усиленной подписью.** Мандат выше порога простой подписью не подписывается: экран говорит клиенту, что нужна усиленная подпись (422 `QUALIFIED_SIGNATURE_REQUIRED`, A7 п. 3.2).

## 7. Как банк берёт модуль

Модуль лежит в исходниках репозитория. В публичных путях пакета (`exports`: `./stand`, `./fixtures`) его нет. Банк берёт `src/ui/mandates/` и `src/ui/shared/` как образец вместе с зависимостями: `fastify`, `@fastify/rate-limit`, `src/http/request-log.ts`, `src/shared/rate-limit.ts`, формы id из `src/consent/model.ts` и `src/confirm/model.ts`.

**Проверка у себя** — тесты `tests/ui/mandates-screen*.test.ts` с подставным портом. Сквозной путь на стенде: `stand.bankApp.session(principal_ref)` → вход → действия → ПИ-8.
