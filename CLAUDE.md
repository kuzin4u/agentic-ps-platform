# agentic-ps-platform — агентная платформа платёжной системы

## Что это за проект

Сервисный слой оператора платёжной системы, который делает агентную операцию видимой, ограниченной и разбираемой на действующих рельсах (карты «Мир», СБП, универсальный платёжный код). Две внешние границы:
1. **интерфейс с процессингом и системами оператора** (ПИ-1–ПИ-9): точка решения ADP в пути авторизации, события операции, токен-сервис, СБП, УПК, антифрод, участники, отчётность;
2. **Протокол агентских операций (ПАО)** для агентов покупателя, в первую очередь BuyerAgent из репозитория `agentic-buyer-ref`.

Реального процессинга нет, поэтому в репозитории живут **эмуляторы окружения**: ОПКЦ, эмитенты, эквайрер, продавцы, СБП, УПК, токен-сервис. Они говорят на канонической модели.

Главный принцип: **агент не инициирует авторизацию.** Он получает агентский реквизит и передаёт продавцу; авторизация идёт продавец → эквайрер → ОПКЦ → ADP → эмитент (РП2).

## Каждая сессия

`/start` → задачи из `docs/core/STATUS.md` → `/finish` перед `/exit`. Новая задача — только через `/task`, изменение документа — только через `/decision`.

## Общие правила

- Правки — только после «да» владельца. Коммит — с подтверждения владельца. Push в ветки `task/*` и PR Claude Code делает сам; слияние PR и теги — только владелец. Push в `main`, принудительный push, push тегов блокирует хук `guard.py`. Ветка `claude-setup`, затем `task/<код>`.
- Язык документов и коммитов — русский, идентификаторы — английские.
- Расхождение документа и кода — в `STATUS.md` «Расхождения» и предложение `/decision`, без молчаливых правок.
- Номер поля или кода внешнего формата не выдумывать: только каноническая модель и пометка `[альбом]` (РП6).
- Нюансы, найденные в сессии (граничные случаи, повторы, гонки, остаточные риски, отступления от протокола), — в документы, а не только в код и PR: DECISIONS, SPEC, AGENT-PROTOCOL (если касается агентов), STATUS. Тем же кирпичом, что и код, или при `/finish` (правило владельца, 17.10.2026).

## Работа через GitHub (с 12.10.2026)

Ревьюер из чата claude.ai читает репозиторий через коннектор GitHub и пишет
только комментарии в PR. Слияние и теги — только владелец, в терминале.

### Начало задачи
1. Ветка task/<код> от свежего main (git checkout main && git pull).
2. Сразу push ветки и черновой PR (gh pr create --draft): в описании — план
   задачи (нормы, инварианты, файлы, проверки, время) и раздел «Кирпичи»
   (см. ниже).
3. Владелец просит ревьюера «проверяй <репо> #N»; дальше ждать «да» или
   «читай ревью».

### Кирпичи (Д2, 14.10.2026)
- Задача делится на кирпичи с кодами К<N>.<M> (К1.1, К1.2…); подшаг —
  буквой (К1.1а). Кирпич — одна проверяемая правка.
- В платформе П<N> — компоненты (П1 реестр … П11 отчётность), РП<N> —
  решения DECISIONS; кирпичи — только К<N>.<M>.
- В описании PR — раздел «Кирпичи»: таблица «Кирпич | Коммит | Состояние».
  Пустой коммит «план: …» для чернового PR — без подтверждения.
- Кирпич = отдельный коммит, только после «да» владельца; в сообщении
  коммита — код кирпича первым словом.
- После каждого кирпича — отметка в таблице через gh pr edit N --body-file …
  (хэш коммита, что проверено).
- Новый шаг из ревью — новой строкой с источником («ревью из чата № 3»);
  перенесённый — строкой со ссылкой на STATUS «Открыто» и задачу.

### Решения
- Текст /decision до записи — комментарием в PR (gh pr comment N --body-file …),
  в окне — только вопрос владельцу. Запись в DECISIONS — после «да».

### «Читай ревью #N»
- Комментарии ревьюера начинаются с «Ревью из чата:» — все комментарии в PR
  от аккаунта kuzin4u, автор различается только по этой метке; свои ответы
  начинай с «Claude Code:».
- gh pr view N --comments; разобрать замечания ревьюера: блокеры — исправить,
  остальное — исправить или в STATUS «Открыто» с адресом задачи; ответ —
  комментарием в PR (что сделано, что перенесено и куда).

### Чек-лист
- Перед коммитом: git status -sb — ветка task/*, не main; файлы явно, без
  git add -A, если не оговорено.
- Перед «готово к слиянию»: CI зелёный; /finish закоммичен в эту же ветку;
  PR переведён из черновика (gh pr ready N).
- Слияние, тег, «PR слит» — не делать и не утверждать: только после того, как
  владелец сообщит вывод `✓ Merged` и `git log --oneline -1` на main.
- Тег — только на коммит слияния main, только владелец.
- Поломка (временная правка → красный нужный тест → откат) проверяется
  локально; через CI — только если тест зависит от среды CI (PostgreSQL,
  сеть, стенд Платформы). Решение владельца, 18.10.2026.

## Совместимость с планами «Россия» и «Запад»

Правила обоих планов ред. 1 (`docs/reference/joint-plan.md` — «Россия», общее
ядро; `docs/reference/plan-west.md` — «Запад»); проверяются на ревью каждого
кирпича.

1. **Только через порт.** Агент работает с Платформой только через ПАО и
   пакет стенда; форматы оператора и сетей (НСПК, Visa, Mastercard) — только
   в `src/adapters/` по альбомам (РП6), ПАО и каноническая модель их не знают.
2. **Сумма — число в минимальных единицах + валюта** (ISO 4217). В ПИ и ПАО
   так уже сейчас (`amount`/`amount_limit` + `currency`); новое поле суммы —
   только парой с валютой, даже если пока только рубли.
3. **Экраны — с переключением языка и настройкой бренда.** Экраны эмуляторов
   (приложение эмитента, страница УПК) — с первого коммита; в ADP, ПАО и
   канонической модели текстов для человека и бренда нет, только коды.

## Инварианты Платформы

1. **Номера карт нет нигде.** Ни в канонической модели, ни в ПАО, ни в журнале, ни в тестах. Только `token_ref`, `funding_ref`, `account_link_ref`.
2. **Неагентские операции не затрагиваются.** `BYPASS` — первая проверка ADP; отказ ADP отклоняет только агентские операции (РП4).
3. **Fail-closed для агентских.** Неподтверждённое состояние, неизвестный тип ограничения, таймаут — отказ, не догадка (A3 п. 4.5).
4. **Неделимое расходование.** Резерв атомарен; конкурентные авторизации не превышают бюджет ни на копейку; резерв → закрепление → освобождение (РП11).
5. **Источник истины — записи, а не стороны.** Класс и уровень агента — из реестра; `in_scope` — сопоставлением с записью мандата; сумма — из сообщения процессинга; запись об исполнении формирует Платформа.
6. **Журнал согласий неизменяем.** Только вставка; хэш-цепочка; изменение — новой записью с `parent_id`.
7. **Подтверждение — только человеком** на странице УПК или в приложении эмитента; `confirmation_ref` однократный и привязан к итоговым значениям.
8. **Отзыв распространяется** до ADP и шлюза за ≤ `revocation_propagation_max_ms`; авторизованное до отзыва исполняется.
9. **События агенту подписаны** Платформой; доставка «не менее одного раза», идемпотентно по `event_id`. Подпись — с ПАО 1.5.0; до неё событие — сигнал, статус — через `GET` (РП39 п. 6).
10. **ПАО — публичный контракт.** Несовместимое изменение — только новой версией пути.

**Правило приёмки:** сценарий, пройденный обходом нормы, — провал.

## Стек

TypeScript, Node ≥ 20.19 (`engines`; CI — матрица 20.19 и 22, К3.1 служебной 14.10), Fastify, PostgreSQL 16, vitest, docker compose для песочницы (РП10). Подпись — ed25519 в песочнице; ГОСТ — точка расширения (РП5).

**Смена тега ядра** (`@kuzin4u/agentic-core`, РП46 нюанс К1.1): ссылка в `package.json` → `version` и `resolved` в `package-lock.json` на `git+https://github.com/kuzin4u/agentic-core.git#<полный хэш коммита тега>` (`git -C ../agentic-core rev-parse vX.Y.Z^{commit}`) → `npm ci` → `grep -n agentic-core package.json package-lock.json` и `version` в `node_modules/@kuzin4u/agentic-core/package.json`. `npm install` для смены тега не использовать: он оставляет прежний коммит в lock и переводит `resolved` на `git+ssh`, а `package.json` — на `github:`.

## Секреты

Ключей API модели здесь нет: Платформа не использует языковую модель. Ключи подписи Платформы и агентов в песочнице генерируются при старте во временный каталог. `.env`, `*.pem`, `*.key` не читать и не писать.
